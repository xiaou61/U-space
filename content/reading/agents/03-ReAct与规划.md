## 先把结论摆出来

ReAct 的意思是 **Reason + Act**：让模型在同一个循环里交替"想"和"做"，而不是先想完全部再一口气执行。

它解决的是一个很具体的问题：**模型如果先规划完整步骤再动手，第一步拿到的事实和计划不符时，它不会回头改计划**。边做边看，才能在信息不全时修正。

## 为什么"先想清楚再动手"会翻车

设想你让 Agent "查一下这个接口为什么慢"。

**先规划后执行**：模型一口气写出 5 步计划——看日志、看监控、看代码、看索引、给结论。然后逐步执行。问题在于写计划时它还没看过日志，第 3 步"看代码"要看的文件，取决于第 1 步日志里出现的类名。计划里写不出来，只能写"看相关代码"，执行时就变成瞎猜。

**边做边看**：看日志 → 发现是 `OrderMapper.selectByUser` 慢 → 去看这个方法 → 发现缺索引 → 结论。每一步都基于上一步的真实结果。

差别不在于模型聪明不聪明，在于**信息什么时候进入上下文**。ReAct 让事实在它被需要的那一刻才进来。

## 循环长什么样

```text
Thought:   我需要先知道哪个方法慢
Action:    查慢查询日志
Observation: OrderMapper.selectByUser 平均 1.2s

Thought:   这个 SQL 要查 user_id + created_at
Action:    看这张表的索引
Observation: 只有 PRIMARY 和 uk_order_no

Thought:   缺 (user_id, created_at) 联合索引
Answer:    ...
```

三段式的关键在 **Observation 必须是真实执行结果**，不能是模型自己编的。这一点很容易被忽视：如果工具调用失败但你给模型的 Observation 是"执行成功，结果为空"，它会基于假事实继续推理，一路错到底。

**工具失败要如实告诉它。** "连接超时"这四个字比任何兜底话术都有用——模型看到这个会换策略，看到"结果为空"只会认为真的没有。

## 三种"规划"的层次

"规划"这个词在 Agent 语境下指三种完全不同的东西，混在一起讲就会乱：

**一、隐式规划**（ReAct 就是这种）
模型每一步都想一句，没有显式的计划列表。灵活，但会绕路——它可能反复看同一个文件，因为"忘了"已经看过。

**二、显式计划**
先让模型输出一个任务列表，然后逐项执行，每完成一项标记掉。好处是进度可见、不会丢项；坏处是计划本身可能错，需要"重新规划"机制。

**三、固定工作流**
步骤写死在代码里，模型只负责每步的内部处理。**这不是 Agent**（见上一篇的判据），但在真实产品里用得最多，因为可测、可控、便宜。

实践中常见的是混合：外层固定流程（确定的部分），内层某一步交给 ReAct（不确定的部分）。比如"必须先生成大纲、再逐节写"——外层写死，每节内容怎么写让模型自由发挥。

## 翻车的四种典型方式

### 一、绕圈

模型反复调同一个工具、拿同样的结果。原因是它"忘了"自己查过——历史里塞了太多内容，早期的观察被稀释了。

**对策**：在上下文里显式记录"已查过哪些"（比如维护一个已读文件列表），或者干脆在轮次上限上硬截断。

### 二、过早收手

查了一条信息就下结论，明明还差一半。

**对策**：系统提示词里明确"结论必须基于哪些证据"，或者加一个检查步骤——让模型自己核对结论是否被观察支持。

### 三、幻觉观察

模型不调工具，直接编一个 Observation 出来（尤其在它"觉得"自己知道答案时）。

**对策**：把 Observation 的生成权完全收归代码，模型只能产出 Action。这一条是架构上的保证，不能只靠提示词。

### 四、工具选择漂移

工具一多（十几个），模型开始选错工具、或者用错参数格式。

**对策**：工具描述写清楚"什么时候用"而不只是"是什么"；工具数量控制在一屏内；必要时分组，先让模型选组再选工具。

## 一个必须设的东西：轮次上限

```text
最多 8 轮工具调用，超出就强制收尾
```

没有上限的循环等于给了一个不封顶的账单和一个可能永不结束的请求。上限到了怎么办？两个选择：

- **直接返回当前已有信息** + 一句"信息可能不完整"；
- **再调一次模型**，让它基于现有信息给结论（这次不允许调工具）。

第二种体验更好，代价是多一次调用。但要注意：**这个收尾调用不能算在正常路径的成本预算里**，因为它只在异常路径触发，容易被漏测。

## 常见误区

### 误区：轮次越多，Agent 越聪明

**你以为**：给更多轮次它就能想得更透。
**其实**：轮次多主要是给了它绕圈的空间。真实项目里限制轮次往往同时提升了准确率和成本。
**怎么验证**：把上限从 15 降到 6 各跑一批同样的任务，比较成功率与平均轮次——通常会看到绕圈的那些被截掉了。

### 误区：规划越详细越好

**你以为**：让模型先写 10 步计划能提高质量。
**其实**：计划越长，越可能基于尚未获得的信息瞎写，后面全都要改。
**怎么验证**：让模型在写计划时标注"这一步需要什么信息才能定"，你会看到大量步骤其实是不可预知的。

### 误区：Agent 失败了会报错

**你以为**：跑不通会有异常。
**其实**：它更可能带着错误前提给出一个自洽答案。错误伪装成成功是 Agent 的常态。
**怎么验证**：要求它输出结论时附上依据（用了哪几次工具结果），然后人工抽查依据是否支撑结论。

## 小结

ReAct 让模型边想边做，好处是事实在需要时才进入上下文，能在信息不全时修正方向。代价是可能绕圈、过早收手、编造观察。三条工程保证：Observation 由代码生成、工具失败如实反馈、轮次有硬上限。
