## 先把结论摆出来

Agent 的行为，**八成由系统提示词决定**，剩下两成由工具设计决定。模型本身没有那么大的差异。

同一个模型，系统提示词写好写坏，任务成功率能差一倍。而换一个更强的模型，往往只提升十几个百分点。

所以调 Agent 的第一步永远是**改提示词**，不是换模型。

## 系统提示词到底在管什么

它管四件事，缺一件就会出问题：

**一、角色与边界**
它是谁、负责什么、不负责什么。"你是代码审查助手，只评论正确性与可读性，不评论风格偏好"——后半句比前半句有用。

**二、工具使用规则**
什么时候用哪个工具、什么时候不该用。"查代码用 search_code，不要用 read_file 遍历目录"。

**三、输出格式**
要结构化还是自然语言、要多长、必须包含哪些字段。

**四、停止条件**
什么时候算做完。"信息足够给出结论时就停止检索，不要追求完美覆盖。"

第四条最常被漏掉，而它直接决定了成本。

## 写提示词的三条硬规则

### 规则一：写"不要什么"比写"要什么"更有效

"请给出准确的答案"几乎没有约束力。"答案里不得出现你没从工具结果中读到的类名"——这条能挡住一整类幻觉。

原因是**否定约束可检验**。模型输出后，你和它自己都能检查"有没有出现未读到的类名"，而"准不准确"没法当场判定。

### 规则二：规则要能落到具体动作

```text
反例：请谨慎处理用户数据
正例：涉及删除或修改的操作，先输出你打算改什么、等用户确认后再调用工具
```

前者是态度，后者是流程。模型只能执行流程。

### 规则三：矛盾的规则会互相抵消

```text
请尽可能详细地回答
回答要简洁，控制在三句话内
```

两条都在，模型会随机满足其中一条。写完通读一遍，把所有互相冲突的要求删掉——**宁可少一条，不要留矛盾**。

## 长提示词的结构

系统提示词写到几百行后，模型对中间部分的遵守率会下降（和长上下文是同一个问题）。有效的结构：

```text
# 角色            ← 两三句
# 工作流程        ← 编号步骤，最重要
# 工具使用        ← 每个工具一句边界
# 输出格式        ← 模板或 schema
# 禁止事项        ← 短句列表，放最后
```

三个要点：

- **流程放前面**，它是主体；
- **禁止事项放最后**，末尾位置模型记得最牢；
- **每节用小标题**，模型对结构化的内容遵守率更高。

## 提示词版本化

提示词是代码，要进版本控制、要有版本号、要和评测结果绑定。

不这么做的后果很具体：三个月后你发现效果变差了，想回滚到"上次好的时候"——但没人记得上次是哪一版。**没有版本号，就没有回滚能力。**

最小做法：提示词放文件里（不是硬编码在 Java 字符串里），提交时带 git 提交号，评测记录里记这个号。

## 少样本示例怎么用

给两三个输入输出示例，能显著提升格式遵循率。但要注意：

- **示例要覆盖边界**，不能全是顺利路径。三个示例里至少一个是"信息不足时该怎么答"；
- **示例会挤占上下文**，三四个就够，多了反而让模型只会照抄；
- **示例要和规则一致**。规则说"简洁"，示例却写了五百字，模型会跟示例走。

## 常见误区

### 误区：换更强的模型比改提示词划算

**你以为**：效果不好就换个更贵的模型。
**其实**：提示词的问题换模型解决不了。同一个提示词换模型通常只提升十几个百分点，而修好提示词能翻倍。
**怎么验证**：固定评测集，先只改提示词跑一遍，再只换模型跑一遍，对比提升幅度。

### 误区：提示词越长越周全

**你以为**：把所有情况都写进去，模型就不会错。
**其实**：超过几百行后，中间部分的遵守率明显下降，而且规则之间更容易互相冲突。
**怎么验证**：把同一套规则分别写成 50 行和 300 行，跑同一批任务比较遵守率。

### 误区：示例越多，格式越稳

**你以为**：多给几个例子总没坏处。
**其实**：示例占上下文，且会挤掉真正的任务信息；示例与规则不一致时，模型跟示例走。
**怎么验证**：把示例从 2 个加到 8 个，看格式正确率是否继续上升——通常会持平或下降。

## 小结

Agent 的行为八成由系统提示词决定。它要管角色、工具规则、输出格式、停止条件四件事。三条硬规则：写可检验的否定约束、规则落到具体动作、不留矛盾。长提示词按"流程在前、禁止事项在后"结构，并且必须进版本控制。
