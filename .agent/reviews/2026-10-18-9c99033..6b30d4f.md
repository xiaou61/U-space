### `backend/paideia-ai/src/main/java/io/github/xiaou61/ai/internal/memory/MemoryStore.java`

- **medium/bug L196** `from` 直接来自请求参数 `offset`（`AiMemoryController.list` 只约束了 `limit`，offset 无任何上限），这里有两个边界问题： 1. `offset=Integer.MAX_VALUE` 时 `from + pageSize` 溢出为负数，两个查询会下发 `LIMIT <负数>`，MySQL 直接报错，请求变成 500； 2. 更常见的是 `offset=5_000_000` 这类：每路都要把 `from+pageSize` 行取回内存再合并排序，等于让请求方决定这次查询拉取多少行（原来只按 pageSize 传输）。一个已登录用户就能把服务打满。 建议给 offset 一个显式上限（面板 200 条/页，上限几千足够），并在超限时直接返回空页，同时避免 `from + pageSize` 溢出。

### `backend/paideia-sandbox/src/main/java/io/github/xiaou61/sandbox/internal/run/DockerCodeRunner.java`

- **critical/bug L61** 这里会把整个沙箱功能直接打死：`docker run --cidfile` 要求目标文件**在使用前不存在**——CLI 在客户端侧会先 stat，发现文件已存在就直接报 `container ID file found, make sure the other container isn't running or delete ...` 并拒绝启动容器。`Files.createTempFile` 恰好把文件提前创建好了，于是每一次执行都会在启动阶段失败（exit 125，容器根本没起来），分帧写入与超时清理都无从生效。建议只保留一个唯一的、不存在的路径（创建后立刻删除，或用临时目录拼文件名），并在 finally 中连同目录一起清理。

- **medium/bug L119** 新增的容器清理只挂在 `!finished`（超时）分支上：上面 `waitFor` 抛 `InterruptedException`（应用 shutdown、线程池关闭、请求被取消）时只调用了 `process.destroyForcibly()`，容器仍归 daemon 管；而 `run()` 的 finally 紧接着会删掉 cidfile，等于把唯一的容器句柄销毁了，容器就此变成无法追踪的孤儿。建议 interrupt 分支同样调用 `removeContainer(command)`，或把 `destroyForcibly + removeContainer` 抽成一个清理方法，在两条异常路径上都执行。

- **medium/bug L200** 这段兜底有三处问题：1) 请求已经等满 `timeoutMs`（默认 10s）才走到这里，再同步阻塞最多 10s，等于超时请求可能被拖到 20s，同时也继续占着 `RunSlot` 名额；2) 不检查子进程退出码、也不消费 `redirectErrorStream` 的输出，无论 `docker rm` 成功与否都打印「已强删容器」，排障时会被日志误导；3) `waitFor` 超时后没有 `destroyForcibly()`，会遗留一个没人读取输出、也没被回收的 `docker` 子进程。建议缩短等待时间、检查退出码，并在超时/失败时销毁子进程。

- **medium/bug L89** 这段写 stdin 仍在两个输出读取线程（`streamReader`）启动之前同步执行，且完全不受 `properties.getTimeoutMs()` 约束。`maxCodeChars=20_000` + `maxStdinChars=4_000` 按 UTF-8 编码后可达约 70KB，超过 64KB 的管道缓冲：只要 docker CLI 此刻还没开始消费 stdin（容器尚未 start、daemon 卡住、CLI 自己阻塞在写 stderr 上），`stdin.write` 就会长期阻塞；而此时 stderr 也没人排空，CLI 同样卡住，形成互等。结果 `process.waitFor(timeoutMs)` 根本执行不到，请求会永久挂起并持续占用 `RunSlot` 名额（超时机制在这里被绕过）。建议先把 `outReader` / `errReader` 启动起来，再把 stdin 的写入放到独立线程（或在同一个超时预算内可中断地执行），超时统一走 kill 分支。

- **low/maintainability L187** 从命令行列表里按字符串反查 `--cidfile` 再 `Path.of` 比较脆弱，且 `Path.of` 抛出的 `InvalidPathException` 是 RuntimeException，不会被下面的 `catch (IOException)` 捕获——一旦命中就会让「清理失败也不抛」的承诺失效，把已确定的超时结果变成 500。`run()` 里本来就有 `Path cidFile`，直接把它作为参数传给 `execute` / `removeContainer` 更稳妥，也省掉这段反解逻辑。
