# AI 观测面板优化需求

## 本项状态与本轮变化

- **2026-10-23 起草**。用户原话：「langfuse 你给我调研一下这个是一个什么东西呢」→ 对比后追加：「那你可以参考他的 新开一个 work 就是优化我们的这个检测相关的，你仔细想想都可以新增一些什么东西呢」。
- 本项是 **WORK-022（AI 调用追踪与运营统计）的续作**，不是重做。WORK-022 已上线并通过验收。
- 本项**尚未实施**。四件工件中只有本文件与 `research.md` 存在，等待签署。

## 已确认事实

证据与逐文件核对在 [research.md](research.md)，此处只留结论。已确认的十一条缺口，按能不能回答真问题分四组：

**趋势与维度缺失**：概览只返回一个窗口内的聚合标量，没有按时间分桶的序列，也**没有任何筛选参数**（明细页有四个，概览一个都没有）。`cache_read_tokens` 在采集但从未显示。

**观测系统自身会骗人**：`RunWriteQueue` 有丢弃与写失败两个计数器，但只打日志、没有接口返回，队列满静默丢数据时面板看起来完全正常；采样只丢成功轮次、失败全留，一旦 `sampling` < 1 成功率会被系统性低估；`ai_runs.credits` 的注释两处都写着"与积分流水做日级对账"，**全仓没有对账代码**。

**质量信号为零**：`ai_messages` 无评分列，学习者端无点赞/点踩。所有统计只能回答"快不快、贵不贵"，回答不了"好不好"。

**既有债**：`parent_seq` 列、mapper、`SpanView` 全都有，但 `SpanSpec` 构造器没有 parent 参数，该列**恒为 NULL**；明细页无法按 `traceId` 定位。

## 用户决定

- **2026-10-23**：参考 Langfuse 优化我们自己的观测，**不引入 Langfuse 或 OpenTelemetry SDK**，继续自建。
- 其余范围决定待签署时确认（见「待确认问题」）。

## 实现选择

- **图表不引依赖**：用内联 SVG（一个 `TrendChart`，约 80 行），只需要单序列折线与堆叠柱两种形状。仓库当前零图表库，与"不新增依赖"的习惯一致。超过五种图表形状再引库。
- **反馈独立建表**而不是给 `ai_messages` 加列：一条回答可能被改判，独立表天然是流水。
- **对账只在接口层算**，不建汇总表：每天数百到数千轮，按天 `GROUP BY` 足够。

## 目标

- 看出趋势与拐点，而不是只看一个窗口的静态数字。
- 概览与明细用同一套筛选维度。
- **观测系统自己的失真必须可见**：丢弃、写失败、采样偏置、账实不符，任何一件发生，其余数字都失去意义。
- 给一条最便宜的质量信号入口（点赞/点踩），让"好不好"第一次有数据。
- 让已经声明但没落地的层级（`parent_seq`）真正可用。

## 非目标

- 不接入 Langfuse / OpenTelemetry SDK / Phoenix / Jaeger（沿用 WORK-022 裁决）。
- **不做数据集与批量评测**。升级触发条件：出现"改提示词前必须验回归"的真实需求，或提示词版本数超过 3 个。
- **不把提示词搬到数据库**做外置与灰度。升级触发条件：需要不发版就调提示词。
- **不做 AI 侧实时告警**。已有 Prometheus 邮件告警覆盖基础设施。升级触发条件：日调用量稳定超过 500 轮（现在两个账号，失败率突增没有统计意义，只会是噪声）。
- 不做瀑布图动画、会话聚合页、多租户切分、日汇总表与分区（触发条件：`ai_runs` 超 500 万行）。
- 不改计费规则与积分余额语义。

## 用户与工作流程

**每天第一眼**：概览最上方是 7 天成功率与耗时趋势 → 看到昨天掉了 → 用顶部场景下拉切到"对话"→ 趋势重算 → 点最差的那个点，直接下钻到那一小时的明细。

**发现数据不可信**：概览顶部出现黄色提示「采集队列近 1 小时丢弃 37 条，以下统计不完整」→ 进「采集健康」看丢弃曲线与最近一次成功写入时刻。

**回答"好不好"**：概览看到"差评 12 条"→ 点进去是差评列表 → 点任意一条展开该轮的完整请求与响应。

**对账**：进「积分对账」→ 看按天的"记录合计 vs 流水净扣"→ 昨天差 3 分 → 点开看差异最大的几轮。

**学习者提反馈**：回答下方点赞/点踩；点踩后选一个原因（答非所问/太啰嗦/内容有错/其它），选完即提交，不打断对话。

## 功能需求

### A 组：趋势与维度（只读，不改表）

- REQ-001：概览返回**按时间分桶的序列**：调用量、成功/失败/超时数、耗时 p50/p95、首字 p50、输入/输出/缓存命中 token、实扣积分。跨度 ≤ 48 小时用 1 小时桶，否则用 1 天桶；边界按服务器时区对齐；**空桶补零而不是缺段**（缺段会让折线在无调用时段静默断开，看起来像数据丢失）。
- REQ-002：概览接受与明细页**同一套筛选参数**（`kind` / `status` / `model` / `userId`），卡片、排行与序列都按筛选后的集合计算。
- REQ-003：概览返回缓存命中 token 与「缓存节省比例」= 缓存命中 ÷（缓存命中 + 输入），与输入/输出并列显示。
- REQ-004：概览返回**名义成本与实扣成本**两个数：名义成本按当前价目表折 token，实扣取 `ai_runs.credits`。两者差值代表缓存命中与价目表变更带来的偏差，必须同时给出，否则"扣分对不上"会被误判成计费 bug。

### B 组：观测系统自身的可信度（本项最核心）

- REQ-005：提供「采集健康」：队列深度、累计丢弃数、累计写失败数、最近一次成功写入时刻、当前采样率。**丢弃或写失败 > 0 时概览页顶部必须出现显式告警条**，说明"以下统计不完整"并给出丢了多少。宁可让面板承认自己漏了，不许它假装完整。
- REQ-006：概览的成功率旁标注当前采样率；采样率 < 1 时必须显示「成功率按采样后数据计算，失败轮次全量保留，因此该值系统性偏低」。
- REQ-007：提供**积分对账**视图：按天对比 `ai_runs.credits` 合计与 `ai_credit_ledger` 的净扣（按各 kind 合计），返回记录合计、流水合计与差值；差值绝对值超过可配置阈值的日期标为异常，可下钻到当天差值最大的轮次。
- REQ-008：提供**耗时构成**：一轮的 `duration_ms` 拆成排队、LLM、工具、其它四段（由 `queue_ms` 与各 span 耗时推出），详情页以横向堆叠条显示。不新增采集。

### C 组：质量信号（回答"好不好"）

- REQ-009：学习者可对助手回答提交赞/踩；踩时从固定枚举选原因（`off_topic` / `too_verbose` / `incorrect` / `other`），**不允许自由文本**（避免把用户输入变成需要审核的内容）。
- REQ-010：反馈与轮次关联：提交时带该轮 `trace_id`，落一条流水（用户、会话、消息、轮次、评价、原因、时间）。同一用户对同一轮的重复提交**覆盖**而非追加（与 WORK-013 重复抑制口径一致）。
- REQ-011：管理端「反馈」列表：按时间窗、场景、评价、原因筛选分页；每条可展开该轮的完整请求与响应（复用现有详情接口）。概览增加好评数/差评数/差评率，并接入 REQ-001 的序列。
- REQ-012：反馈表纳入注销级联，由既有手写表清单与其断言用例覆盖。

### D 组：定位与层级

- REQ-013：明细页支持按 `traceId` 前缀搜索，用于"日志里拿到 id 后直接定位"。
- REQ-014：`parent_seq` 真正落地：采集端口支持在同一步骤内开子步骤，详情页按层级缩进。本期只把"工具内部的检索/子调用"表达成子步骤，**不要求**改造七条路径的埋点结构。

## 质量要求

- 新增统计接口只读，仅 `hasRole("ADMIN")` 可访问。
- 概览与明细筛选语义一致：同一组合下，概览调用量必须等于明细列表 `total`。
- 响应里不出现提示词、回答正文或工具参数原文——**除反馈列表下钻**，那走既有详情接口。
- 采集端新增能力（子步骤）保持"调用方线程零 IO"与"失败只打日志"。
- 新逻辑（分桶、耗时分解、对账差值、缓存节省比例）各留纯函数测试；**分桶边界、空桶补零、阈值为零、差值为负**必须有断言。

## 验收标准

- AC-001：7 天窗口的概览返回 7 个日桶，每桶调用量相加等于同窗口 `ai_runs` 实际行数。
- AC-002：两个有调用的小时之间夹一个无调用的小时，该小时桶存在且各项为 0（**不跳段**）。
- AC-003：同一筛选组合（如 `kind=chat&status=failed`）下，概览调用量等于明细列表 `total`。
- AC-004：cache_read_tokens 非零时缓存节省比例与手算一致；全为零时返回 0 而非 NaN 或 null。
- AC-005：价目表变更前后各取一次名义成本与实扣成本，两个数字都可读出，不等时界面同时显示。
- AC-006：把队列容量改成 1 并灌入超额流量，采集健康返回丢弃数 > 0，概览页出现告警条（e2e 断言文案）。
- AC-007：采样率设为 0.5 后，概览返回 0.5，页面显示"系统性偏低"说明。
- AC-008：造一天"记录合计比流水净扣多 5 分"，对账视图标为异常、差值为 5，可下钻当天差值最大的轮次。
- AC-009：一轮里排队 100ms、两次 LLM 各 500ms、工具 800ms，四段之和等于 `duration_ms`（容差 ±50ms）。
- AC-010：提交"踩 + 内容有错"后 `ai_feedback` 新增 1 行且 `trace_id` 正确；同用户对同轮再提交"赞"，该行被覆盖、总行数仍为 1。
- AC-011：反馈列表按 `rating=down` 只返回差评；展开任意一条能看到该轮完整请求与响应。
- AC-012：注销后该用户 `ai_feedback` 行数为 0、他人不变；`AccountDeletionCascadeIntegrationTest` 清单包含该表。
- AC-013：明细页按 `traceId` 前缀能定位到唯一一轮；不存在的 id 返回空列表而非 500。
- AC-014：带子步骤的一轮按层级缩进显示，`parent_seq` 非空且父步骤在同一轮内存在。
- AC-015：关闭采集开关后，概览与反馈接口仍正常返回（空或历史数据），不报错。

## 假设

- 量级仍是每天数百到数千轮，按天 `GROUP BY` 做对账一次请求内可完成。
- 服务器时区 +08:00 是分桶与"按天"的自然口径（与速递的"今天"一致）。
- 反馈是低频动作，不需要限流（若被刷再按用户维度加，属后续）。
