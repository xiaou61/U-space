# 提案 · MySQL 实训沙箱与题库

## 摘要

在现有沙箱上加第三种语言 `sql`，把 MySQL 课从"只能读和答选择题"变成"能真的写并立刻知道对不对"；同时为题目定了一套**可被自动检验的质量规则**——每道题必须同时满足"换一种正确写法也能过"和"典型错误写法一定被拒"，否则这道题不算合格。

一句话取舍：**这一项的重点是题目可信度，不是 SQL 特性覆盖度。**

## 执行模型：四条路，选隔离最好的那条

| | A. 每次起一个一次性容器（推荐） | B. 常驻 MySQL，按会话分 schema | C. 嵌入式 SQLite | D. 复用宿主 MySQL，每次建临时库 |
| --- | --- | --- | --- | --- |
| **是不是真 MySQL** | 是 | 是 | **不是** | 是 |
| **每次是否干净** | 是，容器销毁即消失 | 否，要自己重置（删库、清连接、恢复数据） | 是 | 否 |
| **冷启动** | 有成本（实测见下） | 无 | 无 | 无 |
| **隔离强度** | 与现有 Java/Python 同级（无网络、只读根、丢弃 capability、资源硬上限） | 弱：多用户共用一个进程，一条 `KILL` 或全局变量就能影响别人 | 中 | **最差：用户 SQL 直接打到生产库实例** |
| **用户能随意建表** | 可以，销毁即清 | 需要额外防越权（别的 schema、`information_schema`） | 可以 | **绝不能** |
| **对宿主的风险** | 独立进程 + 容器边界 | 一个进程被拖垮全部用户 | 低 | 高 |
| **实现量** | 复用 WORK-015 全套 | 中 | 小 | 小 |

**选 A。** 决定性理由有两条：

1. **C 在语义上就不成立**：课程卖的是 MySQL 特有的行为（`DECIMAL` 与 `DOUBLE` 精度差、`EXPLAIN` 输出的 `type`/`key`、`REPEATABLE READ` 快照读、`AUTO_INCREMENT` 空洞）。SQLite 的动态类型让「数据类型怎么选」那一课直接失效，隔离级别根本不存在，`EXPLAIN` 是另一套输出。课程说 MySQL、执行却不是 MySQL，比不能执行更糟。
2. **B 与 D 都破坏「每次干净」这条纪律**，而这条纪律恰好是判题可信度的前提：如果上一题建的表还在，下一题的题面与结果就都不可解释了；D 更严重——用户 SQL 打到共享实例上。

A 的代价是冷启动。这一项的实测数据与本机验证见下节。

## 为什么不用「预初始化 datadir」以外的省时办法

`mysqld --initialize` 每次都要跑一遍（实测数秒），而一次练习的 SQL 本身往往只要几十毫秒——不优化启动，用户 95% 的时间都花在等数据库起来。

两条可省的路：

- **预初始化镜像**：镜像里带一份已初始化的 datadir，运行时直接 `--datadir` 指过去。本项采用这条。
- **常驻 + 快照恢复**：更快，但要自己做状态管理，且与 A 的隔离结论冲突（回到 B）。不采用。

预初始化镜像是**一次性的构建成本**换每次运行的固定收益，且不牺牲隔离。

## 题目设计：把「质量」变成可执行断言

用户明确说这一项最重要的是题目设计。所以这里不是"多写几道题"，而是**给题目定一套能被脚本否掉的规则**。

### 每道可执行题必须带的四样东西

| 字段 | 作用 | 缺了会怎样 |
| --- | --- | --- |
| `reference` | 参考解（一段查询） | 期望结果无从复现，只能手写——手写必然与数据集脱节 |
| `alternatives` | 至少一个**写法不同**的正确解 | 无法证明判题不误杀等价写法（`JOIN` 与子查询会被判错却没人发现） |
| `antiPattern` | 至少一个**看起来对但错**的写法 | 无法证明这题能区分真假；一道谁都对的题等于没出 |
| `datasets` | 至少 2 个（1 公开 + 1 隐藏） | 只在一个数据集上对，`SELECT 487.50` 也能拿满分 |

期望结果**不落盘**：由 `reference` 在数据集上真跑得出。这样数据集改了，期望自动跟着变，不存在"改了数据忘了改答案"。

### 门禁怎么判这道题合不合格

```text
对每道题：
  对每个 dataset：
    跑 reference      → 记结果 R
    跑每个 alternative → 必须与 R 相等  （否则：判题太严，误杀正确写法）
    跑每个 antiPattern → 至少在一个 dataset 上与 R 不等（否则：这题没区分度）
  检查 goal / trap 非空，trap 能在本课「常见误区」里找到
```

三条断言各自挡一类真实的坏题：

- **alternative 失败** = 判题口径太窄（比如要求列顺序严格），会把正确写法判错。这类错误最伤用户，因为学习者会以为自己写错了。
- **antiPattern 全过** = 这题没有区分度，任何写法都能过，题目在骗人。
- **只有一个 dataset** = 可以硬编码答案，隐藏集就是为这个存在。

### 五种题型，三种不需要执行

| 题型 | 考什么 | 执行 | 举例 |
| --- | --- | --- | --- |
| `sql-write` | 从需求写出查询 | 是 | 「列出每笔订单的客户与总额，按总额降序」 |
| `sql-fix` | 找出并修正一处坑 | 是 | 「这段想统计有订单的用户，但没下单的消失了，改对」 |
| `sql-predict` | 读懂语句会返回什么 | 否 | 「这个 `LEFT JOIN + WHERE` 会返回几行」 |
| `sql-diagnose` | 看 `EXPLAIN` 判断原因 | 否 | 「这条为什么走了全表扫」 |
| `sql-blank` | 关键字与语法 | 否 | 复用现有 `fill` |

后三种存在的意义不只是"省资源"：**沙箱关掉时课程必须还能走完**（现有 `run` 题型的降级口径就是这样）。所以每课强制至少一道不需执行的题。

### 题目与课程的单向绑定

每题的 `trap` 必须能在该课「常见误区」里找到对应条目。这条约束的作用是**防止出超纲题**：课里没讲的东西不许拿来考。反过来也保证了课程内容与题目是同一份知识，不是两拨人各写各的。

## 判题口径：归一化到什么程度

这是最容易出错的地方。SQL 结果集比对不是一个 `===` 能解决的，但归一化过头又会让「排序」这一课无法出题。

| 项 | 默认 | 可覆盖 | 为什么 |
| --- | --- | --- | --- |
| 列名 | **参与比对**（按列名对齐） | 题目可声明按位置 | 列名错了说明理解错了；但 `AS` 别名风格不同不该判错 |
| 列顺序 | 忽略 | 可声明严格 | 大多数查询列顺序无所谓 |
| 行顺序 | **忽略** | **排序题必须声明严格** | 一刀切会让整课「排序分页」失效 |
| `NULL` | 显式标记，与 `''` 区分 | — | 混同会让 null 题失去意义 |
| `DECIMAL` | 按数值比较（`92.5 == 92.50`） | — | 否则同一份数据换个写法就判错 |
| 日期时间 | 归一后比较 | — | 时区与格式差异不该影响判题 |
| 浮点 | **禁止出现在判题列** | — | `DOUBLE` 误差会让比较不稳定 |

最后一条是硬约束不是建议：题目数据一律用 `DECIMAL`，出现 `FLOAT`/`DOUBLE` 列时门禁直接报错。

## 判题逻辑的单一真相

前端要用这套口径判题，`scripts/verify_course.py` 也要用它验题库——两边各写一遍必然漂移（历史上"两份规则各写一遍必然漂移"在本仓库已经吃过亏，见 `verify_course.py` 顶部的注释）。

做法：一份语料 `tests/sql-judge/corpus.json`（输入结果集 + 口径 + 期望判定），前端 TS 与门禁 Python **各自实现、同一份语料对照**。任一侧改动都要跑一次对照测试。

## 交付拆分

按"能被单独验证"切成四段：

1. **执行能力**（不改内容）：能跑一段 SQL、拿到结构化结果、五种失败状态可区分。
2. **判题口径**：归一化实现 + 两侧语料对照通过。
3. **题库与门禁**：门禁能对一道题判"合格/不合格"，并真有题被判不合格（反向验证）。
4. **关卡接入与自由练习**：课程 12 关接题、练习页可用、进度与审计口径正确。

第 1、2 段不依赖题库，可以并行；第 3 段是关键路径（题目质量），第 4 段最后。

## 风险与缓解措施

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 冷启动太慢，用户每次等好几秒 | 练习体验崩坏，题目没人做 | 预初始化镜像；实测后若仍 >4 秒，改为「同一题的多个数据集共用一个实例」 |
| SQL 容器吃掉服务器内存，挤掉 Firecrawl | 线上其它功能故障 | `maxConcurrency` 保守起步 + 实测内存峰值后定值；数据库层同时限流 |
| 判题归一化写错，把正确写法判错 | 用户以为自己错，比报错更伤 | `alternatives` 断言 + 语料对照测试；每条归一化规则都要有正反例 |
| 用户写出拖垮实例的查询 | 单次运行占满 CPU 数分钟 | **实测过：不限时的九表笛卡尔积跑了 259 秒**。三道上限（库层 `max_execution_time`、容器墙钟硬杀、行数上限）缺一不可 |
| 题目泄露：隐藏数据集被看到 | 硬编码答案就能过 | 隐藏数据集**不随题面下发**，只在服务端执行时使用 |
| 门禁只能证明"这题不难被绕过"，证不了"这题考得对" | 题目可能考了个没价值的东西 | `goal`/`trap` 与课程误区绑定；由人评审题面质量，脚本只挡机械错误 |

最后一条要说清：**自动断言能挡住"坏题"，挡不住"平庸的题"**。所以题目质量仍需要一次人工评审，脚本不替这一步。
