# 提案 · 决策模型接入（Laya）

## 摘要

引入 Laya（Apache-2.0 的 System 1 决策模型，非自回归、不生成文字）作为**一个**过滤器：判断抓来的面经帖是不是技术内容。部署在 `codenest-online` 本机，`laya-serve` 只监听回环，主应用通过 HTTP 调用。

**它只做一件事。** 其余它宣传的用途（邮件分流、内容审核、提示注入防护、客服路由）一个都不接——我们系统里没有那些流程，硬接等于为不存在的问题付 1.7G 内存。

## 为什么值得接

抓来的面经里混着大量非技术帖。实测同一天 14 条里只有 5 条真在讲题，其余是「终于找到实习了！」「如何提高工程能力」这类。不过滤就会为每条都花一次 AI 解析——那是有成本的，而判定本身零成本（本地推理）。

**关键判断是"为什么不直接用规则"**：规则能分掉大部分，但边界地带（提到一两个技术词、其实在讲求职）规则判不准。Laya 在这个位置上的实测表现是：技术面经 P(tech) 0.957~0.980，纯求职帖落到 career 一侧。所以它是**规则的补充，不是替代**。

## 三种做法，为什么选本机自托管

| 做法 | 优点 | 缺点 |
| --- | --- | --- |
| **本机 laya-serve（选定）** | 零调用成本、数据不出机器、延迟 150~260ms | 吃 1.7G 内存；要自己维护进程与权重 |
| HF Inference API | 不用自己跑 | 免费额度限流、数据出境、延迟不可控 |
| 不用它，纯规则 | 零成本零维护 | 边界地带判不准，等于放弃这条能力 |

选本机的决定因素是**成本结构**：判定的量级是每天几十条，用托管 API 会引入一个不必要的依赖与计费面；而自托管在这台 16G 机器上放得下。

## 一期做到哪

**做**：`ContentClassifier` 端口 + Laya 实现 + `TechEssayFilter`（规则优先）+ 配置开关 + systemd 单元 + 测试。

**不做**：
- 容器化（现在是 venv + systemd，官方 compose 是另一条路，暂不重复建设）
- 温度拟合（不做它就不该调低阈值）
- 微调
- 接入遥测
- 内容审核 / 提示注入防护 / 场景路由

## 风险

| 风险 | 严重度 | 缓解 |
| --- | --- | --- |
| **模型判错，把真内容过滤掉** | 高 | 规则在前（命中 0 种技术词直接否、命中 ≥5 种直接是），只在边界问模型；模型判"非技术"时仍按规则结论走 |
| 4 核机器上与沙箱/AI 调用抢 CPU | 中 | `LAYA_THREADS=2`（官方基准：超过物理核数反而慢）；`MemoryMax=3G` 防止拖垮同机服务 |
| 上游改了响应结构 | 中 | 真连测试 `LayaContentClassifierLiveTest` 会立刻红 |
| 服务挂了无人知 | 中 | 端口失败返回 empty 并**降级到规则**，功能不中断；`Restart=on-failure` |
| 冷启动 16~22 秒期间请求超时 | 低 | 那是"判不了"的语义，降级到规则；不给它加长超时 |
| 概率不可信（ECE 0.219） | 中 | 阈值 0.7 只用来区分"很确定"与"在猜"，不做准确率解读；注释写死在代码里 |

## 与项目规则的冲突检查

- 不新增 Maven 依赖（用 JDK 自带 `HttpClient`）。
- 不走 `GuardedHttpTransport`：那是给**用户可填**的 AI 上游地址用的 SSRF 防线；这里的地址来自部署配置、只能是回环，且显式禁止重定向。**这是两条不同的信任边界，不复用是对的。**
- 不引入向量库、不改数据库、不加迁移。
