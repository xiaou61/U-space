# 提案 · AI 记忆的自动提取与控制面

## 一句话

**在"回答完成之后、每 6 轮一次"跑一次小的提炼调用**：把它当成"一次收益明确、代价可预算、失败与欠费都可跳过"的后台动作；写入前先检索相似旧记忆、由模型判 `ADD/UPDATE/DELETE/SKIP` 来保证**同一件事只留一条**；控制面照 ChatGPT 做三层（总开关 + 两个独立轴 + 清空并关闭），让用户永远能说"我不要"。

## 备选方案

### A. 每轮都自动提取（框架的 `STATIC_CONTROL` 语义）

- **做法**：每次回答结束后异步提取一次，模型自己决定记什么。
- **好处**：最"自动"，用户从不操心；这也正是 `AgentScope Java` 里 `LongTermMemoryMode.STATIC_CONTROL` 的标准模式。
- **代价**：**每轮多一次调用**。用用户自己的数字（输入 909 / 输出 518）算：一轮从 ≈0.6 分涨到 ≈1.1 分，**+80%**。更麻烦的是**失败面**：每轮都写就每轮都可能写错，而记忆会被**后面每一轮**读进提示词——一条错记忆会持续污染，且用户往往发现不了。
- **结论**：**不选**。用户已裁决走 B（"固定某些时候、一轮总结一次之类的"）。

### B. 每 N 轮（默认 6）批量提取一次 —— **已选**

- **做法**：按会话内的消息游标判断"距上次提取是否已新增 N 轮"；提取时喂**增量对话** + 检索出的**相似旧记忆**，一次性决定这一批的写入。
- **好处**：成本摊薄到 **约 +13%**（每 6 轮一次小调用）；素材更足（6 轮里能看出"他反复卡在哪"），提炼质量比单轮好；**写入次数少 = 出错面小 = 用户更容易看见和纠正**。
- **代价**：口碑上没那么"实时"——一句重要的话可能要等到第 6 轮才进记忆；最后不足 N 轮的一截若用户此后再也不回来就不提取。

### C. 助手提议候选，用户点一下才写（半自动）

- **做法**：每 N 轮跑一次提取，把结果作为**候选**显示在回答下方（"要记住这条吗？"），用户点击才落库。
- **好处**：写入质量最高（人做最后一道过滤）；与 WORK-006 的「记住这条」机制天然同源。
- **代价**：用户不点就等于没记忆——"千人千面"的个性化永远攒不起来；而且候选区是新的界面负担。
- **结论**：**不选为默认**，但**作为"实测提炼质量差"时的退路**写进「什么情况下该重审」。

### D. 保持纯手动（现状）

- 代价：记忆永远只有"用户主动点的那几条"；用户已经问出"这不应该是自动的吗"，说明现状**用不起来**。**不选**。

## 决策

1. **写**：走 **B**，N 默认 6，**异步**（回答之后），**增量**（会话内消息游标）。
2. **不膨胀**：写入时**去重合并**（`ADD/UPDATE/DELETE/SKIP`），相似旧记忆用**现有 SQL 全文检索**找——**不引向量、不引外部服务**（用户裁决 4；也避免推翻"暂不做向量化"这条既有裁决）。
3. **控制面**：照 **ChatGPT 三层**——总开关 + 「使用已保存的记忆」/「把当前对话的历史消息作为参考」两个独立轴 + 「清空并关闭」。**关掉不删历史**（照 OpenAI 的语义），清空是另一个动作。
4. **边界收紧**（本项唯一改写既有裁决的地方，需用户确认）：自动提取**只允许写"记忆"两路**；用户内容（笔记、自评、分享）仍然只能由用户动作产生。理由是「自主只建议不动作」的原意是"不许替用户改**用户的东西**"，而记忆是**助手对自己的印象**。
5. **失败与欠费一律跳过**：提取是一次真实的 AI 调用（花用户的积分、进流水），但它**永远不能影响本轮回答**。

## 代价（已告知并接受）

| 代价 | 数字 / 说明 |
| --- | --- |
| 积分 | 每 6 轮一次小调用，摊到每轮 **+约 13%**（详细算式见需求「调研结论」最后两行）。**必须写在界面上**，不能偷偷扣 |
| 可能的错记 | 记忆会被后面每一轮读到。因此**每条都记来源与理由**、面板可逐条删、可一键清空并关闭——用"可撤销"换"自动" |
| 一个后台任务 | 提取要在回答之后异步跑：多一条错误处理路径（失败/欠费/结构非法都要放弃整次），且要防"同一会话并发触发两次"（用游标 + 单飞） |
| 一点不确定性 | "他反复卡在哪"这类判断交给了模型，会出现"我觉得该记但它没记"。**用可撤销与可追溯承担**，不用更复杂的算法承担 |
