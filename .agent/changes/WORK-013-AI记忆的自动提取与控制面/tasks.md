# 任务 · AI 记忆的自动提取与控制面

**排序原则**：**先把"用户能说不"做掉**（设置 + 三个开关 + 短路），此时系统行为与现在一致（默认全开）、但用户已经能关；**再把"写"这条路按可测的顺序铺开**（纯逻辑 → 提示词 → 触发单飞 → 异步与记账），每一步都能单独验证；**最后是界面与文档**。这样即使哪一步卡住，用户拿到的东西也是完整可用的（"能关"永远比"会自动写"更该先到）。

## 验收要点（对应 AC）

- **AC-001**（T-06）自动提取真的发生且是提炼。
- **AC-002/003**（T-09）幂等与纠错可追溯。
- **AC-004**（T-07、T-08）失败与欠费都不影响本轮。
- **AC-005/006/007**（T-03、T-10）三个开关各自成立、"只关不删"与"清空并关闭"分得开。
- **AC-008**（T-01、T-10）来源可见。
- **AC-009**（T-07）不占用户时间。
- **AC-010**（T-08）账对得上。

## 风险与默认处置

- **提炼质量**：若实测"该记的没记/记了一堆废话" → 先调提示词与 `kind` 枚举，再把 N 调大（素材更足、成本更低）；仍不行就退到提案里的**方案 C**（提议候选、用户点确认）——**那要回到需求重裁**（写入方从"服务端自动"变回"用户确认"）。
- **成本噪声**：提取会在流水里多出一类消耗，用户可能觉得"我没聊几次怎么花这么多"。默认处置：`kind` 分开记 + 面板显示最近一次整理消耗 + 设置区写明频率与花费。
- **并发**：同一会话多标签页同时提问 → 条件更新保证只有一个跑（T-06 要真有并发用例，不能只靠推理）。
- **提取调用的已知坑**：`max_tokens` 不足会让 flash **静默返回空内容**（WORK-005 踩过）→ "空"必须按**放弃整次**处理，不能当成"这次没什么可记的"。
- **口径**：本项不做向量、不引外部服务。实施中若发现"不去重就没法用"，**停下确认**，不许顺手引依赖。
