# AI 记忆的自动提取与控制面需求

## 本项状态与本轮变化

- **2026-10-16 登记并起草**。起因是用户在线上看过助手面板后问：「这个存住笔记和记住这条是什么意思呢？…记忆这个不应该是我们要用一些什么算法，自动总结的吗？然后用户可以设置有没有记忆…这样是不是更好一点呢？」
- 用户逐条裁决（原话见「用户决定」）：**①写 = 每 N 轮或会话结束批量提取一次；②可以写入时去重合并；③控制面照 ChatGPT 的三层；④不引外部记忆服务**。并明确「我们记忆目前不需要那么标准」——本项**不做**知识图谱、不做向量检索、不做重要度打分。
- 工件状态 `draft`：**签字之前不动代码**。
- 前置：`WORK-006` 已把记忆做成"两路 + 严格私有 + 可逐条删除"（已实施并部署，硬依赖满足）。**与本项相关但独立**的是 `WORK-010`（身份化，含"自评→结构化记忆"那条桥，未实施）。

## 已确认事实

**代码复核（2026-10-16，逐文件读过）**

| 项 | 事实 |
| --- | --- |
| 写入路径只有一条，而且是**手动的** | `POST /api/v1/ai/memories` 是**记忆唯一的写入口**（`AiMemoryController` 的注释里写明：模型那条路径**不存在**，这是"写操作必须用户确认"在接口层的落点，不是靠前端自觉） |
| **召回是自动的** | `ConversationService.memorySnippets(userId, keyword)` 每轮都调 `MemoryStore.recall`，关键词取**本轮用户输入**；召回结果标注两类来源（`[学习者事实]` / `[他说过]`）后拼进**系统侧**提示词（`ConversationPrompt.memory`）。**读路径是纯 SQL、零 LLM 调用** |
| 两路存的是同一形状 | `ai_memories_structured`（`kind` + `ref_id` + `content`，上限 512 字）与 `ai_memories_text`（`content`，上限 1024 字）。超长**直接报错，不静默截断** |
| 召回上限固定 8 条 | 结构化取最近 8、全文按关键词（中文退回 `LIKE`）取 8 → 进提示词的就这些。**上下文不会随记忆条数膨胀** |
| **没有去重** | `rememberText` 就是一条 `INSERT`：同一句话点两次「记住这条」= 两条记忆 |
| **没有任何总开关** | 面板只有"查看 + 逐条删除"；后端没有设置表、没有设置端点（本次全仓搜过） |
| **结构化那一路没有界面入口** | 「记住这条」写的是 `type=text`。结构化那路目前只有（未实施的）WORK-010 那条"自评→记忆"的桥能写——**所以现在的记忆天然是"他说过的话"的清一色列表** |
| 面板有 200 条显示上限 | `MemoryStore.list` 用 `LIST_LIMIT = 200`，无分页 |
| 提取/召回都是"助手对自己的印象"，不是用户内容 | 「存进笔记」落的是笔记系统（用户可编辑、可分享）；记忆是助手私有的一份印象。两者去处不同：**笔记助手不会自动读，记忆每轮都会带上** |

**调研结论（外部，2026-10-16 联网核实）**

| 来源 | 关键事实 |
| --- | --- |
| **AgentScope Java 官方文档**（我们已依赖的框架，D-09 唯一 AI 框架） | 它自带 `LongTermMemory` 接口（`record` 写 / `retrieve` 读）与 **`LongTermMemoryMode`：`STATIC_CONTROL`（推理前自动召回、回答后**异步**记录）/ `AGENT_CONTROL`（模型用工具自己决定）/ `BOTH`**，并有三个实现：Mem0、ReMe、阿里百炼。**"一轮一次、异步记录"就是它的标准模式**。⚠️ 但我们的 harness 是**自写循环**（WORK-006，只用了它的模型客户端与流式累加器），不是 `ReActAgent`，所以这套抽象接不上；且三个实现内部都依赖向量检索 |
| **mem0**（43k star，官方文档） | 写入 = ①查重（先找相似旧记忆）→ ②LLM 提取事实 → ③去重+嵌入 → ④实体抽取；**自动路径是"只增不改"，纠错靠显式 update/delete**；检索融合语义/关键词/实体/时间四路 |
| **Zep / Graphiti** | 时序知识图谱，事实带"有效期 + 记录时间"两条时间轴；**读路径不需要 LLM** |
| **Letta（MemGPT）** | 分层（常驻上下文的核心记忆 + 向量检索的归档记忆），**由模型自己用工具编辑记忆** |
| **ChatGPT**（OpenAI 帮助中心：Memory in ChatGPT / Memory FAQ） | 控制面最完整：**总开关 Memory** + **「引用已保存的记忆」「引用聊天历史」两个独立轴** + 记忆摘要页 + 一键「删除并关闭」。且明确：**关掉记忆不会删你的历史对话**；日后再打开，它可能从旧对话里重新生成记忆 |
| **deepseek-flash 官方价**（api-docs） | 输入未命中 高峰 2 元/百万、空闲 1 元；输出 高峰 8 元/百万、空闲 4 元；缓存命中 0.04 / 0.02 元 |
| 成本实测（用用户自己的真实数字） | 线上那一轮 = **输入 909 / 输出 518 tokens** → 高峰 **≈0.6 分钱/轮**。**若每轮都自动提取**：多一次小调用（输入 ~1.4k、输出 ~250）→ **+约 0.48 分/轮，即 +80%**；**按本项选的"每 6 轮一次"**：摊到每轮 **+约 13%** |

## 用户决定

| # | 问题 | 裁决 |
| --- | --- | --- |
| 1 | 记忆怎么写 | **每 N 轮或会话结束批量提取一次**（不做每轮自动、不做纯手动） |
| 2 | 怎么不膨胀 | **可以做写入时去重合并** |
| 3 | 控制面 | **照 ChatGPT 的三层**（总开关 + 两个独立轴 + 一键清空） |
| 4 | 要不要引入外部记忆服务 | **不需要**（原话："我们记忆目前不需要那么标准"，同步排除向量检索、知识图谱、重要度打分） |

## 目标

- 用户**不必手动点**，助手也能把"值得留着的"记住；但**每一条都看得见、能删、能一键关掉**。
- 同一件事**只留一条**（说不两次不会出现两条互相矛盾的记忆）。
- 记忆的写入**不占用户看到答案的时间**，且**花的是用户自己的积分**——因此必须能关、且写得清花在哪。
- 每一条记忆都能回答"**它为什么在这里**"（谁写的、什么时候、出自哪段对话）。

## 非目标

- **不做向量检索**（沿用既有裁决）：相似旧记忆用现有 SQL 全文检索找，中文退回 `LIKE`（`SearchQuery` 已有这套判定）。
- **不引外部记忆服务**（mem0 / ReMe / 百炼）：不为"去重"引进一整套基础设施与向量库。
- 不做知识图谱、双时间轴、重要度打分、记忆摘要压缩（ChatGPT 那种"把若干条合并成一条更抽象的"）——用户明确"不需要那么标准"。
- **不做"记忆分享"**（WORK-006 已裁：严格私有）。
- **记忆不按身份切**（WORK-010 已裁：记忆全属于用户一份）。本项不新增任何身份维度。
- **不做"自评 → 结构化记忆"那座桥**——那是 `WORK-010` 的剩余任务（见「关联工作项」的边界约定）。
- 不改助手面板形态（WORK-011）、不改 markdown 渲染（WORK-012）。

## 用户与工作流程

**读者**：学习者正常问助手 →（第 6 轮、且记忆总开关是开的）助手在回答之后**自己整理一次**：把这几轮里"值得留着的"挑出来、和已有的比对、合并或新增 → 用户下次问别的问题时，助手自然记得。用户想知道它记住了什么，就点开「记忆」页；不喜欢就逐条删、或者一键「清空并关闭」。

**三种状态要说清**（这块是用户最可能误解的地方，界面文案要跟上）：

| 用户看到的 | 实际含义 |
| --- | --- |
| 记忆开关关着 | **不召回、不自动提取**；手动点「记住这条」会被挡住并说明原因 |
| 记忆开着，但没点过「记住这条」 | 仍然可能有记忆——**自动整理写的**；每一条在面板里都标了来源 |
| 关掉记忆 | **不删已有的记忆**（照 ChatGPT 的语义）；要删要另外点「清空」 |

## 功能需求

- **REQ-001 批量提取**：每 **N 轮**（默认 6）触发一次，处理**上次提取之后的新增对话**（按会话内的消息游标，不是"全文重来"）。**不以"会话结束"为必须条件**：用户新开/切换会话不丢——剩余不到 N 轮的那一截会被**下一次提取**一起覆盖；若用户此后再也不回来，那几轮不提取（可接受，它们也是最不值钱的）。
- **REQ-002 提取的输入与输出**：输入 = 增量对话 + 由候选事实检索出的**相似旧记忆**；输出 = 0–k 条候选，每条含 `type`（structured / text）、`content`、可选 `kind` 与 `ref_id`、动作（**ADD / UPDATE / DELETE / SKIP**）与一句理由。**输出必须是可校验的结构化结果**（模型返回非法结构 → 整次提取放弃，不写半条）。
- **REQ-003 去重合并**：**同一件事只留一条**。判定顺序是"先检索相似、再让模型决定"，不是"模型自由发挥"；`UPDATE` 是**覆盖**（与 WORK-010 已裁的"重复抑制用覆盖、不追加"一致）；`DELETE` 只在模型判定"这条旧记忆已不成立"时使用，**并记下理由**。
- **REQ-004 两路写到哪**：关于学习者的**事实**（如"这个条目他还不懂""他的目标是秋招"）→ **结构化那路**（带 `kind`、尽量带 `ref_id`）；**他说过的话/偏好**（如"他喜欢先看例子"）→ **全文那路**。这条同时把"结构化那一路没有界面入口"这个缺口补上一半。
- **REQ-005 记账与余额不足即跳过**：提取**自己也是一次 AI 调用**，走同一套预扣/结算，进用户积分流水。**余额不足时静默跳过提取，绝不因此让本轮回答失败**。
- **REQ-006 不占用户的时间**：提取在**回答流结束之后异步**进行（复用 JDK 25 虚拟线程）。用户看到答案的时刻不受影响；提取失败只记日志，不向用户报错。
- **REQ-007 总开关**：关掉后 **①不召回 ②不自动提取 ③手动「记住这条」被挡住并给出明确原因**（不能静默写库——那是"看起来关了其实还在记"）。
- **REQ-008 两个独立轴**（照 ChatGPT）：**「使用已保存的记忆」**与**「把当前对话的历史消息作为参考」**各自独立开关。后者关掉 = 助手只回答当前这一句、不看前文。
- **REQ-009 清空与关闭分开**：「一键清空并关闭」（清空两路记忆 + 关掉总开关）与"只关不删"是**两个动作**，界面必须让用户分得清。
- **REQ-010 可追溯**：每条记忆记录 `source`（`manual` / `auto`）与（`auto` 时）`conversation_id`、`ref_message_id`、以及判定动作与理由。面板能显示"这条是自动整理的／出自哪段对话"。
- **REQ-011 面板补全**：两路来源可分辨、可按来源筛选、条目多时能翻页（当前 200 条硬上限）；「清空并关闭」入口放在这里。
- **REQ-012 透明**：设置区写明"自动整理会**消耗你的积分**，频率是每 6 轮"（数字随配置）。
- **REQ-013 设置的所有权范围**：设置与端点都是**本人**范围（请求体里没有 userId，传不了别人的）；沿用既有约定。
- **REQ-014 不改既有纪律**：严格私有、注销级联硬删（若新增表必须进 `AiUserDeletionListener` 的清单）、四路召回上限、超长报错不截断。

## 质量要求

- **三条可验收口径**（替代"记忆很聪明"这种不可验收的说法）：
  1. **幂等**：同一件事说两次 → 记忆条数**不增加**（第二次是 `UPDATE`/`SKIP`）；
  2. **不影响本轮**：提取失败或余额不足时，**本轮回答逐字节不变**、错误不进用户可见的报错位；
  3. **可对账**：自动提取产生的每一次调用都在积分流水里能对上（复用 WORK-009 的对账口径）。
- **提炼而非照抄**：写入的 `content` 必须是提炼后的一句话，不是把某轮回答整段塞进去——用"字符上限 + 结构化校验 + 语料断言"来保证，不靠感觉。
- **可维护**：提取提示词**单独一个版本号**（`assistant-chat-v1` 之外新开一个），将来"同一段对话为什么提炼得不一样"有据可依；判定动作的分支在纯函数里，有独立单测。
- **失败可放弃**：整次提取是**全有或全无**（不做"写了一半"）。

## 约束与依赖

- 依赖 `WORK-006`（已实施）：记忆两路、严格私有、逐条删除、召回口径都由它建立。
- 复用 `WORK-009` 的积分预扣/结算与流水（提取的消耗走同一条路）。
- **本项改写 WORK-006 的一条边界，必须由用户确认**：原裁决「自主只建议不动作」的意思是"**不许替用户改数据**"。本项的自动提取让模型**间接**产生了写入。边界收紧为：**自动提取只允许写"记忆"这两路**（助手对自己的印象），**笔记、自评、笔记分享等"用户内容"仍然只能由用户动作产生**；且自动提取**全在总开关之下**、**一键可清空**。这条不确认就不实施。
- 不做向量：相似记忆检索复用 `SearchQuery` + `ai_memories_text` 的全文索引（中文单字在 ngram 索引上召回为零 → 退回 `LIKE`，这是知识库那边踩过一次的坑）。
- 提取会花 token：默认 N=6，实测增量约 **+13%**（对比"每轮自动"的 +80%）。

## 关联工作项

- `depends_on: WORK-006`——记忆的形状与私有性由它建立；本项只改"谁在什么时候写"。
- `related_to: WORK-009`——提取的消耗要进积分账本。
- `related_to: WORK-010`——**边界约定**：WORK-010 的"自评 → 结构化记忆"那座桥属于它；本项只做"对话里的自动提取"。两者都会写结构化那一路，**谁后实施谁负责对齐**（覆盖式更新的语义一致，因此不冲突）。
- `related_to: WORK-011 / WORK-012`——面板与渲染由它们建立，本项只在面板里加设置与来源显示。
- **不属于本项**：向量检索、知识图谱、外部记忆服务、记忆摘要压缩、记忆分享、身份维度。

## 验收标准

- **AC-001 自动提取真的发生**：同一会话聊够 N 轮后，记忆里出现由这几轮提炼出的条目（集成测试：造 N 轮 → 断言新增条目且内容是**提炼**，不是原文整段）。
- **AC-002 幂等（不膨胀的核心）**：把同一件事在两次提取里说出 → **条数不增**，且内容被`UPDATE` 成最新说法。
- **AC-003 纠错可追溯**：一条已不成立的旧记忆被 `DELETE`/`UPDATE` 后，面板能看出它变了、以及为什么（理由与动作可见）。
- **AC-004 失败与欠费都不影响本轮**：余额不足 / 提取调用失败 → **本轮回答一致**、无用户可见报错、提取被跳过（集成测试两条）。
- **AC-005 总开关真的关掉**：关掉后 ①下一轮的提示词里没有任何记忆片段（可断言）②不再发生自动提取 ③点「记住这条」给出明确原因且**落库为 0 行**。
- **AC-006 两个轴独立**：「引用当前对话历史」关掉后，提示词里只有本轮这一句（可断言）。
- **AC-007 清空并关闭**：两个动作分开——"只关不删"时记忆仍在；"清空并关闭"后两路表为空、开关为关、面板显示空态。
- **AC-008 来源可见**：每条记忆能看出是手动还是自动、自动的出自哪个会话。
- **AC-009 不占用户时间**：提取调用发生在**回答完成之后**（用事件顺序断言，不用墙钟时间）。
- **AC-010 账对得上**：自动提取的消耗在积分流水里有记录，且与总消耗一致。

## 实现选择

以下几条是实现层的取舍，连同「待确认问题」一起，签的时候可以推翻（推翻要改这一节，不是改设计）：

| # | 选择 | 为什么这么定 |
| --- | --- | --- |
| 1 | **N = 6**（每 6 轮提取一次，模块常量） | 摊到每轮 +约 13%（对比"每轮自动"的 +80%）；6 轮的素材足够看出"他反复卡在哪"，比单轮提炼准 |
| 2 | **不做"会话结束"补触发** | 剩余不足 N 轮的一截会被**下一次提取**覆盖；而"服务端识别会话结束"在无状态 JWT 下没有可靠信号（加端点让客户端上报＝可漏可伪造，idle 计时器＝多一套状态） |
| 3 | **判重时把该用户已有记忆全部喂给模型**（上限 40 条），不做相似检索 | 我们不做向量，而 SQL 关键词检索拿一段对话当关键词效果很差；一个用户只有几十条记忆，全喂更准也更简单。上限 40 是 `ponytail:` 天花板（更早的记忆不参与判重），升级路径写在设计里 |
| 4 | **提取用 JSON 输出、不用工具调用** | 已知限制：工具调用与结构化输出不能在同一次调用里并用；且后台动作不需要工具 |
| 5 | **一个端点做"清空并关闭"** | 分成两个调用会出现"清空了但没关上"的半状态 |
| 6 | **三个开关默认全开** | 默认全开 = 不改变存量行为（现在既召回又带历史）；记忆在默认关闭时价值为零 |
| 7 | **提取失败不重试**（游标已推进，那段不重跑） | 重试要引入重试状态机与"失败要不要计费"的一串问题，而漏一条记忆的代价远小于这套复杂度。代价在设计的「已知缺口」里登记 |

## 假设

- 一个学习者的记忆增长很慢（一天几句话），所以"膨胀"的**上下文侧**早已被 top-8 召回挡住；本项要解决的其实是**重复与不可控**，不是容量。
- 模型能从 6 轮对话里提炼出值得留的事实；若实测提炼质量差（废话多、照抄原文），先调提示词与上限，必要时把 N 调大（成本更低、素材更足）。
- 结构化那路的 `kind` 先用一小撮固定值（如 `weak_topic` / `goal` / `preference`），不开放自由文本种类。

## 待确认问题

**没有阻断批准的问题**。两条属实现选择，已按推荐值写入设计，签的时候可以推翻：

1. **N 取多少**：建议 **6**（增量约 +13%）。取值越小编译越大、素材越少；越大越省、但"卡住很久的那句话"要等更久才被记住。
2. **"会话结束"要不要作为补触发**：建议**不做**。理由是上面 REQ-001 那条——剩余不足 N 轮的一截会被下一次提取覆盖，而"服务端识别会话结束"在无状态 JWT + 无服务端会话的架构下没有可靠信号，做它要么加端点让客户端上报（可漏可伪造），要么靠 idle 计时器（多一套状态）。**如果你要"关掉面板/新开对话就立刻整理一次"，说一声，我把它加进来（成本是多一个端点 + 客户端可能不报）。**

## 什么情况下该重审

- 若实测"自动提取明显拖慢了回答"或"提炼质量差到用户开始删" → 回到本项，先把 N 调大或默认关闭自动提取（改为只提议候选、用户点确认）。
- 若为了去重不得不引入向量检索（即 SQL 全文检索找相似记忆效果不可接受）→ 那是推翻既有裁决（暂不做向量），必须回到需求重裁，不能顺手加。
- 若要做"记忆摘要压缩"（把 N 条并成 1 条）或"跨身份的记忆" → 回到本项重开（前者是本项明确的非目标，后者与 WORK-010 的裁决冲突）。
