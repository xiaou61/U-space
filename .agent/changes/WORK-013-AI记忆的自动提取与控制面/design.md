# 设计 · AI 记忆的自动提取与控制面

## 1. 一张图看清"谁在什么时候写"

```
用户提问 ──▶ 召回（读记忆，纯 SQL，受「使用已保存的记忆」控制）
              └─▶ 拼提示词（受「当前对话历史」控制）──▶ 流式回答 ──▶ 结算 ──▶ 用户看到答案
                                                                    │
                                      回答之后（异步、事务外）      ▼
                              本会话新增轮次 ≥ N？ ──否──▶ 什么都不做
                                       │是
                                       ▼
                    抢游标（条件 UPDATE 成功才算抢到，保证单飞）
                                       ▼
              预扣积分 ──失败/余额不足──▶ 静默跳过（记日志）
                                       ▼
        一次调用：提炼指令 + 增量对话 + 已有记忆（≤40 条）
                                       ▼
     模型输出候选 JSON（ADD/UPDATE/DELETE/SKIP + 理由）──非法/空──▶ 放弃整次
                                       ▼
                         按动作写两路记忆（一个事务）+ 记来源与理由
                                       ▼
                      结算（真实消耗进流水，kind = 记忆整理）
```

## 2. 数据模型

### 2.1 两路记忆表各加四列（`ai_memories_structured` / `ai_memories_text`）

| 列 | 用途 | 依据 |
| --- | --- | --- |
| `source` | `manual` / `auto` | 面板要能说"这条是自动整理的"（REQ-010、AC-008） |
| `conversation_id` | auto 时的出处 | 回答"它为什么在这里"，出错时能回看那几轮（REQ-010） |
| `ref_message_id` | auto 时的出处消息 | 同上；也是将来"这条记忆对应哪一段"的锚点 |
| `reason` | auto 时模型给的判定理由 | 覆盖/删除时尤其重要（AC-003） |

默认值 `source='manual'`（存量行因此自然归为手动写入 ✓ 不需要数据回填）。

### 2.2 新增 `ai_user_settings`（每用户一行）

| 列 | 含义 |
| --- | --- |
| `user_id` | 主键（**一人一行**，不按身份切——WORK-010 已裁） |
| `memory_enabled` | 总开关，默认 **开** |
| `reference_saved_memories` | 「使用已保存的记忆」，默认 **开** |
| `reference_chat_history` | 「把当前对话的历史消息作为参考」，默认 **开** |
| `updated_at` | |

**默认全开**：一是现状就是"既召回又带历史"（不改变存量行为），二是记忆的价值在默认关闭时等于零。

### 2.3 游标：`ai_conversations` 加一列

`last_memory_extract_message_id`（可空，指向该会话里已提取到的消息 id）。**放在会话上而不是用户上**：增量天然是"某个会话里从此处往后"的一段，放用户上会让多个会话互相抢游标。

> 迁移编号**不写死**：实施时以当时仓库里实际最大号 +1 为准（WORK-004 就撞上过并发会话占用编号）。

## 3. 提取的调用形状（一次调用，不做第二次）

**顺序照 mem0：先看已有，再决定**——但把它的"向量检索相似旧记忆"换成**直接把该用户已有记忆全给模型看**：

- 我们**没有向量检索**（既有裁决），而 SQL 关键词检索拿一段对话当关键词效果很差（中文单字在 ngram 上召回为零，要退回 `LIKE` 全表扫）。
- 现实是**一个用户的记忆只有几十条**（一天几句话）。**全喂进去让模型自己比对，比检索更准，而且更简单、更便宜**。
- **上限 40 条**（模块常量）。`ponytail:` 超过就只喂最近 40 条 —— 天花板是"很久以前的记忆不参与判重，可能出现跨时间重复"；升级路径是"按 `kind`/`ref_id` 分批"或将来真做向量检索。到了那个规模再改。

**调用参数**（三条都有依据）：

| 项 | 值 | 依据 |
| --- | --- | --- |
| 流式 | **否** | 后台动作，没有逐步显示的需求 |
| 输出格式 | **JSON 对象**（`response_format: json_object`，DeepSeek 官方支持） | 需要可校验的候选数组；**不用工具调用**——已知限制：工具调用与结构化输出不能在同一次调用里并用 |
| `max_tokens` | 给足（≥2048） | 已知坑：思考 token 吃满 `max_tokens` 会**静默返回空内容**。因此"空内容/非法 JSON"必须按**放弃整次**处理，不能当成"没有可记的" |
| 提示词 | 独立版本号 `memory-extract-v1` | 将来"同一段对话为什么提炼得不一样"要有据可依 |
| 前缀缓存 | 固定指令放最前 | 缓存命中价 0.04 元/百万，比未命中便宜 50 倍 |

## 4. 判定与写入（REQ-003 / REQ-004）

模型对每条候选给一个动作，**四种动作的语义写死在提示词里、由纯函数校验**：

| 动作 | 含义 | 落库行为 |
| --- | --- | --- |
| `ADD` | 新事实 | 插入一条 |
| `UPDATE` | 已有记忆要改（说错了/更完整了） | **覆盖**同一条的 `content`（并刷新 `reason`）——与 WORK-010 已裁的"重复抑制用覆盖、不追加"一致 |
| `DELETE` | 已有记忆**已不成立** | 删除该条（理由入库前先写进日志，便于回查） |
| `SKIP` | 不值得记 / 与已有重复 | 不动库 |

**写到哪一路**（REQ-004）：关于学习者的**事实**→ 结构化路（带 `kind`，`kind` 限一小撮固定值：`weak_topic` / `goal` / `preference`；`ref_id` 能定位到条目就带）；**他说过的话/偏好**→ 全文路。**`kind` 不接受自由文本**（写死枚举，超出的候选按全文路处理）。

**整次提取全有或全无**：一个事务里完成全部写入；任何一条校验不过 → 整批放弃（不写半条）。

## 5. 触发与单飞（REQ-001 / REQ-006 / REQ-009 的顺序）

1. **计数**：本轮回答成功后，算该会话里 `id > last_memory_extract_message_id` 的**助手消息条数** ≥ N（默认 6，模块常量）；
2. **抢锁**：`UPDATE ai_conversations SET last_memory_extract_message_id = ? WHERE id = ? AND last_memory_extract_message_id <=> ?`
   —— **条件更新成功才算抢到**（与 WORK-009 扣余额同一手法）。并发两个请求只会有一个跑，天然单飞，不需要分布式锁。
3. **异步**：抢到之后**在回答事务之外**、用虚拟线程（JDK 25）执行；失败只记日志，绝不影响用户那一轮。
4. 跑完之后游标已在第 2 步推进——**若提取失败，那一段就不重跑了**。这是有意的取舍：重跑要引入重试状态机与"失败要不要计费"的一串问题，而记忆漏一条的代价远小于这套复杂度。**代价写进已知缺口。**

## 6. 控制面的落点（REQ-007 / REQ-008 / REQ-009）

| 开关 | 短路点 | 关掉后的可断言行为 |
| --- | --- | --- |
| `memory_enabled` | ①`ConversationService` 不调 `memorySnippets` ②提取触发前先查（关着直接返回） ③`AiMemoryController.create` 直接拒绝（错误码 `MEMORY_DISABLED`，**带明确文案**，不是静默 0 行） | 提示词里没有任何记忆片段；不产生自动提取；点「记住这条」落库 0 行且有明确提示（AC-005） |
| `reference_saved_memories` | 只挡 `memorySnippets`（自动提取**不受它影响**——提取是"写"不是"用"） | 不再引用已保存的记忆，但仍会整理新记忆 |
| `reference_chat_history` | 只挡 `ConversationPrompt.history(...)` 的拼装 | 提示词里只有本轮这一句（AC-006） |

**"清空并关闭"是一个端点做两件事**（`DELETE /api/v1/ai/memories` → 清空两路 + `memory_enabled=false`），前端再加二次确认：**分成两个调用会出现"清空了但没关上"的半状态**。

设置端点：`GET/PUT /api/v1/ai/settings`（本人范围，请求体里没有 `userId`；沿用既有约定）。**PUT 只接受布尔**，不做部分更新的花活。

## 7. 记账（REQ-005 / AC-010）

- 提取是**一次真实 AI 调用** → 走 `CreditService` 的预扣/结算，**进用户流水**；
- **预扣失败 → 直接跳过**（不 reserve 就不调用），本轮回答早已完成、不受影响；
- 流水 `kind` 新增一个值（如 `MEMORY_EXTRACT`），与对话消耗**分得开**——否则用户看到"我明明没聊几次怎么花了这么多"没法对账；
- 面板显示"最近一次自动整理：X tokens"（数据取该用户最近一条该 kind 的流水）。这属于 REQ-012 的透明性要求，成本是一个查询。

## 8. 界面（REQ-011 / REQ-012）

`memory-panel.tsx` 扩成三块，**顺序按用户会问的问题排**：

1. **开关区**（最上面）：总开关 + 两个轴；（说明文字必须写"自动整理**会消耗你的积分**，每 6 轮一次；关掉不会删除已有记忆"）
2. **记忆列表**：每条显示 `content` + **来源标签**（手动 / 自动）+ 自动时"出自某段对话"与**理由**；可按来源筛选；超过 200 条要能翻页（现在是硬上限）
3. **危险区**（最下面）：**「清空全部记忆并关闭」**（二次确认；文案必须与"只关不删"分开写清）

## 9. 测试口径

| 层 | 覆盖什么 |
| --- | --- |
| 单测（纯函数） | 候选 JSON 的校验与降级（非法/空 → 放弃）；`ADD/UPDATE/DELETE/SKIP` 四种动作的分支；`kind` 枚举外落到全文路 |
| 集成测试 | 造 N 轮 → 触发一次提取（AC-001）；两次说同一件事 → 条数不增（AC-002）；余额不足 → 本轮回答一致且无用户可见报错（AC-004）；总开关关掉 → 提示词无记忆片段 + 落库 0 行（AC-005）；历史轴关掉 → 只有本轮（AC-006）；清空并关闭 → 两路为空 + 开关为关（AC-007）；注销 → 级联删掉设置行（REQ-014） |
| 前端单测 | 开关与文案、来源标签、"只关不删"与"清空并关闭"的区分 |
| e2e | 面板上真的能开能关能清空（学习者端一条；不依赖真实上游——提取是后台动作，e2e 只验设置面） |

**时序类断言用事件顺序，不用墙钟时间**（提取发生在回答完成之后 → 断言调用顺序/游标推进，不断言"快了多少毫秒"）。

## 10. 已知缺口（登记，不当成没有）

1. **最后不足 N 轮不提取**：用户此后再也不回来时，那几轮永不进入记忆（REQ-001 已说明取舍）。
2. **提取失败不重试**：游标已推进，那一段不再重跑。
3. **判重只看最近 40 条**：更早的记忆不参与判重，可能出现跨时间重复。
4. **提炼质量依赖模型**：可能出现"该记的没记/记了废话"。退路是方案 C（提议候选、用户点确认），见需求「什么情况下该重审」。
5. **不做的**：向量检索、外部记忆服务、知识图谱、记忆摘要压缩、记忆分享、按身份切分。
