# Agent 运行时、记忆与个人笔记提案

## 摘要

把 WORK-005 建立的"一次调用"助手，扩展成一个**有会话、有记忆、有工具、能把结果写进学习者自己的笔记**的常驻助手；并把原 WORK-007 的"个人笔记与只读分享"并入同一项交付。关键取舍是：**只用 AgentScope 的模型与工具编排面，会话、记忆、笔记三类数据全部自建存储**——因为它们是用户私有数据，其生命周期（严格私有、注销级联硬删）不能交给一个 GA 仅三个月的框架托管。

## 推荐方案

**机制**：在 WORK-005 的 `paideia-ai` 薄端口之后扩展出三类能力——多轮会话、记忆召回、工具编排——**框架类型不出端口**。会话、记忆、笔记的持久化全部由本平台自己的表承担；AgentScope 只负责模型调用与工具循环。

**所有权划分**：

- 会话与记忆是 **AI 运行时数据**，留在 `paideia-ai`（谁的对话、谁的记忆，随用户走）。
- 笔记与分享是 **业务数据**，新建 `paideia-note` 模块，对外只暴露 API 包。理由：笔记的可见性（私有／已分享）与所有者规则，跟 `paideia-knowledge`（内容是管理员写的、所有人读同一份）**恰好相反**，混在一起会让两端权限规则互相打架。
- 助手写笔记时，`paideia-ai` 通过 `paideia-note` 的 **API 接口**写，不碰其内部实现（沿用 Modulith 边界）。

**三条硬约束的落地方式**：

1. **工具与结构化输出不可并用**（DeepSeek）：助手对知识库的检索用**工具**；凡是需要结构化取回的地方（记忆写入参数、笔记元数据）走**第二次调用**——先由模型给出结构化结果，再单独执行工具轮。这条必须在设计里写成明确的分流规则，不能靠"碰巧不撞"。
2. **思考 token 吃 `max_tokens`**：`max_tokens` 按"思考 + 正文"给足以留出余量；流式下对"只有思考、正文为空"的响应要有可见提示而不是空白。
3. **无定时任务**：会话有效期与分享到期**一律走读取时校验**（过期即视为不存在），不引入调度器。

**分享的形态**：新增一个免鉴权读端点，与 `GET /files/{uuid}` 同构——**id 不可枚举即凭据**；分享产物只含笔记正文与其归属条目的可公开部分，**不含**记忆、标记与作者身份。

## 范围

**包含**：多轮对话（任意页入口、条目为可选上下文）、流式与思考分离展示、会话持久化与上限/有效期、结构化 + 全文两路记忆、记忆的查看与逐条删除、只读工具、写本人私有数据（登录确认）、助手写本人笔记、基于记忆的建议（不自动动作）、笔记 CRUD、只读分享（免登录、可撤回、固定有效期、不可枚举）、举报与管理员下架、注销级联硬删、纯 BYOK 与用量返还、运行时限流。

**不包含**：依赖学习状态的自主行为、向量与语义检索、记忆的编辑与分享、宽限期删除与恢复、平台兜底 Key 与成本记账、可观测性栈、多实例部署、定时任务、练习/作答/判分/掌握度/学习路径。

## 备选方案

**把所有东西塞进 `paideia-ai`（含笔记与分享）。** 最强的一面是模块数不增加、边界最少。未选：笔记与分享是**业务数据**，让 AI 模块承担"内容所有权"会让"模型调用"这个职责被稀释；且将来若要出现"非 AI 来源的笔记"，所有权会立刻错位。

**笔记并入 `paideia-knowledge`。** 最强的一面是"笔记挂在条目上"，与条目同模块，取数据不用跨模块。未选：`paideia-knowledge` 的所有权模型是"管理员写、所有人读同一份"，而笔记是"用户写、只有自己能看（除非主动分享）"——两套可见性规则放在同一个模块里，权限校验会变成最容易出错的地方。WORK-004 已经因为"文件端点免鉴权"付出过一次边界成本，不重复。

**不做流式、不做工具，只做"带记忆的多轮对话"。** 最强的一面是工作量与风险都显著下降，且天然避开 DeepSeek 的"工具 × 结构化输出"冲突。未选：用户在 2026-10-12 明确裁决**四件一起做**，并已知悉代价（见需求第 1 条）。若将来要收缩，这条是首选退路。

**直接采用 AgentScope 自带的 memory / session / tool 抽象。** 最强的一面是少写大量代码，框架已经把多轮与记忆做完了。未选：① D-09 要求业务代码不直接依赖框架类型；② 会话与记忆是本项的**用户私有数据**，其"严格私有""注销级联硬删""不依赖定时任务"三条硬要求，若交给框架的表结构，等于把数据所有权与生命周期绑死在一个一年内仍有近九百个未关 issue 的 2.0.0 框架上。**代价**：自建存储意味着这些代码要自己写、自己测——本项因此比"直接用框架"重。

## 仓库影响

**后端**

- 新增模块 `backend/paideia-note/`（笔记、分享、举报与其 API 包）。
- 扩展 `backend/paideia-ai/`（会话、消息、记忆两路存储、工具集合、流式、建议；端口形状随之扩展）。
- `backend/paideia-app/`：Flyway 迁移（**编号不写死**，实施时取下一个可用号）、`/api/v1/**` 的显式安全规则、新模块注册。
- 新的**免鉴权**读端点（分享），需与 `GET /files/{uuid}` 一样放进静态放行列表并限定为 `GET`。

**前端**

- 扩展 `frontend/packages/assistant/`：从"精简卡片"扩为"对话 + 流式 + 思考折叠 + 工具过程 + 建议"。
- 学习者端新增：笔记页（本人笔记的读写）、分享入口与分享结果的公开页、设置内的记忆查看与逐条删除。
- 管理端新增：举报处理与下架。
- `frontend/packages/knowledge/` 或新包：笔记与分享的客户端。

**部署**：形态不变（单实例、8081、无 Docker、无定时任务）。新增环境变量沿用 WORK-005 的注入方式；**不新增任何凭据入库**。

## 交付拆分

按纵向切片推进，每片完成后可独立演示：

1. **多轮 + 流式**：会话存储、消息表、SSE 流、思考折叠、任意页入口。
2. **记忆（结构化 + 全文）**：两路写入与召回、设置内的查看与逐条删除。
3. **只读工具**：检索条目／分类／本人标记；越权防护。
4. **写路径**：写本人私有数据（点击确认）+ 写本人笔记（含工具与结构化输出的分流）。
5. **笔记 CRUD**：创建、编辑、持久化、挂靠条目；AI 内容落进笔记。
6. **只读分享**：免鉴权读端点、不可枚举、撤回、固定有效期、读取时判失效。
7. **举报与下架**：举报入口 + 管理员处理。
8. **注销级联硬删 + 用量与限流收口**。

## 风险与缓解措施

| 风险 | 缓解 |
| --- | --- |
| **本项规模很大**（8 片、含新增模块、两处协议扩展） | 纵向切片，每片独立验收；若中途要收缩，退路是"去掉工具与流式"（备选方案第三条） |
| **DeepSeek"工具与结构化输出不可并用"** | 设计里固定分流规则：工具轮与结构化轮分开调用；AC-016 专门验证 |
| **免鉴权分享端点成为新的泄漏面** | 与 `GET /files/{uuid}` 同纪律：id 不可枚举、只允许 `GET`、产物不含学习痕迹；AC-011 验证 |
| **无定时任务下的"到期"** | 一律读取时校验（过期即视为不存在）；不引入调度器，也不假装有清理 |
| **自建会话/记忆存储的代码量与正确性** | 三态越权检查（匿名/他人/本人）对每一类数据都有自动化用例 |
| **AgentScope 2.0.0 年轻** | 只用模型与工具编排面，不用其会话/记忆抽象；薄端口保证可替换 |
| **成本随轮次放大** | 纯 BYOK + 用量返还 + 按用户限流；不做成本记账（已裁） |
| **与 WORK-005 的端口/前端包被实质扩展** | 实施前复核 WORK-005 的稳定规格；扩展处回填 `design.md` 并在验证报告里覆盖精简原路径不回归 |

## 待决定事项

均不阻断本项实现，属实现选择，将在设计阶段定值：

1. 会话条数上限与会话有效期的具体数值。
2. 多轮对话的限流数值（沿用 WORK-005 的按用户固定窗口做法）。
3. 分享的固定有效期数值与撤回的交互方式。
4. "思考过程不入库"与"举报不单独通知作者"两条实现选择，用户可在批准前改为相反做法（需求「实现选择」已列）。

## 门槛合并说明

用户在 2026-10-12 明确要求**把需求、方案、设计、任务四件一次起草、再由用户按序审批**，而不是每道门槛单独停下来确认。因此 `design.md` 与 `tasks.md` 在本提案签署之前就已起草，四件共享同一批审阅与签署。

这条决定改变了门槛的**节奏**，没有改变门槛的**内容**：四件工件仍然各自需要用户确认，只是确认发生在一次审阅里。严格顺序的检查工具会把"上游未签署而下游已存在"报告为结构性错误——这是合并节奏的必然中间态，不是工件有问题；四件按 `requirements → proposal → design → tasks` 顺序签署后即消失（WORK-002 已有同样先例）。
