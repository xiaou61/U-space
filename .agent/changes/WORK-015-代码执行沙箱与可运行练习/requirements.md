| 计费与配额 | WORK-009 已有积分预扣/结算与流水，可复用来限制运行次数 |
| 身份 | 注册开放；只做登录后可用；无多租户 |

### 调研事实（待本项 proposal 补齐）

v1 只记录已知的三条硬约束，不在需求阶段选型：

1. **隔离级别决定上限**：进程级隔离（`timeout` + seccomp + 只读挂载）挡不住内核提权；gVisor / Firecracker / 独立 VM 才是强隔离。选哪个由 proposal 给备选与代价。
2. **必须无网络**：任何允许出网的执行都可能被当作代理、扫描或挖矿。
3. **镜像与依赖是供应链面**：语言运行时镜像必须钉 digest，不能让用户自带镜像。

## 目标

- 学习者在练习块里能**写/改代码并运行**，看到真实输出（stdout/stderr/退出码），从而验证"我真的懂了"。
- 运行是**安全、可预算、可审计**的：无网络、有 CPU/内存/时间上限、有人均频率上限、每次运行可追溯到用户与条目。
- 失败是**可解释**的：超时、内存超限、编译错误、运行时错误分别给出不同提示。
- 不破坏现有部署：执行器与应用隔离，跑满时不影响 API。

## 非目标

- **不做多语言全家桶**：v1 只支持 1–2 种语言（建议 Java 与 Python），其余语言不承诺。
- **不做交互式终端**（stdin 逐行交互、REPL）：v1 是"提交一次、跑完返回"。
- **不做用户自定义依赖安装**（`pip install` / `npm install`）：依赖随镜像预置。
- **不做持久化工作区**：每次运行是干净容器，不留文件。
- **不做代码分享/公开运行历史**。
- **不做分布式调度**：v1 单机；跑量上来再谈队列与多机。

## 用户与工作流程

学习者在 `code-challenge` 的「运行」题型里编辑代码 → 点「运行」→ 看到"排队中/运行中"→ 返回输出与判定 → 可以改完再跑。额度用完时明确告知"本次未执行、未扣分"。

## 功能需求

- **REQ-001 运行题型**：`code-challenge` 新增 `kind: "run"`，含初始代码、语言、公开用例与隐藏用例；运行后逐用例显示通过/失败。
- **REQ-002 执行契约**：输入代码 + 语言 + 用例，输出每个用例的 `stdout`、`stderr`、退出码、耗时、是否超时/超内存；**代码与输出设长度上限**。
- **REQ-003 隔离**：每次运行在**一次性隔离环境**中执行；无网络；根文件系统只读（可写临时目录有配额）；无宿主设备与凭据；进程数有上限。
- **REQ-004 资源上限**：单次 CPU 时间、墙钟时间、内存、输出字节、临时磁盘各有硬上限；超出即终止并返回明确原因。
- **REQ-005 并发与配额**：全局并发上限（不拖垮 API）+ 每人每分钟次数上限 + 走 WORK-009 的积分记账（或等价配额）；**未实际执行不扣费**。
- **REQ-006 审计**：每次运行记录用户、条目、语言、结果、耗时、资源用量与是否被拒；**不记录完整源码**（避免变成用户内容存储），只保留哈希与长度。
- **REQ-007 失败分类**：编译失败、运行时错误、超时、超内存、输出超限、被拒绝（配额/限流）分别有不同提示与不同计费语义。
- **REQ-008 判定**：用例比较 stdout（可配置 trim 与行尾归一化）；隐藏用例只在结果里显示通过与否，不回显期望值。
- **REQ-009 与 WORK-014 的关系**：运行题型复用同一套进度与得分记录；没有执行器时该题型在 UI 上不可用并说明原因，**不影响其他题型**。
- **REQ-010 部署独立**：执行器不监听公网；应用只通过本机/内网通道调用；执行器崩溃不影响 API，重启后自恢复。
- **REQ-011 可关闭**：配置项可整体关闭执行能力，关闭后 UI 自动隐藏「运行」。

## 质量要求

- **不可逃逸到宿主**：隔离方案必须有书面威胁模型与"能挡住什么、挡不住什么"的说明；不把"能跑"当成"安全"。
- **不可被当成代理或矿机**：无网络、CPU 时间硬上限、并发上限。
- **可预算**：单次运行的资源上限与人均频率写进配置，启动时校验。
- **可观测**：运行成功/失败/拒绝各一条计数；无源码内容入日志。

## 验收标准

- **AC-001 能跑**：Java 与 Python 各一个样例程序返回正确 stdout 与退出码。
- **AC-002 无网络**：程序内尝试连接外网失败，且不产生任何出网请求。
- **AC-003 超时终止**：死循环在墙钟上限内被终止，返回"超时"，API 不受影响。
- **AC-004 内存上限**：超量分配被终止，返回"超出内存"，宿主内存无明显上涨。
- **AC-005 并发保护**：并发打满时新请求被拒绝或排队，API 响应时间不劣化。
- **AC-006 配额与计费**：超过每人频率上限被拒且不计费；正常运行有记账记录且与实际执行一致。
- **AC-007 审计可用**：能从记录里查到"谁、何时、哪个条目、什么结果、用了多少资源"，且**查不到源码正文**。
- **AC-008 隔离证明**：尝试读取宿主文件、访问 Docker socket、提权的行为全部失败（以测试用例形式留档）。
- **AC-009 关闭开关**：关闭后 UI 不显示「运行」，接口拒绝执行，其他题型照常。
- **AC-010 不影响既有部署**：跑满执行器时，学习者端与管理端既有 e2e 仍通过。

## 实现选择

需求阶段不选型。proposal 必须给出至少三档隔离方案（容器 + 加固 / gVisor / 微虚拟机）的代价与风险对比，并明确"挡不住什么"。

## 假设

- 学习者运行的是练习用的小程序，不是生产代码；单次运行秒级到十秒级。
- 一期只需要 1–2 种语言；语言越多，镜像与依赖维护成本越高。

## 待确认问题

**没有阻断批准的问题。** 语言、额度、隔离档位与用例口径已按上表决定；隔离档位的具体选型在 `proposal.md` 里给三档对比与推荐，签字时确认。

如果下面任何一条与你的预期不同，说一声再改：

- **运行不等于判题**：服务端只执行代码并回传 stdout/stderr/退出码，判定仍在客户端（用例写在正文 JSON 里，本来就对读者可见）。这样服务端不存任何题目，也不需要"题库"表。
- **不提供 stdin 交互**：每次运行是一次性提交，`stdin` 可预置一段文本。
