# 个人知识图谱与掌握度提案

## 摘要

把"知识的最小单位"从**条目**改成**概念**：新建一张概念表记录知识点本身，一张多对多表把条目挂到概念上，一张边表记录概念之间的先后与关联。学习者的掌握度由三路信号（练习分数、自评、浏览）在一个纯函数里算出，不落库。前端用 2D 力导向图呈现，坐标持久化；3D 作为按需加载的切换视角。

这条链路一次接通四件已有但互不相连的数据：`learning_progress`（分数）、`knowledge_self_assessments`（自评）、新增的浏览记录、`knowledge_entry_relations`（内容结构）。

## 推荐方案

### 为什么概念要独立成表

现在的知识库只有条目。同一件事在三门课里出现时，系统看到的是三个孤立条目。举个具体的例子：Python 的「字典」、Java 的「HashMap」、MySQL 的「索引结构」，对学习者来说都属于"哈希表"这个知识点，但它们之间没有任何连接。条目级的图会把这三者画成三个点，无法回答"我在哈希表这件事上到底行不行"。

概念成表之后，这条关系是一行数据；掌握度也自然按概念聚合，而不是按"你读了哪些文章"聚合。这也正是调研里几个公开知识图谱项目的共同最小结构（概念 + 概念间关系 + 内容关联）。

### 为什么边要单独建表，而不从前置条目推导

`knowledge_entry_relations` 已经有 `prerequisite`。很自然会想：A 条目前置于 B 条目，那 A 的所有概念都应该指向 B 的所有概念。问题是这会产生 N×M 条边——两个各挂 5 个概念的条目会画出 25 条线，其中绝大多数没有语义（"HTTP 报文格式"并不前置"MySQL 索引结构"）。图会立刻变成一团毛线。

概念间的边必须是人明确写下的，这是本方案唯一不能自动化的部分，也是它能成立的原因。

### 为什么掌握度不落库

掌握度是派生值：它随时可能因为新的一次小测、一次到期复习、一次自评改变。落库就要处理"什么时候重算、算错了怎么修、并发写怎么合并"。而它的输入只有几十到几百行数据，按用户一次查询算完是毫秒级。

不落库还有一个直接好处：**算法可替换**。现在用加权加衰减，将来数据够了想换 BKT，只改一个纯函数，数据库不动、接口不动、前端不动。

### 为什么浏览要单独记

"看过"是唯一**事后补不回来**的数据。分数有 `learning_progress`、自评有专表、代码运行有 `code_runs`，只有"你上周读过哪三篇"没有任何记录。

不把它塞进 `learning_progress` 是因为两者语义不同：`learning_progress` 的一行代表"我开始学这一课了"，会被课程进度统计当成已开始；而浏览只是路过。混在一起之后，"我什么都没做"和"我看了一眼"就分不开了。

### 为什么 2D 主入口、3D 按需

3D 力导向图有一个绕不过去的性质：布局每次加载都会重新收敛。人对空间位置的记忆（"Redis 那片在右下角"）在每次打开都变的情况下无法建立，图就退化成一张好看的星云。所以无论 2D 还是 3D，**坐标持久化**是前提。

在这个前提下，2D 的优势是方位感稳定、节点点击区域大、文字标签可读、小屏可用；3D 的优势是遮挡关系更清晰、观感更强。用户已决定 2D 为主入口，本提案照此执行，3D 作为切换。

## 范围

**做**：
- 概念、条目↔概念、概念↔概念三张表与迁移；
- 浏览记录表与记录端点；
- 掌握度纯函数与四档划分；
- 学习者图谱端点（节点 + 边 + 每节点载体条目摘要 + 统计）；
- `/learn/graph` 页面：2D 默认、3D 切换、坐标持久化、重建布局、点选面板、空状态；
- 管理端概念维护页（概念 CRUD、关联条目、概念间关系）；
- 注销级联新增浏览表；
- 助手工具新增薄弱/待复习概念的查询。

**不做**（与需求非目标一致，此处只点名最容易"顺手做掉"的三项）：
- 不做自动概念抽取——脏概念会毁掉整张图的可信度；
- 不做 BKT——样本量不足，参考实现是 Python；
- 不做概念级题目——题目仍挂在条目上。

## 备选方案

### 备选一：条目即节点（不建概念表）

**它最强的理由**：零新表、零标注成本，`learning_progress` 现成可用，一周就能上线；对内容量少的阶段，"你读过哪些"和"你会哪些"几乎等价。

**为什么没选**：用户明确选了概念级。更实质的问题是，条目级无法表达"同一个知识点分散在多篇内容里"，而这恰恰是个性化平台要解决的问题——没有概念层，平台只知道"这个用户读了 12 篇文章"，不知道"他掌握了网络分层、但完全没碰过 TCP 重传"。以后补概念层等于接口、数据结构、掌握度全部重写。

**它给出的代价，本方案接受了什么**：条目级方案立刻可用而本方案在概念表为空时图谱是空的。这是本方案真实的短板，见风险一节。

### 备选二：用现成图数据库（Neo4j / 图查询）

**它最强的理由**：多跳查询（"前置链上我缺哪一环"）用 Cypher 一行就写完，关系深的图查询性能更好。

**为什么没选**：项目已裁决"仅 MySQL，不做多数据库适配"，引入图数据库是新增一个有状态服务、一套备份与运维。而本项的数据量在数百节点、数千边，MySQL 的普通表加两次查询完全够用；多跳分析本期不做。等真的需要多跳再评估，那时属于新的架构裁决。

### 备选三：把掌握度落库并异步重算

**它最强的理由**：可以按掌握度排序、做索引、做分页，图谱端点只读一张宽表；重算成本被摊到后台。

**为什么没选**：输入量小、算法简单，实时计算更快也更不容易出错；落库要额外承担失效与一致性问题。将来若概念数增长到万级且需要按掌握度做全局排序，再考虑物化。

### 备选四：3D 作为主入口

**它最强的理由**：用户最初的诉求就是 3D，观感与"知识宇宙"的想象最接近，演示效果最好。

**为什么没选**：用户已明确改为 2D 主入口。技术上 3D 的方位不稳定、点击目标小、文字难读，作为主入口会牺牲可用性。

## 交付拆分

1. **数据与算法**（概念表、关联表、边表、浏览表、掌握度纯函数）——可独立验证：单测覆盖所有档位。
2. **端点**（浏览上报、图谱聚合、管理端概念维护）——可用 curl 验证：建概念、挂条目、看图数据。
3. **2D 图谱页**——用户可见的第一个完整切片。
4. **管理端概念页**——让概念能被真正建立出来。
5. **3D 切换与助手联动**——两项增量，任一推迟都不影响前四项交付。

## 风险与缓解措施

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| **概念表为空，图谱没有内容** | 功能看起来"做了没用过" | 管理端概念页必须好用（一次能挂多个条目）；空状态明确指路；首批概念随内容导入一起录入 |
| **条目页分数尚未接线（WORK-020 TASK-013 未做）** | 掌握度只有浏览与自评两路，档位上限「熟悉」 | 已在需求里写明降级行为；不伪造分数；WORK-020 接线后自动生效 |
| 概念划分粒度失控（要么太细上百个点，要么太粗没信息） | 图不可读 | 管理端强制名称唯一；设计里给出"一个概念应对应一次可独立测验的知识点"的口径；首批按课程大纲控制在一门课 8–15 个概念 |
| 前端引入图库后包体膨胀 | 其他页面变慢 | 两个图库都动态 import；只在 `/learn/graph` 加载；验收里要求证明 3D 不加载 |
| 3D 在小屏不可用 | 用户否掉观感 | 保留 2D；3D 是可选视角，不承载必需功能 |
| 浏览记录被刷新/预取放大 | 数据失真 | 同一次页面停留只上报一次；服务端只累加计数，不做去重判断（去重放在前端一次会话内） |
