# 提案 · 身份化千人千面与求职者面

## 一句话

把"身份"落成一个**可切换的维度**（用户画像的一行 + 代码里的注册表），把 AI 的行为从"一份通用提示词"扩成**可切换的行为模板（harness）**，第一个身份面做 **AI 模拟面试**（多轮追问 + 独立点评），并补上"自评 → 记忆"这座断桥。

## 已确认事实

见 `requirements.md` 的「已确认事实」表。最要紧的三条：

1. **身份/画像在数据上完全不存在**（`users` 表一个画像字段都没有），但接入点已预备好（`AccountApi` 注释写着"等第一个真实消费者出现时再加方法"）。
2. **"一个任务一个提示词类"是既有模式**（`SummaryPrompt` / `ConversationPrompt` 分开，注释明写"混用会让约束打架"）——harness 分化是它的延伸，不是新架构。
3. **记忆是"用户一份"**（两表都带 `user_id`），且**已有界面**（记忆面板 + 「记住这条」）；缺口只在"结构化那路没人往里写"与"自评没接进记忆"。

## 备选方案

### A. 身份 = 画像行 + 代码注册表 + 配置包；harness = 提示词与工具的可切换组合（建议）

**做法**：新增 `learner_profiles`（身份 + 求职者画像字段）；身份注册表就是代码里的枚举（一期只有 `job_seeker`）；harness 是"提示词 + 工具子集"的可选组合，给 `AssistantConversation.Request` 加一个 `harness` 入参；会话表加一个可空 `harness` 标记。

**优点**：
- 与既有的"一个任务一个提示词类"模式一致，改动面小。
- **一期只动 1 张既有表**（会话表加一个可空列）；记忆按裁决不分区，一列都不用加。
- "记忆是用户一份"天然成立，不需要为身份做任何数据切分。
- 无新增依赖（AgentScope 已接入）。

**缺点/代价**：
- 身份是**横切关注点**，将来每加一张用户私有表都要问一次"它要不要认身份"。
- 一期只有"求职者"一个身份实心 → **多身份切换路径无法端到端验收**（已写进需求假设）。

### B. 身份建成独立实体表（`personas`），记忆与会话外键指向它

**优点**：结构上强制"记忆挂在某个身份上"，不存在"忘了填"的状态；将来若要做"用户自定义助手"，那张表有地方装定制项。

**缺点/代价**（不建议的理由）：
- **它表达不了"记忆全局"**：需求 REQ-004 要求记忆是用户一份（"事实类跨身份成立"）。若记忆必须挂到某个身份，就得给每个用户造一条"全局身份"来挂这些记忆——这是 hack。
- **越权面变宽**：读记忆要先证明"这个身份是这个用户的"；而现在 `WHERE user_id = ?` 就挡住了。
- **多一份生命周期**：建/删时机、注销清单、迁移都要跟着多一份。
- 而它现在**没有内容可装**：一期没有"用户自定义助手"，那张表的每一行只有 `(user_id, 身份)`，等于一行 `users`。

### C. 只做"场景化助手"，不引入身份维度

**优点**：最省，只做 harness 分化（面试官/点评官），不碰用户数据模型。
**缺点**：**放弃"按身份推荐"这个产品诉求**（本项的核心目标之一），且"扩展点成立"这件事无法验证。**不满足 REQ-001/002/009。**

## 决策

**选 A。** 理由：身份在数据上就是"用户的一行画像 + 一个当前选择"，没有任何需要独立生命周期的东西；harness 是**行为模板**不是**人**，代码里已有先例。B 的成本花在"结构强制"上，而它换来的结构恰恰**表达不了**已裁决的"记忆不分区"。

## 代价（已告知并接受）

- 身份维度横切：将来新增用户私有表时要多问一句"认不认身份"。本项确立了处置原则（**记忆不分区；只有会话带行为标记；新表自带身份**），后续照抄。
- **一期只有单身份 → 多身份切换路径无法端到端验收**；同理，"身份当默认行为"在一期没有可观察差异（默认恒为通用助手）。两处都要在测试计划里写明是缺口而不是漏测。
- 面试是 AI 重度功能（多轮带工具 + 一次点评），**token 消耗成倍**；依赖 `WORK-009` 的积分与平台凭据。
