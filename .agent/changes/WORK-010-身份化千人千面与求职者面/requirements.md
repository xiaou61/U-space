## 核心模型（讨论定论）

**一次对话 = 公共的行为 × 私有的数据**

```
一次对话 = 公共的行为（harness：提示词 + 场景工具，按场景/身份选）
         + 私有的数据（记忆 + 历史 + 凭据，按用户取）
```

这两半在当前代码里**已经合在一处**（`ConversationService`）。**千人千面恰恰发生在两半的交叉点**：同一个公共的面试官行为 × 你的记忆（"上次 Redis 那一块你答砸了"）→ 这次专门追问 Redis。这个"专门追问"公共或私有单独都产不出。

**因此不把"场景 agent"和"个人 agent"做成两个实体**——那会新造一个"跨 agent 传记忆"的问题（面试行为要知道你哪块弱就得回去取），而且**积分制下每轮至少两次调用，直接双倍花钱**。落地形态是：**一个运行时 + 两个可替换插槽**（行为按场景选、数据按用户取）。

## 背景

`deferred-scope.md` 自己写着：练习、作答、判分、掌握度、学习路径这五项"产品命门"**全部推迟、无归属**。也就是说**输入侧（内容 + AI）齐了，输出侧（个性化）是空的**。本项是第一次把"输出侧"接上归处——用身份作为个性化的入口，用第一个身份面（求职者）作为具体承载。

选择"求职者"作为第一个面，是因为用户本人正在秋招——**他就是这个功能的第一个真实用户**，第一个用户数据就是他自己的面试表现。

## 目标

- 让用户**选择并切换**自己所处的身份，且身份**不影响能做/不能做什么**，只影响**推荐什么**与**AI 以什么形态出现**。
- 把 AI 的行为从"一份通用的学习助手提示词"扩成"**多套可切换的行为模板**"，并按"页面优先、身份当默认"选择。
- 落地第一个身份面：**AI 模拟面试**（多轮追问 + 结束点评），题源来自知识库条目与用户自己的材料。
- 让"助手记得你"这件事真正成立：**补上自评 → 记忆的桥**。

## 非目标

- 不做硬性权限边界（"只有求职者能看 X"这类）。
- 不做多身份并存（主 + 副）与权重合并——一期是单选可切换。
- 不做多 Agent 协作（planner/executor/critic）。
- 不做推荐算法、排序模型、协同过滤——一期只做规则映射。
- 不做语音（STT/TTS）、不做视频面试。
- 不做简历文件解析（简历/项目那一块二期；一期面试的素材来自笔记与知识库条目）。
- 不做练习/作答/判分/掌握度/学习路径——那是这条路的后续，不在本项。
- 不做"千人千面"的内容分发侧（UGC 上传与审核）——见「关联工作项」。

## 用户与工作流程

**选择身份**：首次进入或设置里选择"我现在的身份"（一期只有求职者一个可选项）→ 首页、导航、推荐内容按该身份的配置包重排。

**模拟面试**：在求职者面进入模拟面试 → 面试官基于题源开场提问 → 用户作答 → 面试官追问（多轮）→ 用户结束 → 点评官给出结构化评分与改进点 → 结果留存在本人名下。

**记住你**：用户在条目上改动自评（懂了/还不懂）→ 系统自动写一条结构化记忆 → 之后助手在相关对话里"记得"。用户也可以在助手回答旁点「记住这条」（既有能力）。

**切换身份**：随时切换 → 推荐与助手默认行为随之变化 → **记忆、笔记、自评都不丢**。

## 功能需求

- **REQ-001 身份维度**：新增"身份"概念，与角色正交；身份**不得**写入 `users.role`。用户当前身份需要持久化。
- **REQ-002 身份选择与切换**：用户可单选一个当前身份并随时切换；一期只有"求职者"实心，其余只在注册表留位。
- **REQ-003 用户画像**：记录身份相关的最小目标信息（求职者所需：目标岗位、目标城市/公司、时间线秋招/春招、当前阶段）。**不是所有身份共用一套字段**——一期只定义求职者的字段。
- **REQ-004 记忆不分区**：记忆是"用户一份"，不按页面、场景、身份切分。撤销原 2A。
- **REQ-005 harness 注册与内置**：平台内置多套行为模板（提示词 + 工具集）；一期内置**面试官**与**点评官**两套，加上既有的"通用助手"一套。
- **REQ-006 harness 选择规则**：**页面优先、身份当默认**。有明确场景（面试页等）时用场景行为；无明确场景（全站对话入口）时用身份默认行为。
- **REQ-007 工具分层**：通用工具（操作本人数据）在所有场景都提供；场景工具只在对应场景提供——**非面试场景下，面试专用工具不得出现在传给模型的工具集里**。
- **REQ-008 personal agent 不新建实体**：一个用户一份，即既有 `user_id`；记忆、会话、凭据、消耗均按 `user_id` 归属。
- **REQ-009 推荐配置包**：每个身份一份配置（推荐哪些知识分类、首页卡片与顺序、导航入口顺序、助手开场白）；一期**规则映射**，不做算法。
- **REQ-010 模拟面试（面试官）**：多轮、可追问、流式输出（思考与正文分开渲染，沿用既有能力）；题源来自知识库已发布条目与用户本人材料；面试过程中**不写任何用户数据**（沿用"自主只建议不动作"）。
- **REQ-011 面试点评（点评官）**：面试结束时以**独立、无工具**的一次调用产出结构化评分与改进点。**这一分工同时绕开 DeepSeek 的"工具调用与结构化输出不能在同一次调用里并用"限制。**
- **REQ-012 自评 → 结构化记忆的桥**：用户改动某条目的自评时，自动写入一条结构化记忆（`kind` 指向"条目理解"）。
- **REQ-013 切换身份不丢数据**：记忆、笔记、自评、会话在切换后全部保留可见。
- **REQ-014 注销级联**：本项新增的用户私有表登记进 `AiUserDeletionListener` 的清单。
- **REQ-015 前端**：身份选择入口；面试界面（提问/追问/流式/思考折叠/结束与评分）；首页与导航按身份配置重排。

## 质量要求

- **身份与权限严格正交**：改身份**不得**改变任何权限判定结果（有回归断言）。
- **两个维度不串味**：同一个用户在不同场景发起对话时，行为不同、但"它是同一个人"（记忆一致）。
- **场景工具不外泄**：非面试场景下工具集里没有面试工具（有断言）。
- **记忆不因切换而丢失或重影**：切换身份不产生重复记忆、不隐藏已有记忆。
- **面试可中断**：用户中途退出不产生脏数据，也不扣未发生的费用。
- **积分语义正确**：**依赖 WORK-009**——余额不足时面试入口给出明确提示而非报错。

## 约束与依赖

- **硬依赖 `WORK-009`**：`WORK-009` 把凭据来源改成平台统一配置之后，用户不再自带 Key；本项的 AI 功能必须走那条路。**顺序反过来也让依赖方向变干净了**：现在 `WORK-010` 依赖 `WORK-009`，而 `WORK-009` 不依赖 `WORK-010`。

- 不新建"身份"以外的 AI 实体；不新增依赖（AgentScope 已接入）。
- 身份字段命名避免与既有形近词冲突：`ai_entry_summaries` 已有唯一键 `uk_ai_summary_identity`，那里的 "identity" 指**缓存指纹**（条目+内容哈希+模型+提示词版本+属主），**不是用户身份**——新字段不要复用 `identity` 这个名字。

## 验收标准

- **AC-001 身份与角色正交**：把某用户身份设为"求职者"，其 `role` 仍为 `learner`，管理端访问判定不变。
- **AC-002 切换身份生效**：切换后首页/导航/推荐顺序按新身份的配置变化。
- **AC-003 记忆不分区**：在身份 A 下的对话内容被助手记住后，切到身份 B 仍能被召回（集成用例）。
- **AC-004 记忆与既有数据不丢**：切换身份后，记忆列表、笔记、自评、历史会话条目数与内容不变。
- **AC-005 harness 选择正确**：面试页发起对话 → 用面试官行为；全站入口发起 → 用身份默认行为（有可观察差异的用例）。
- **AC-006 场景工具不外泄**：非面试场景下传给模型的工具集不含面试工具（断言工具 schema 名称集合）。
- **AC-007 点评是独立无工具调用**：点评那次请求的工具集为空，且返回结构化评分（可被解析、字段齐全）。
- **AC-008 自评桥生效**：把一条自评改为"还不懂" → `ai_memories_structured` 出现一条对应记忆；重复修改不产生重复堆积（规则见「待确认问题」）。
- **AC-009 面试闭环**：能完整走完"开场 → 多轮追问 → 结束 → 评分"，中途退出不产生脏数据。
- **AC-010 零积分语义**：余额为 0 的用户点面试入口 → 明确的"积分不足"提示，**不是** 500 或上游错误（依赖 WORK-009）。
- **AC-011 注销清零**：注销后本项新增表的断言行数为 0（并入既有逐表清单用例）。

## 假设

- **一期身份只有一个可选值（求职者）**，因此"切换身份"这条验收在数据上靠"人工造第二个身份"来测——**这是一个已知的测试缺口**：真实的多身份切换路径在一期无法被端到端走过。需要在测试计划里写明。
- 面试一期为文本；不做语音、不做实时音视频。
- 题源以知识库已发布条目为主，用户自己的材料（笔记）为可选补充；**笔记里可能有用户隐私内容，送进上游前需要有明确的取舍**（见「待确认问题」）。

## 待确认问题

1. **身份注册表一期留哪几个注册位？**（只留位、不做界面）——建议留"考研/考公/日常学习"三个占位，便于验证扩展点形状。不阻断批准（可随实现定）。
2. **面试的题量 / 时长 / 是否限时？**——建议一期不限时、题量由用户主动结束控制。属实现选择。
3. **自评 → 结构化记忆的重复抑制规则**：同一条目反复改动，是**覆盖**（保留一条，更新内容）还是**追加**（累积多条）？建议覆盖（否则记忆会被反复改动撑爆召回名额）。**这一条会改变记忆的读写行为，需要你定。**
4. **用户笔记是否可以作为面试素材送进上游？**——笔记是严格私有的数据，送进上游意味着它离开了本机（上游是第三方）。建议：**默认不送，由用户在面试开始时显式勾选**。

## 什么情况下该重审

- 一期验收时发现"只有一个身份"让扩展性无法验证 → 需要真的铺第二个身份方位。
- `WORK-009` 的积分制让面试成本高到不可接受 → 需要重新看题量与轮次上限。
- 出现"身份应该限制能力"的真实诉求 → 那是权限模型的变化，本项的核心护栏（身份不写入 role）需要重审。
