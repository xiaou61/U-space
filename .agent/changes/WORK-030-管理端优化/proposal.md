# 提案 · 管理端优化

## 摘要

管理端现在有十个页面，但**只有条目管理一个同时有筛选和分页**；三处要知道"用户是谁"的页面都要管理员手敲内部主键；总览只看得到知识库的三个数字。本项做四件事：**新建用户管理页**（搜人、看积分与 AI 消耗、改角色、删除、调积分）、**删掉独立的积分调整页**、**给所有列表补筛选**、**按 new-api 的密度重做调用明细**。

## 推荐方案

### 为什么先做用户管理

用户最痛的那一条是「发积分要记用户 id」。而现在的代码自己写着：

> 用户 id 是内部主键，敲错一位就会给另一个人发分，而这一步能顺手发现。

**发积分是不可撤销的动作，正确性却挂在"管理员肉眼核对一串数字"上。** 这是可用性问题，也是安全问题。

根子在 `AccountApi` 只有 `findRoleById` / `findProfile` / `saveProfile` 三个方法——账号模块**根本没有列表或搜索能力**，所以上面几页只能拿 id 没法拿名字。

### 关键机制

| 机制 | 做法 | 为什么不能省 |
| --- | --- | --- |
| **搜索走后端** | 用户名 / 邮箱模糊匹配，分页返回 | 前端全量过滤只在"已全部取回内存"时成立，引入分页就不成立了 |
| **列表用行内展开** | 选中一行就地展开详情与操作 | 跳新页会丢掉筛选与页码状态 |
| **聚合口径统一** | "已用积分"只认 `ai_credit_ledger` 的负向合计 | 另一条路（累加 `ai_runs.credits`）会漏掉精简那一路 |
| **不可自伤在服务端** | 目标 id == 令牌里的 id 直接拒绝 | 前端藏按钮挡不住直接调接口 |
| **改角色吊销 refresh** | 复用现成的 `deleteByUser` | 降级的意思就是"立刻没有权限" |
| **payload 独立表** | `ai_run_payloads`，30 天保留 | 完整 prompt 几十 KB，`attrs` JSON 列装不下 |

### 不选的路

| 方案 | 为什么不做 |
| --- | --- |
| 在前端下拉里塞全部用户 | 用户量一上来就是几 MB 的响应；且与分页冲突 |
| 给 `users` 加 `status` 列做禁用 | 用户裁决不做禁用（U-19）。加列要改登录链路，收益不匹配 |
| 复用 `AccountDeletionService.delete` 删号 | 它要求**用户自己的密码**，管理员拿不到；但级联那段必须共用 |
| 引入图表库补"图" | new-api 的密度来自列多、筛选多、汇总多，不是图。先不加依赖 |
