### 三条决定实现方式的仓库事实（改角色/删除）

| 项 | 事实 | 后果 |
| --- | --- | --- |
| 角色在令牌里 | `TokenService.issueWithin` 把 `user.getRole()` 写进 `AuthPort.Subject`，签发后**不再查库** | 改角色对已签发的访问令牌**不生效**，直到它过期；只能靠吊销 refresh 让它尽快退场 |
| 吊销是现成的 | `RefreshTokenMapper.deleteByUser(userId)` 已存在（注销时在用） | 改角色/删除时顺手调它，不需要新写 SQL |
| 注销要求密码 | `AccountDeletionService.delete(long userId, String rawPassword)` **校验用户自己的密码** | 管理员删人拿不到对方的密码，**不能直接复用这个方法**；需要一条跳过密码、只做级联的路径 |
| `UserMapper` 的列 | 三条 `SELECT` 都写死了 `id, username, email, password_hash, role, email_verified_at`，**没有 `created_at`** | 列表页要显示注册时间，必须**新增查询**；**不动登录用的那三条**，降低回归面 |

## 实现选择

### 一、为什么不用 AgentScope 的 streamEvents（U-15 的核实结论）

那篇文章讲两样东西：`agent.streamEvents(...)`（SDK 自己驱动 ReAct 循环并吐事件）与 `Middleware`（在 `onAgent / onReasoning / onModelCall / onActing` 各阶段插钩子）。

**我们两样都没在用，而且换过去是净亏。**

| 事实 | 出处 |
| --- | --- |
| 我们用的是 `agentscope-core:2.0.0`，**只用了 `Model` + `ChatResponse` + 两个 accumulator**（`TextAccumulator` / `ToolCallsAccumulator`） | `backend/paideia-ai/pom.xml:56`、`AgentScopeAssistantAnswerer` 的 import 头 |
| 工具循环是**自己写的 `for (int round = 0; round < MAX_TOOL_ROUNDS; round++)`**，不是 `ReActAgent` | `AgentScopeConversation.java:103` |
| 我们已经有自己的步骤记录：每轮 LLM 各开一步、每次工具各开一步，落 `ai_run_spans` | 同上 `:112`、`:290` |
| 文章用的是 **2.0.3**，我们是 **2.0.0** | 版本核实 |

换 `streamEvents` 的代价：**整条对话链路重写**（现在这套手写循环里塞满了实测修出来的坑——每轮各发一条 `ToolResultMessage`、最终轮才推正文、思考内容不进历史），而它的产出（模型轮次、工具调用、文本增量、最终结果）**我们现在这五样一个不少**。

文章里真正值得学的只有两条，而且不用换框架就能拿：**① 每一步都记下请求与结果的标识**（它用 `source + toolCallId`，我们用 `seq`，等价）；**② 工具步要能看到参数与返回**——这一条现在是我们的空白，已写成 REQ-052 / 053。

### 二、其余由 Agent 依既有边界决定的选择

1. **搜索走后端**，不做前端全量过滤。用户表与流水表会增长，前端过滤只在"已经全部取回内存"时才成立，而分页一进来就不成立了。
2. **用户管理用「列表 + 行展开/抽屉」，不跳新页**。new-api 也是就地编辑；跳页会丢掉筛选与页码状态。
3. **不动 `users` 表**（U-19）：不做禁用就不需要状态列，本项**零 schema 变更**，登录链路一行不改。
4. **改角色 / 删除时统一吊销该用户全部 refresh token**（复用现成的 `RefreshTokenMapper.deleteByUser`）。代价是被踢下线，这正是降级与删号该有的效果。
6. **管理员删人不复用 `AccountDeletionService.delete`**（它要求用户自己的密码），但**共用级联那一段**：抽一个不校验密码的内部方法，`delete` 与管理员删除都走它。
7. **步骤内容存在 `ai_run_spans.attrs` JSON 里**，不新增列。已有列够用，加列会让这张写入最频繁的表变更代价变大。
8. **不引入图表库**（见「假设」）。

## 背景

管理端现在有五组页面，但**它们都不知道"用户是谁"**：积分调整、用量审计、调用明细三处都要管理员自己记住并手敲一个内部主键，列表里显示的是 `#123`。管理员要回答"给张三发点分"，得先去数据库查 id。

这既是可用性问题，也是安全问题：**发积分这个不可撤销的动作，正确性依赖管理员记住一串数字**。

更大的问题是**信息密度**。十个页面里只有条目管理一个同时有筛选和分页；用量审计与调用明细把查询条件写死在代码里（`limit=200`、`size=50`、7 天）；调用概览的排行是纯文字；总览的三个数字全是知识库的。sub2api 那种「统计卡片 + 多维筛选 + 分布图 + 分页 + 下钻」的形态，这里一半都没有。

## 目标

- 管理员能从**用户名或邮箱**找到人，而不是记 id。
- 管理端有「用户管理」页：浏览、搜索、看单个用户的积分与 AI 消耗，并就地改角色、启停、删除、调积分。
- 独立的「积分调整」页消失，入口合到用户管理。
- 所有列表页都有筛选控件；能后端筛的走后端，不要前端全量过滤。
- 调用明细按 new-api 的形态重做（多维筛选、自定义时间区间、页面级汇总、分页）。
- **字段补密**：每个列表的列数按 new-api 的密度对齐，不再出现"四列就看完了"的表。
- 管理端整体的信息密度拉齐，不再有"一张白纸加一行表"的页面。

### 该用户详情（下钻）

积分流水（时间 / 种类 / 变化 / 模型 / tokens / 操作人 / 备注）+ AI 调用（时间 / 场景 / 模型 / 状态 / 耗时 / 首字 / 轮次与工具 / tokens / 扣分）+ 汇总（余额、累计消耗、调用次数、成功率、平均耗时）。

**这些数据全都在，只是从来没有一个页面把它们按人摆在一起。**

### 调用明细（每行，对齐 new-api 的日志列）

时间 / 场景 / 状态 / 模型 / tokens（输入、输出、缓存） / 扣分 / 耗时 / 首字 / 轮次与工具 / 用户 / 详情。
**现在缺的**：模型单独成列、缓存的 tokens、用户显示为用户名。

### new-api 有而本项目没有的字段

分组、令牌、渠道、邀请、IP、RPM/TPM——**没有对应实体，不造**。要 RPM/TPM 得先有"最近 60 秒"的滑动窗口统计，而本项目一天只有几次调用，这两个数没有意义。

## 非目标

- **不做 new-api 的网关能力**：分组、令牌、渠道、上游调度、兑换码、订阅、支付、邀请返利——本项目不是 API 网关，没有这些实体。
- **不做 RPM / TPM 实时看板**：一天只有几次调用，这两个数没有解释力；有需要时由运维页的 Prometheus 承担。
- **不做批量操作**（批量删除/批量启停/批量发分）：现在只有两个账号，批量是给不存在的规模做优化。
- **不做列可见性切换并存 localStorage**：new-api 有，但它解决的是"几十列挤不下"的问题；本项列数在 15 以内，先不引入这份复杂度。若实现后确实挤，再单独加。
- **不做账号自助改密、找回密码**：既有决定（WORK-003）是不做找回密码。
- **不改运维页**（WORK-028）。
- **不做审计导出、图表导出、CSV 下载**。

## 用户与工作流程

**发分**：用户管理 → 搜"张三"或他的邮箱 → 列表里选中 → 展开详情看到余额、已用、调用次数、最近活跃 → 填增减值与原因 → 提交 → 余额与流水立即更新。

**查某人花在哪**：用户管理 → 选中某人 → 详情里看积分流水与调用记录。

**处置一个用户**：用户管理 → 选中 → 改角色 / 删除（都要二次确认；**当前登录的管理员本人不可被选中执行这些操作**）。

**排查一次慢调用**：调用明细 → 选时间区间与条件 → 看页面级汇总与列表 → 点开某行看步骤耗时。

## 功能需求

### 用户管理

- **REQ-001 按人查，不按 id 查**：搜索至少支持用户名与邮箱；区分"搜不到"与"有多条"；输入即筛（防抖），不做"回车才查"。
- **REQ-002 用户列表**：分页展示账号；列见「字段清单」。**任何列表与详情都不得返回 `password_hash`。**
- **REQ-003 筛选**：按角色（管理员 / 学习者）筛选；可按余额或调用次数排序（回答"谁快没分了""谁用得最多"）。**不做状态筛选**（U-19 不做禁用，没有状态可筛）。
- **REQ-004 单个用户详情**：同页展开（不跳走）看到该用户当前余额、累计消耗、调用次数、最近活跃时间，以及最近的积分流水。
- **REQ-005 AI 消耗**：详情里看到该用户**最近的 AI 调用**与**汇总**（调用次数、成功率、扣分合计、平均耗时）。
- **REQ-006 调整积分**：增减积分必须填原因；调整后余额与流水立即反映。
- **REQ-007 改角色**：学习者 ⇄ 管理员。改完**立即吊销该用户全部 refresh token**（U-18）：他手里的访问令牌仍能用到过期（分钟级），但下次刷新就要重新登录，新令牌才带新角色。
- **REQ-009 删除账号**：二次确认；复用既有的注销级联（`AccountDeletionService` + `UserDeletedEvent`），把各模块的用户数据一起删干净。**不需要用户自己的密码**（管理员操作，与自助注销不同）。
- **REQ-010 不可自伤**：当前登录的管理员**不能对自己**改角色、删除、调整积分。这些操作在服务端按"目标 id = 令牌里的 id"直接拒绝，不能只靠前端把按钮藏起来。

### 各页筛选（U-07）

- **REQ-011 用量审计**：支持按用户、流水种类、时间区间筛选；分页；用户列显示用户名而不是 `#123`。
- **REQ-012 举报处理**：按状态筛选（待处理 / 已下架 / 全部），默认待处理；分页。
- **REQ-013 概念**：按名称搜索 + 按分类筛选。
- **REQ-014 条目**：补分类筛选（现有状态 + 标题保留）。
- **REQ-015 分类**：按名称搜索（层级树保留）。
- **REQ-016 调用明细**：见下条。

### 调用明细（U-08 / U-10）

- **REQ-020 时间区间可自定义**：至少支持"近 1 小时 / 今天 / 近 7 天 / 近 30 天 / 自定义区间"，不再写死 7 天。
- **REQ-021 筛选维度**：场景、状态、模型、用户（按用户名搜索选择，**不是数字输入框**）。
- **REQ-022 页面级汇总跟着筛选变**：调用次数、成功率、扣分合计、tokens 合计、耗时 p50/p95，口径与「调用概览」一致。
- **REQ-023 分页**：有页码与每页条数；不再写死 `size=50`。
- **REQ-024 下钻保留**：点开一行看步骤耗时（现有能力不退化）。
- **REQ-025 一律用家里组件**：筛选控件用 `@paideia/ui` 的 `Select`，不许再出现原生 `<select>`（WORK-002 已定）。
- **REQ-026 列补密**：见「字段清单」里的调用明细列。

### 步骤明细要能看到"调了什么、回了什么"（U-14 / U-15）

**现状**：`ai_run_spans` 已经记录了 `seq / kind / name / status / duration_ms / 输入输出 tokens`，页面也按 6 列展示。**问题不是没记录，是记录得太少**——页面上只能看到「工具 `my_notes` 花了 300ms、成功」，看不到它**收到了什么参数、返回了什么、返回多大**。排查"它为什么答错了"时这四样正是关键。

四项缺口（2026-10-21 逐行读码核实）：

| 缺口 | 现状 |
| --- | --- |
| 工具参数 | `AgentScopeConversation.execute()` 手里有 `call.getInput()`，**没有记录** |
| 工具返回 | 手里有 `outcome.text()`，**没有记录** |
| 首字延迟（步骤级） | `SpanRecord` 有 `ttftMs` 字段，但 `DefaultRunRecorder` 的 `close()` **恒定传 `null`** |
| 模型与提示词版本（步骤级） | 只在 run 级记，步骤级没有 |

另有两条结构性限制：`parentSeq` **永远是 null**（不产生嵌套）；`ALLOWED_ATTRS` 白名单只有 8 个键（`httpTraceId / historyMsgs / memoryHits / entryChars / learningSummaryChars / queued / reqChars / respChars`），**全是请求级的量，没有任何工具级内容**。

- **REQ-050 步骤级首字延迟**：每一步（尤其 LLM 步）记 `ttft_ms`，不再恒为 null。首字来自流式增量，`runRound` 里已经有回调点。
- **REQ-051 步骤级模型与提示词版本**：每个 LLM 步记 `model` 与 `prompt_version`，这样一次多轮调用里"第 3 轮换了模型"看得见。
- **REQ-052 工具参数**：工具步记下入参 JSON，**截断到固定上限**（建议 1000 字符），超限标注「已截断」。
- **REQ-053 工具返回**：工具步记下返回内容长度 + **截断预览**（建议 500 字符）；不得只记长度不记内容——排查时"返回了什么"才是答案。
- **REQ-054 步骤详情可展开**：调用明细里点开某一步，能看到上四样（参数、返回预览、首字、模型）。形态对齐 new-api 的日志详情弹窗，用行内展开或抽屉，不跳页。
- **REQ-055 步骤表列补密**：现有 6 列之外补「首字」「模型」，并让「类型 / 名称」可读（`llm#2` 这类标号要配一句人话）。

### 完整的 prompt 与模型原始返回（U-17）

**这是本项最重的一块，也是唯一会新增一张表的地方。**

`REQ-052/053` 只能装"截断的片段"，而排查"模型为什么这样答"需要的是**这一轮实际送上去的全部内容**与**模型吐回来的全部内容**。两者体积都在几十 KB 级，`ai_run_spans.attrs` 是 JSON 列、那表写入最频繁——塞不进去。

- **REQ-060 独立表存一次交互的输入与输出**：新表 `ai_run_payloads`，按 `trace_id + seq` 定位到某一步，存：请求体（送上游的 messages 数组、工具清单、采样参数）、响应体（模型返回的完整内容、tool_calls、finish_reason）、字节数。**只在 LLM 步落，工具步不落正文。**
- **REQ-061 存的是"实际发送"而不是"打算发送"**：必须在真正发上游那一刻抓取序列化后的内容，不能拿构造前的对象——否则序列化层偷偷加的 system 提示、裁剪后的历史、注入的记忆都不会体现。
- **REQ-062 独立保留期**：`ai_run_payloads` 的保留期默认 **30 天**（U-20），比 `ai_run_spans` 的 90 天短。理由：它是诊断用的临时证据，不是账目；体积大且含用户内容。
- **REQ-063 到期清理走既有清理器**：`TelemetryRetentionPurger` 现在按 `retentionDays` 清 `ai_runs / ai_run_spans`；本表要一种更短的保留期，因此**加一个独立配置项**，不复用同一个值。
- **REQ-064 停用开关**：配置项 `paideia.ai.telemetry.payload.enabled`，默认开。关掉时**不写库**，页面显示「本次未记录请求体（已停用）」而不是空白。
- **REQ-065 页面上能看**：调用明细 → 展开某一步 → 「请求」与「响应」两个可折叠区块，等宽字体、可复制。**超过 50KB 的内容只给下载不留内联渲染**（避免浏览器卡死）。
- **REQ-066 体积上限与拒绝**：单条 payload 超过 1MB 时**存一条占位记录**（写明原始字节数、标记 `truncated=1`），不写正文。**不静默丢弃**——静默丢弃会让"这一轮为什么没有请求体"变成一个新的谜。
- **REQ-067 敏感内容不入 payload**：API Key、Authorization 头、refresh token 一律不得出现在存下来的请求体里（它们在 HTTP 头而不在 body，但**必须有测试证明这一点**，不能只靠"应该不在"）。

### 调用概览

- **REQ-030 时间区间可自定义**：与调用明细同一套选择器，不再写死 7 天。
- **REQ-031 补「按用户」排行**：回答"谁在烧钱"。

### 总览

- **REQ-040 总览要有运营数字**：账号数、近 7 天调用次数、近 7 天扣分合计、待处理举报数。**不再只有知识库三个数**。

## 质量要求

- **权限**：新端点挂 `hasRole("ADMIN")`，规则写在 `/api/**` 的服务端匹配表里，且必须排在更宽的规则之前；前端隐藏不算控制。
- **隐私**：邮箱只在管理员端点返回；不得返回 `password_hash`。
- **不可信入参**：搜索串要限长、转义；分页 `size` 必须有上限（防止 `size=100000` 拖库）。
- **聚合口径一致**：同一用户"积分消耗"在用户管理、用量审计、调用明细三处必须由**同一数据源**得出，不能一处读 `ai_credit_ledger`、另一处读 `ai_runs` 后各算各的。
- **筛选必须真的生效**：点筛选后结果条数要跟着变；空结果要有可读提示。
- **步骤内容入库要限长**：`REQ-052 / 053` 的记录必须在上限处截断，**不能把整份工具返回写进库**——一次笔记全文或一段记忆可能就是几十 KB，`attrs` 是 JSON 列，写大了会拖慢整张表。截断要在写入前做，不是读出来再截。
- **payload 与步骤是两种数据，别混**：`attrs` 存的是**量**（长度、条数、截断标记），`ai_run_payloads` 存的是**内容**。不要因为后者存在就往前者塞正文。
- **payload 写库不能拖慢对话**：写入必须走既有的 `RunWriteQueue` 异步队列，**不许在响应链路上同步写 1MB 的 body**。
- **隐私边界（U-16 已裁）**：管理员通过本项能看到用户私有笔记与记忆的片段/全文。**这是用户明确要求的**，但必须在页面上有一句说明这一页能看到什么，不能让人误以为只是技术指标。

## 验收标准

- **AC-001 搜到人**：在用户管理里输入某人的用户名片段或邮箱片段，列表在 300ms 内筛出该用户；输入一个不存在的串，页面显示「没有匹配的用户」而不是空表。
- **AC-002 列表字段齐**：列表每行显示用户名、邮箱、角色、余额、已用积分、调用次数、最近活跃、状态、注册时间。用真实数据核对其中至少一行的余额与「用量审计」里该用户流水合计一致。
- **AC-003 调积分可用**：对某个学习者加 100 分，余额从 N 变 N+100，流水多一条 `管理员调整`（操作人是当前管理员、备注是填写的原因）；再减 100 分回到 N。两次操作都立即反映在列表里，不需要手动刷新。
- **AC-004 不可自伤**：以管理员 A 登录，页面上无法对 A 自己调积分/改角色/删除；**直接调接口传自己的 id 返回拒绝**（4xx，不是 200）。
- **AC-005 改角色生效**（U-18 的验收）：把学习者 B 升为管理员，B 重新登录后能进管理端；降回学习者后，B 手里旧的 refresh token 已失效（刷新被拒），重新登录后进不了管理端。
- **AC-006 无 schema 变更**：本项不新增任何迁移文件，`users` 表结构与登录链路一行未改。
- **AC-007 删除干净**：删除一个测试账号后，该账号在 `users`、`ai_credit_accounts`、`ai_credit_ledger`、`ai_runs`、记忆、会话等表里都没有残留行（按注销级联的表清单逐表核对）。
- **AC-008 积分调整页已消失**：侧栏没有「积分调整」，手敲 `/ai-credits/grant` 不会渲染空白页（转向或 404 有明确落地）。
- **AC-009 每个列表都能筛**：用量审计（用户/种类/时间）、举报处理（状态）、概念（名称/分类）、条目（分类）、分类（名称）、调用明细（时间/场景/状态/模型/用户）——逐个点一遍，结果条数随筛选变化。
- **AC-010 举报页默认只看待处理**：进入举报页默认只显示待处理，切「全部」才看到已下架。
- **AC-011 调用明细分页可用**：能翻到第 2 页，每页条数可切换；不再固定 50 条。
- **AC-012 时间区间可用**：调用明细与调用概览都能从"近 7 天"切到"今天"或"近 1 小时"，切完后汇总数字跟着变。
- **AC-013 无原生下拉**：管理端源码里不再有 `<select`。
- **AC-014 总览有运营数字**：总览显示账号数、近 7 天调用次数、近 7 天扣分合计、待处理举报数，且都能点进去。
- **AC-015 不泄露口令**：用户列表与详情的响应体里不含 `password_hash`（用真实响应核对）。
## 阶段 B 的验收

**2026-10-21 用户追加批准**（原话「可以的继续做吧」），以下十项生效。

- **AC-016 步骤能看参数与返回**：调用明细里点开某一步，能看到工具入参 JSON 与返回预览；超 1000 / 500 字符时标明原长。
- **AC-017 步骤有首字**：LLM 步显示 `ttft_ms` 而不是「—」；库里该行非 NULL。
- **AC-018 截断真的生效**：入参与返回在库里长度有上限，不是全文。
- **AC-019 原有能力不退化**：`ai_run_spans` 的列仍显示，`AiTelemetryIntegrationTest` 仍绿。
- **AC-020 能看到完整请求与响应**：展开某一步能看到送上游的完整 messages 与模型返回的完整 body（JSON 美化）。
- **AC-021 payload 保留期独立**：30 天，与 spans 的 90 天分开清理；只删过期载荷，spans 与 runs 不动。
- **AC-022 开关有效**：`payloadEnabled` 关掉后不写库，页面显示「本次未记录请求体与响应体（采集已停用）」。
- **AC-023 超限不静默丢**：超 1MB 时存带字节数与 `truncated` 标记的占位记录。
- **AC-024 密钥不入库**：`PayloadJson` 只取白名单字段；用带真实 API Key 的 `GenerateOptions` 跑一遍，序列化结果里搜不到该串。
- **AC-025 注销级联**：注销后 `ai_run_payloads` 里这个人的行归零，别人的不受影响。
## 假设

- 「用户管理」指**平台的账号**，不是身份/画像（WORK-010 的身份是另一个维度）。
- 「AI 消耗」以积分流水与调用记录两处呈现，不新造一套计费口径。
- 「已用积分」取积分流水里消耗类记录的合计（`ai_credit_ledger` 的负向部分），**不取 `ai_runs.credits` 累加**——后者会漏掉精简那一路（那一路未必有 run 行，但一定有流水行）。两处口径若不一致，以流水为准。
- 图表：**不引入图表库**。new-api 的密度来自列多、筛选多、汇总多，不是来自图；调用概览的四个排行用 CSS 条形保持现状即可。若实现后觉得确实缺图，再单开一轮。
