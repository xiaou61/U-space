# 第三方登录与账号绑定需求

## 本项状态与本轮变化

- **2026-10-23 建项起草（draft）**。用户原话：「我们目前的这个登录方式都有哪些呢？其实我想新开一个 work 仔细优化一下这个登录方式，支持更多，比如说 GitHub qq 等等」→ 讨论资质门槛后裁决：「暂时就 GitHub gitee 这俩个吧，给我新建一个 work 项目吧先。开始吧。」
- 本文件只描述期望行为与边界。表结构、端点形状、状态防伪等实现细节放在 proposal（需求批准后创建）。
- **尚未签署，不得实施**。理由不是流程洁癖：`## 待确认问题` 里有一条会改变交付边界（桌面端回调），在它定下来之前，任务计划会建在流沙上。

## 已确认事实

### 现有登录方式（2026-10-23 读码）

| 项 | 事实 |
| --- | --- |
| 唯一入口 | `POST /api/v1/auth/login`，`identifier` 同时认用户名与邮箱，配 `password` |
| 注册 | `POST /api/v1/auth/register`，需要 `username + email + password + 邮箱验证码`；发验证码前先过图形验证码 |
| 令牌 | access 是 15 分钟 JWT（无状态），refresh 是 14 天随机串 + 状态表（轮换 + 整链吊销 + 重放检测） |
| 找回密码 | **不存在**（WORK-003 裁决"不做"），因此忘掉密码即永久锁死 |
| 第三方登录 | **零**。全仓无 OAuth 客户端依赖、无 `provider` 相关表或字段 |

### 受影响的既有实现（改之前必须一起改的地方）

| 位置 | 现状 | 为什么会被本项撞到 |
| --- | --- | --- |
| `users` 表 | `username` / `email` / `password_hash` **全部 NOT NULL**，且 `email` 有唯一索引 | 第三方用户可能没有邮箱、也可能没有密码 |
| `LoginService` | 直接 `passwordHasher.matches` | 无密码账号不能进密码登录路径 |
| `AccountDeletionService` | **要求密码确认**才允许注销 | 第三方注册的用户永远注销不了自己的账号——这是本项必然暴露的既有缺陷 |
| `AuthTokens.UserView` | `email` 为非空 `String` | 邮箱可空后对外视图与契约都要放宽 |
| `api-shape.json` | login / register / refresh 三条契约含 `data.user.email: string` | 三条契约都要重录 |
| 管理端用户列表 | 展示 email 列 | 要能显示"无邮箱"而不是空白或 `null` |
| 桌面壳 | 从 `http://127.0.0.1:<端口>` 加载页面，无自定义协议 | 远端回调页落在服务器上，令牌进不了应用 |

### 平台资质（2026-10-23 核实，决定范围的那一条）

| 平台 | 个人可用 | 是否需要 ICP 备案 | 审核 |
| --- | --- | --- | --- |
| GitHub | 是 | 否 | 无审核，创建即用；官方文档允许最多 10 个回调地址，loopback 允许 http |
| Gitee | 是 | 否 | 无审核，创建即用；回调地址按完整字符串精确匹配 |
| QQ 互联 | 是 | **是**（网站地址与回调地址都必须已备案） | 约 1 天 |
| 新浪微博 | 是 | **是** | 数个工作日 |
| 微信网站应用 | **否**（需企业营业执照） | — | — |

## 用户决定

- **2026-10-23 范围只做 GitHub 与 Gitee**。原话「暂时就 GitHub gitee 这俩个吧」。QQ / 微博 / 微信不在本期，原因是它们卡在 ICP 备案上，而备案周期不由本项目控制。
- **本期不启动备案**。这意味着 QQ 在此之前不是"难做"而是无法提交审核。
- **本项作为独立工作项建项**，不并入 WORK-003。
- **2026-10-23 桌面端回调取路 ②**：注册 `paideia://` 自定义协议由桌面壳接管回调，桌面端与 Web 端都支持第三方登录。用户回复「可以的 签署一下吧，然后在新的 worktree 里面开始制作就可以了」，按推荐方案定案。代价是桌面壳要加 `setAsDefaultProtocolClient` 与一次协议唤起处理（约 40 行），收益是不用手工复制握手码。
- **2026-10-23 Q3 取默认**：平台昵称生成站内用户名冲突时加数字后缀，并允许用户后续自行修改。用户同一条回复未反对默认方案。

## 实现选择

以下由 Agent 依据已批准边界与仓库既有模式选定，记录理由；它们不替代用户对产品范围的决定。

- **不引入 `spring-boot-starter-oauth2-client`**。它是围绕 `HttpSessionOAuth2AuthorizedClientRepository` 设计的，而本项目无状态、无 Cookie、纯 Bearer。用它要么被打回会话 cookie（桌面端直接失效），要么全程与之对抗。手写一个通用授权码客户端规模在百余行，出站 HTTP 沿用仓库已有的 JDK `HttpClient` 写法（`DigestHttp` 同一路数）。
- **`state` 放 `ExpiringStore`**（一次性、5 分钟、消费即删），不引入 cookie。现有 `ExpiringStore` 已被图形验证码、邮箱验证码与限流共用，天花板相同（进程内，多实例不可用）——这一点随本项记入已知限制，不新增。
- **不自动按邮箱合并账号**。GitHub 返回值里可能有已验证邮箱，QQ 类的拿不住；自动合并是账号劫持的经典入口。走"先登录已有账号，再手动绑定"。
- **第三方带来的昵称与头像只作为首次建议值**，登录成功后不再回写，否则用户改过的昵称会被外部平台覆盖。
- **来源不写进 `role`**。`role` 只表示能做什么。需要统计注册渠道时用独立的可空列，不参与任何权限判定（与 WORK-010 的「身份不是角色」同一条护栏）。

## 目标

- 登录页可以不再只有用户名密码：支持 GitHub 与 Gitee 授权登录，新用户首次授权即建号。
- 一个账号可以绑定多种登录方式，并在同一个页面里看到与解除绑定。
- 第三方注册用户的账号生命周期与密码用户**完全一致**——尤其"能注销"。
- 加第三个平台（QQ）时只增加配置与一个枚举值，不改表结构、不改登录主链路。

## 非目标

- **不做 QQ / 微博 / 微信**。升级触发条件：域名完成 ICP 备案（QQ、微博），或具备企业主体（微信）。
- **不做邮箱验证码登录与找回密码**。它在本轮讨论中被提为更该先做的一项（覆盖全部用户、零备案），但用户未采纳进本期范围。独立成项时再评估。
- **不做第三方账号的邮箱自动合并**（见实现选择）。
- **不做第三方资料持续同步**（昵称、头像、关注列表）。
- **不引入聚合登录/免签 API 类中间服务**。它把凭据边界从平台转移到不知名第三方，且可随时下线。
- 不改 refresh 轮换、JWT 有效期与积分/计费规则。

## 功能需求

- **REQ-001** 登录页提供 GitHub 与 Gitee 两个入口；点击后跳转到对应平台的授权页，授权完成后回到本站并处于已登录状态。
- **REQ-002** 首次通过某平台授权的用户自动建号，不需要先填表单；建号时若平台提供了可用昵称，用它生成一个不与他人冲突的站内用户名。
- **REQ-003** 已登录用户可以在账号设置里绑定新的第三方登录方式，也可以解除绑定。
- **REQ-004** 解除绑定有一个硬约束：**解绑后必须仍存在至少一种可用登录方式**，否则拒绝并说明原因。
- **REQ-005** 账号设置页列出当前账号已绑定的登录方式，并标出哪一种是"没有设密码"的那个。
- **REQ-006** 第三方注册的用户可以注销账号，确认方式不依赖密码。
- **REQ-007** 平台不支持、或用户拒绝授权、或授权码已失效时，回到登录页并给出可读的失败提示，不泄露内部错误。
- **REQ-008** 平台侧凭据（Client ID / Secret）只从服务端配置读取，不进入仓库任何被跟踪文件，也不下发到浏览器。
- **REQ-009** 新增平台只需增加配置与枚举值：不新增表、不修改登录主链路的代码分支。
- **REQ-010** 桌面端产物同样支持第三方登录：授权在系统浏览器完成后，通过 `paideia://` 协议唤起应用并落到已登录状态；协议被恶意页面伪造唤起时不得产生登录态。

## 质量要求

- **安全**：授权回调必须校验 `state` 且一次性；回调端点不接受任何可以篡改登录结果的入参；失败信息不区分"这个第三方 id 已绑定别人"与其它原因（避免账号枚举）。
- **数据**：既有密码用户的登录、注册、刷新、注销行为**逐条不变**；对既有数据零迁移风险（`users` 三列由 NOT NULL 改为可空是收缩性变更）。
- **可访问性**：第三方按钮是真正的按钮/链接，键盘可达，有可读标签，深浅色主题下对比度达标。
- **可观测**：第三方登录的成功与失败要能在服务端日志里区分平台，但**不记录授权码、access token 或任何平台令牌**。

## 约束与依赖

- `WORK-003` 的既有裁决继续有效：整端登录门、refresh 轮换、注销硬删不可恢复。
- 项目规则：凭据不进仓库；管理端写接口必须自行声明 `hasRole("ADMIN")` 且顺序在前；迁移文件名用 14 位时间戳。
- 本项**没有硬依赖**（`WORK-003` 已完成）。

## 验收标准

- **AC-001** 未登录用户点 GitHub 登录，授权完成后回到站内且显示已登录；数据库中该用户有一行 `user_identities` 记录，`provider = github`。
- **AC-002** 同一流程对 Gitee 成立。
- **AC-003** 首次授权建出的账号，其用户名唯一且非空；重复授权同一平台同一账号时**不新建账号**，仍是同一个 `user_id`。
- **AC-004** 已登录用户绑定 GitHub 后，账号设置页显示两条绑定；解除后剩一条。
- **AC-005** 只有一个绑定且未设密码时尝试解除，接口拒绝并给出可读原因，绑定数不变。
- **AC-006** 通过第三方注册（`password_hash` 为空）的用户能完成注销，级联删除与密码用户一致。
- **AC-007** 伪造或重放 `state` 的回调被拒绝，不产生任何登录态。
- **AC-008** 既有密码用户的登录、注册、refresh、注销四类集成测试全部通过且断言未放宽。
- **AC-009** 响应中不出现 Client Secret；`application.yml` 之外的被跟踪文件里不含任何平台凭据。
- **AC-010** 管理端用户列表对无邮箱账号显示为明确的"无邮箱"，而不是空白或字符串 `null`。
- **AC-011** 桌面产物中完成 GitHub 授权后，应用被唤起并显示已登录；手工构造 `paideia://` 链接（不含有效一次性凭据）不会产生登录态。

## 假设

- GitHub 与 Gitee 都能返回一个稳定、长期不变的平台内用户 id（GitHub 的数值 id、Gitee 的 `id`）。绑定关系以它为准，**不以昵称或邮箱为准**。
- 线上当前是 `http://<公网IP>:8081`、无域名无 HTTPS。GitHub 官方文档只明文承诺 loopback 允许 http，对公网 IP **没有明文**——需要实际建一个应用打一发才能确认回调能否登记成功。若不成功，则第三方登录只能在本地开发环境验证，生产不可用，这会改变本项的价值判断。
