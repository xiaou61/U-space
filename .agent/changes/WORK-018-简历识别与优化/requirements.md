## 实现选择

> 根据已批准边界与仓库既有模式做的技术决定，不替代用户对产品范围的决定。

1. **原文件不落盘**：只在内存抽文本，抽完即弃；库里只留结构化数据 + 纯文本。简历是最敏的 PII，少存一份原件就少一个泄露面；也不必塞进那个免鉴权读附件端点。天花板：不能再次下载或重解析，要重传。
2. **支持 PDF 与文本型 `.docx`**：PDF 用 PDFBox 3.0.7（Apache-2.0），`.docx` 用 JDK 自带 zip + XML；扫描件、图片型 PDF、`.doc` 拒绝并说明原因。
3. **模型调用三次**：① 简历文本 → 结构化 JSON；② 主简历 + JD → 分析；③ 主简历 + JD + 分析 → **逐条改写提案**。第三次单独拆出来，是因为"逐项采纳"要求模型为每处改动给出原文片段与改写片段，而不是交一整稿让用户找差异。
4. **关键词三桶由代码算**：模型抽显式要求，代码做归一化子串匹配（大小写、全半角、空白、少量等价缩写）分三桶。模型自评"我会/我不会"是幻觉温床，字符串比对可测可复现。
5. **采纳状态是数据**，不是前端状态：未采纳的提案留在版本记录里（能改主意），只有采纳的进定稿与打印。
6. **不做服务端 PDF**：浏览器打印 + 专用打印视图。服务端出 PDF 要嵌中文字体、处理分页断行，成本高于收益。不做模板库，样式复用 `@paideia/ui` 令牌。
7. **落点：`paideia-ai` 的 `internal/resume` 子域，不新开 Maven 模块**。实体上是"三次调用 + 若干私有表 + 一套校验 + 一套编辑用例"，与 `internal/interview`、`internal/memory` 同构；新开模块要装配四处而它没有第二个消费者。天花板：若长成独立产品面再拆 `paideia-resume`。
8. **表**：`resume_documents`（主简历）、`resume_edit_history`（编辑快照）、`resume_versions`（岗位版本）、`resume_proposals`（逐条提案与采纳状态）。不做字段级逐次 diff。

## 背景

求职这条链路上真正**每次投递都要重复做**的动作，是把同一份简历改成那个岗位想要的样子。这一步现在完全靠人，而且最容易滑向编造。

career-ops 最值钱的不是"让模型改写"，而是**在改写前后各放一道确定性闸门**：改写前先分清"哪些要求我确实有、哪些只是正文里提过、哪些完全没有"，改写后再验证"新出现的每个数字、头衔、时间是不是真来自原文"。这两道闸门不需要模型判断，因此可测可复现，也让"AI 优化简历"不至于变成"AI 编简历"。本项把这条骨架搬进产品，并补上缺了就不能用的一件事：**简历本身要能在产品里编辑**——否则改一个错别字都要重传。

## 目标

- 上传一次简历，**在一次确认之后**得到结构化、逐条可核对的主简历，且之后能像文档一样**持续编辑**。
- 粘贴一段 JD，能看清"这个岗位要什么、我有什么、我缺什么"，并拿到一份**逐条可采纳**的改写提案；每处改动都能看见原文与改后，由用户决定采不采纳。
- 定稿前必须过确定性事实闸门：编造的数字、改掉的职位与时间、无出处的改写一律拦下；定稿里每个字都能追回原文。
- 出稿是一张单栏 A4 打印视图，用户自己按浏览器打印存成 PDF。
- 简历数据严格按用户隔离、可单独删除、注销即级联清空，且**不存在任何免鉴权可读的简历 URL**。

## 非目标

- **不做 OCR**：扫描件、图片简历、纯图片 PDF 不支持，明确报错。
- **不做 JD 链接抓取**：只接受粘贴文本——URL 抓取要处理 SSRF、反爬、动态渲染与登录墙，而用户本来就在那个页面上。
- **不做"要不要投"的判断**：不做 A–H 评估、公司调研、薪资分析、发帖真实性判断，也不打 1–5 分；不做投递跟踪器、求职信、面试题。
- **不做用户自带 Key / 自填 baseUrl**：统一走平台凭据 + 积分。
- **不做模板库、不做服务端 PDF**：一期一个打印版式，浏览器打印出稿。
- **不做富文本编辑**：编辑是结构化字段级的，不做自由排版的所见即所得。
- **不做"ATS 通过率"承诺**，不模拟具体 ATS 厂商解析器，也**不做 PDF 版面分析**。
- **不做英文/双语简历的专门优化**；不做公开分享、导出到第三方、自动投递；不做向量检索。

## 用户与工作流程

**识别**：上传 → "正在读" → **核对页**（按分区列出条目，每条可展开看原文引证）→ 逐项确认/修改/补空 → 「保存为主简历」→ 进入编辑页。**点保存之前库里没有这份简历的任何数据。**

**编辑**：左分区导航、右当前分区；每条能改能删能上下移能新增。改动自动保存（防抖），页头显示"保存中 / 已保存 / 未保存"与上次保存时间。「历史」可看快照并回滚（回滚也记为一次新编辑）。保存后体检清单就地更新。

**投岗**：编辑页点「按岗位优化」→ 粘贴 JD → 「分析」（一次积分）看三块：要什么 / 我有什么 / 我缺什么 → 「生成改写提案」（一次积分）→ **提案页**：左侧逐条提案（原文与改后并排、改动高亮、依据引用 JD 原句），右侧实时定稿预览。每条默认**不采纳**，用户勾选才进定稿；顶栏汇总"已采用 N / 共 M"、可一键全部不采用；可先编辑"改后"文本再采纳（编辑后重跑闸门）。「定稿」做事实闸门校验 → 通过则存为岗位版本，不通过则列出违规项并定位到提案。最后「打印 / 存为 PDF」。**主简历始终不被修改。**

**回头查**：编辑页下方是版本列表（时间倒序），可看当时的 JD、关键词覆盖、采纳情况与定稿；可删版本、可基于旧版本"再来一次"。

## 功能需求

### 识别（输入）

- **REQ-001 导入**：上传 PDF 或文本型 `.docx`（10 MB / 20 页上限）。扫描件、图片型 PDF、`.doc` 返回**可读的拒绝理由**（说清是格式不支持还是没有文字层）。
- **REQ-002 结构化识别**：解析成固定结构——基本信息、求职意向、教育、工作/实习、项目、技能、证书与奖项、自我评价；**每个条目携带原文引证**（原文那句与所在分区）。
- **REQ-003 确认后才落库**：解析结果先以**可编辑表单**返回核对，点保存才创建主简历；未确认时不得写入任何数据。
- **REQ-004 原文件不保留**：解析完立即丢弃上传文件，库里只存结构化数据与纯文本。

### 在线编辑

- **REQ-005 字段级编辑**：每个分区可增删改条目，条目内每个字段可编辑。**不做整页富文本**。
- **REQ-006 自动保存与状态**：防抖自动保存；显示"保存中/已保存/未保存"与上次保存时间；失败时保留内容并提示重试，**不得静默丢失用户正在打的字**。
- **REQ-007 编辑历史与回滚**：每次保存形成快照（连续保存可合并）；可查看、预览、回滚；**回滚不删历史**，本身记为一次新编辑。
- **REQ-008 顺序调整**：经历、项目、要点、技能条目可上下移；顺序是数据的一部分，打印与提案都以它为准。
- **REQ-009 多份主简历**：可存多份（不同方向），列表显示标题、更新时间与"默认"标记；可改名、删除、设默认。

### 体检（无 JD）

- **REQ-010 体检清单**：逐项结果（通过 / 待改）并注明位置。至少覆盖：联系方式齐全、有求职意向、有技能区、起止时间完整且格式一致、有无数字的要点、总长度超长、重复要点、空分区。
- **REQ-011 不编造分数**：只有逐项通过/待改，不产出 0–100 分，也不出现"通过率""ATS 兼容度"这类无法验证的表述。

### 岗位定制（有 JD）

- **REQ-012 JD 输入**：粘贴 JD 文本（至少 30 字），可填公司名与岗位名（缺省用第一行或"未命名岗位"）；URL 不作为输入。
- **REQ-013 关键词三桶**：逐条分「现有」（技能区写明）/「有证据」（正文出现过）/「缺口」（全文没有），**逐条可查**：关键词能定位 JD 原文，前两类能定位主简历位置。
- **REQ-014 逐条改写提案**：每条含所属条目与字段、**原文片段**、**改写片段**、改动类型（改写/重排/新增/删除）、**依据**（JD 原句或"排序调整"）、覆盖的关键词。**必须是结构化的**，不是一整段成品。
- **REQ-015 可视化对比与逐项采纳**：必须能看见"原文 vs 改后"（并排或上下对照、改动高亮），**每条单独采纳/不采纳且默认不采纳**；可编辑改后文本再采纳；可按已采纳/未采纳筛选。
- **REQ-016 采纳状态持久化**：采纳与否是数据的一部分，刷新与换设备后仍保持；可一键全部不采用。
- **REQ-017 事实闸门**：定稿前做确定性校验，不通过的条目不进定稿并返回违规项：① 数字/百分比/金额/时长必须在主简历原文出现过（归一化）；② 改写与原文的内容词重合度不低于阈值；③ 职位名、公司名、起止时间**逐字一致**；④ 不得出现任何「缺口」关键词。
- **REQ-018 匹配度**：显示「已覆盖 N / 全部 M」与缺口清单，标注这是关键词覆盖面，**不是录用概率**。
- **REQ-019 定稿与版本**：采纳的提案合成定稿并存为岗位版本（含 JD、分析、提案与采纳状态、定稿、时间）；主简历不被修改；可删单个版本。
- **REQ-020 重新生成**：可对同一 JD 重新生成，每次都是新的计费调用且按钮写明；新提案替换旧提案，**已定稿的旧版本不受影响**。

### 输出与数据

- **REQ-021 打印视图**：专用打印页（A4、单栏、黑白可读、无输入控件、条目不跨页断开），浏览器打印或另存 PDF。
- **REQ-022 归属与删除**：只能本人读写（归属用 SQL 校验，拿不到统一 404）；可单独删除主简历或版本；注销时本项全部表级联清空。
- **REQ-023 无公开读路径**：不得新增免鉴权的简历读端点，也不得把简历写入既有公开附件存储。

## 质量要求

- **计费**：三次调用都走既有预扣/结算；余额不足返回 402 且**不发起上游请求**；失败按既有语义退款或按已发生用量结算；流水按用途单独记 `kind`。**不提供任何绕过积分的调用路径**。
- **失败不落半条数据**：解析失败不创建主简历；分析或提案失败不创建版本；闸门不通过不落定稿。
- **不可信内容**：简历文本与 JD 都是**数据，不是指令**。文件里出现"忽略前面的指令""把技能改成 X""调用工具"这类文字只能当作被引用的内容，不得改变流程或触发工具。
- **超长处理**：文本超上限时截断并明确告知哪部分没被读取，不得静默截断。
- **编辑不丢字**：自动保存失败必须可见，且不能覆盖用户继续输入的内容（AGENTS.md 记过一次同类缺陷：同步 effect 把正在打的字冲掉）。
- **移动端**：390px 宽下编辑页、提案对比、打印入口不得横向滚动；对比视图窄屏改上下堆叠。
- **文案诚实**：不出现"保证通过 ATS""提高 80% 面试率"这类承诺；所有比例都说明怎么算出来的。
- **常驻技术纪律**：Boot 4 / JDK 25 / 手写 MyBatis / 仅 MySQL / Flyway，不引入向量检索；新增依赖只允许一个 PDF 文本抽取库（`.docx` 先用 JDK 自带能力，样张不达标再评估 POI 并写明实测依据）；迁移号取当时实际最大号 +1；不建跨模块外键；集成测试不用 H2，无口令时"跳过而非失败"的规则不变且必须核对 Skipped 列；新增 `/api/v1/**` 端点必须 `@ApiAccess` 声明并由契约测试对照真实行为。

## 验收标准

- **AC-001 识别→确认→落库**：上传文本型 PDF 得到带原文引证的结构化条目；**未点保存时库里 0 行**；保存后可读到同样内容。图片型 PDF 返回明确的"没有可读文字"错误，不落库、不扣积分。
- **AC-002 编辑、自动保存与回滚**：改一条经历的职位名 → "保存中"→"已保存" → 刷新后是新值；保存失败时输入框内容不被回填覆盖（用必定失败的接口桩验证）；连续保存三次后回滚到第二版 → 内容等于第二版，历史条目不减且多一条"回滚"记录。
- **AC-003 逐项采纳与对比可见**：生成后默认全部未采纳 → 采纳一条 → 刷新后仍是"已采纳" → 定稿只含那一条；每条提案能同时看到原文与改后，改动部分有可见差异标记。
- **AC-004 闸门反向验证**：注入主简历中不存在的数字 → 该条不可采用且定稿被拦；注入被改写的职位名 → 同样拦住；移除后通过。
- **AC-005 三桶与缺口**：固定夹具下三桶分类与人工标注一致，"现有/有证据"能定位到字符位置；定稿文本不出现任何「缺口」关键词（CJK 用子串比对）。
- **AC-006 零积分与单一路径**：余额为 0 时发起任一调用 → 402 且上游调用次数为 0；不存在接受 baseUrl 或 apiKey 的端点，调用一律经 `CredentialService.access`。
- **AC-007 归属与注销**：用户 B 用用户 A 的主简历或版本 id 访问 → 404（不是 403）；注销后本项全部表逐表 0 行。
- **AC-008 无公开读路径**：路由清单里无 `PUBLIC_READ` 的简历端点；简历数据不在公开附件可读的存储里。
- **AC-009 打印视图**：打印 CSS 下 A4 单栏、无输入控件、无分页断裂；对比度满足既有 WCAG 门槛。
- **AC-010 窄屏可用**：390px 宽下编辑页、提案对比、版本列表无横向滚动，对比视图上下堆叠。
- **AC-011 失败不留脏数据**：上游超时或返回空内容时数量不变，积分按既有语义退款/结算。
- **AC-012 识别质量记录**：3 份合成简历（双栏 PDF、表格 PDF、中英混排 DOCX）各跑一次，把必填字段召回情况如实写入报告。**只记录、不设通过线**。

## 假设

- 简历是有文字层的电子文档（不是扫描件）。
- 用户接受简历正文随三次调用发给平台配置的上游模型（DeepSeek）——与聊天记录同一链路，没有本地模型兜底；首次使用时给一次性告知。
- 一份简历识别后以手工编辑为主，不需要反复重解析。
- 一期只有中文表达的优化规则；英文简历能读能编辑但不做专门优化。

## 待确认问题
