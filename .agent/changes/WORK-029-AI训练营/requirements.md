### 调研事实

见 [`research.md`](research.md) 第二、三节。三条影响设计的结论：

1. 同类产品最大的工程技术问题是**模型编造不存在的学习资源**；本项目用「计划项必须锚定真实条目 id」从结构上消除。
2. 一个人十几道题的数据量**估不出题目参数**，CAT / IRT / BKT 都不成立；可行且诚实的是**分难度档出题 + 平行卷复测**。
3. 1/2/4/7/15/30 天间隔复习在别的产品里要自己写，**本项目已经有了**（1/3/7/21），不要造第二套。

## 实现选择

以下由 Agent 依既有边界与仓库模式决定，签字时可整体否决或逐条改：

1. **AI 只出题，计划由纯函数算。** 模型写计划会编造条目、且不可复现（同输入两次结果不同），无法对比也无法测试。计划锚定 `knowledge_entries` 真实 id，同样输入必得同样计划。
2. **不做自适应出题，改分档平行卷。** 每题带难度（易/中/难），每个主题按固定档位分布出题；复测用同分布的另一套题，于是「诊断 vs 结营」可比。
3. **对错由服务端判定，薄弱点由数字聚合。** 模型给选项与答案，服务端比对；薄弱点按「该主题错几题 / 共几题」算。沿用 `ResumeKeywordClassifier` 三桶那条纪律：不让模型自评「他会不会」。
4. **复用既有复习阶梯与通过判据。** 计划里的「复习」任务读 `review_due_at`；「达标」用 `passRatio ≥ 0.8` 同一口径。不新建调度器。
5. **给掌握度加第四路证据。** 训练营的诊断/复测得分按概念聚合后喂进 `ConceptMastery.compute` 的证据列表，图谱随之变化。这是本项「有用」的兑现点。
6. **每天一个时间预算，按天数推导**：3 天营 90 分钟/天，7 天营 60 分钟/天。不提供可调项（没人会去调，且多一个配置就多一条要测的路径）。
7. **只做客观题（单选 4 选 1）。** 主观题评分不稳定，而 `learning_progress` 的「讲一遍」需求走既有助手即可。
8. **每个用户最多 3 个进行中的营。** 限制 AI 花费与表行数，避免刷接口刷出账。
9. **营不是定时任务。** 全部由用户点击驱动，不需要调度、不需要推送；「第几天」只是展示用的序号。

## 背景

平台现在有两组彼此不通的能力：

- **能读的**：知识库条目、学习轨道、八股文。`learning_progress` 记录了每站做没做题、得几分、什么时候该复习。`ConceptGraphService` 把三路证据聚合成一张掌握度图谱。
- **能改的**：简历（WORK-018）。它能告诉你「我写了什么」，还能按 JD 告诉你「我缺哪些关键词」。

中间缺的那一步是：**「我到底会不会」**。

现在的用户路径是「看到简历 → 自己猜哪里弱 → 在知识库里随便找一篇看」。他既没有验证过自己会不会，也没有一条能走完的路。图谱能显示「哪些概念弱」，但图谱的弱项靠浏览、自评和站内小测三路信号——**没做过站内小测的概念，图上就是灰的**。

本项补的就是这段：**用简历决定考什么，用考卷测出真实水平，用测出的差给自己排一条几天能走完的路，走完再测一次看有没有变好。**

## 目标

- 用户能在一份简历上开一个训练营，选 3 天或 7 天。
- 系统按这份简历的技能画像出一套诊断卷，**答案由服务端判**，立刻给出**按主题的**对错分布（不是总分）。
- 薄弱点、以及每天做什么，由这套作答结果**算出来**，每一项都指向库里真实存在、点得进去的内容。
- 走完计划后能测第二次（同主题、同难度分布、不同题目），并**把两次结果并排显示**。
- 训练营的成绩**进入掌握度**：做完一个营，图谱上那些概念的颜色会变。
- 全程不需要管理员介入；管理员已有的「概念」维护面不需要改。

## 非目标

- **不做语音面试、不做多轮对话式测评、不做情绪分析**。这些属于 WORK-010 的面试面，本项是测评与计划，不是面试。
- **不做自适应出题（CAT）、不做 IRT/BKT**。样本量不够，做了就是把噪声包装成科学。理由见 research.md 第 2.7 节。
- **不做主观题 AI 批改**。需要「讲一遍」时用既有助手，不新增评分路径。
- **不做向量检索、不做相似题推荐**。项目级约束本期仍生效。
- **不做每日提醒、推送、邮件、日历导出**。
- **不把生成的题目写进知识库**。题目只属于训练营，不产生公共内容——未经外部校验的题不该污染题库。
- **不做计划的手工编辑与拖拽排序**。一期只读 + 勾选完成；排得不合意就重新生成。
- **不做排行榜、积分奖励、徽章、等级、跨用户对比**。
- **不做「上岸率」「面试通过率」这类承诺**，也不出 0–100 的能力总分。
- **不改简历的任何数据**，本项对简历只读。
- **不自动创建概念**。概念是管理员维护的公共内容，模型只在已有概念名里挑，挑不上就退成自由主题。

## 用户与工作流程

**开营**：简历详情页点「用它开训练营」→ 选 3 天或 7 天 → 「生成诊断卷」（一次计费，按钮上写明）→ 得到 12 道（3 天）或 18 道（7 天）单选题。

**作答**：一题一屏，显示「第 3 / 12 题」，可回上一题，全部答完才能交卷。交卷后立即出分，不需要等。

**看诊断**：结果页按主题分组，每个主题显示「答对 2 / 共 3 题」与三个难度档各自的对错。**不出现总分、不出现百分制能力值。** 明显的弱项带一句人话（「这个主题 3 题错 3 题，而且难档一题没对」）。

**生成计划**：点「排一个 3 天计划」（**免费**，纯计算）→ 得到第 1/2/3 天各若干项，每项写明：做什么、大概几分钟、为什么排它。点任意一项直接进对应条目；做完回来勾掉。

**计划里可能出现的四种项**：
- **读**：打开一个真实条目的正文；
- **做**：打开一个条目里的练习块，做完分数自动记进学习记录；
- **复习**：某个概念到了复习期（读 `review_due_at`）；
- **缺口**：这个概念还没有任何内容——如实写「暂时没有可读的内容」，并给一个「让助手讲一讲」的入口（开既有助手，带好这句话）。

**结营复测**：计划走完（或用户想提前验）→ 点「结营测评」（一次计费）→ 同一批主题、同样的难度分布、全新的题目 → 出结果页，**左右并排显示诊断与复测**，逐主题给「进步 / 持平 / 退步」。

**回看**：营列表显示每个营的天数、创建时间、诊断与复测的完成情况；可删除营（连带题目与作答一起删）。

## 功能需求

### 开营与出卷

- **REQ-001 从简历开营**：只能从**本人的**一份简历开营；开营时把该简历的 id 与标题记下来，之后简历被改不影响已开的营（营不回头读简历）。
- **REQ-002 天数只有两种**：3 天或 7 天。3 天营出 12 题，7 天营出 18 题。
- **REQ-003 技能画像不送原文**：交给模型的是从简历**提炼出的技能词**（技能区的条目 + 项目/经历正文里的技术词），**不发送姓名、电话、邮箱、公司名、学校名与整段原文**。
- **REQ-004 画像为空则拒绝**：从简历里提炼不出任何技能词时，不开营、不扣积分，并提示去把技能区补齐（给出简历体检的入口）。
- **REQ-005 出题要求**：单选题，每题四个互不相同的选项、恰好一个正确答案、附一段解析。题干与解析都不得包含简历里的个人身份信息。
- **REQ-006 题目带三样标签**：所属主题（自由文本或已有概念名）、难度（易 / 中 / 难）、概念（可选，只能取已有概念名）。
- **REQ-007 结构校验与丢弃**：选项个数不对、答案下标越界、选项重复、题干过短或过长、解析缺失、解析与正确选项对不上——任一条命中即**丢弃该题**，并记录丢了几道。**丢弃后剩余题目仍可用**，营照常创建。
- **REQ-008 题量不足要说明**：有效题数少于目标题数的 80% 时，结果页明确写「本次只生成了 N 道题」（不静默少给，也不假装满额）。
- **REQ-009 主题覆盖**：每个主题至少 2 题、至多 4 题；难度分布为易 / 中 / 难各占约 1/3（整数取整，余数给中档）。
- **REQ-010 幂等与重来**：同一份简历可以开多个营；每个营独立。**重新生成题目会产生一个新营**，旧营及其作答保留不动。

### 作答与判定

- **REQ-011 交卷即出分**：全部答完后一次提交，服务端比对答案，立即返回结果；**没有「正在判卷」的等待态**。
- **REQ-012 判定在服务端**：请求体只带「第几题 + 选了第几个」，**不接受** `correct`、分数或任何判定结果。
- **REQ-013 不许提前看答案**：交卷前任何接口都不得返回 `answer_index` 与解析。
- **REQ-014 已交卷不可改**：同一份卷只能交一次；重复提交返回冲突，不改数据。
- **REQ-015 结果只有计数**：结果页只给「主题 × 难度 × 答对/共几题」，**不给总分、不给百分制、不给等级**。

### 薄弱点

- **REQ-016 弱项判据（三条任一命中）**：
  1. 该主题答对率低于 80%（与 `LearningProgressRules` 的通过口径一致）；或
  2. 该主题错题数 ≥ 2；或
  3. 该主题难档题全错。

  第 2 条的作用是**防止一道坏题把整个主题打成弱项**：一个主题有 4 道以上、只错 1 道时，答对率已经 ≥ 75%，不会被误判。**但题量为 2–3 道时，错 1 道仍会命中第 1 条**——这是刻意的：题量少时一道题就是 25–50% 的信息，不能忽略。所以「错一题不判弱」只在题量 ≥ 4 时成立，不属于无条件承诺。
- **REQ-017 强项也要显示**：达到 80% 以上的主题单独列出，标注「不用学」。理由是只显示弱项会让人一直觉得自己很差（调研里 Tail Villain 的同一结论）。
- **REQ-018 优先序**：`优先级 = (1 − 答对率) × 覆盖度`，其中覆盖度 = min(1, 该主题在简历里出现的区段数 / 3)。**模型的意见不参与排序**。「低信心 ≠ 高优先」：答对率已经接近 80% 的弱项排在有前置依赖的后面。
- **REQ-019 前置联动**：若某弱项概念有前置概念、且**前置也弱**，前置必须排在被依赖项之前（拓扑约束）。若前置**不弱**（用户已经会了），不加任务、不改顺序——不拿第一天去复习已经掌握的东西。

### 计划

- **REQ-020 计划是纯函数产物**：输入是弱项列表 + 载体条目 + 天数 + 每日预算，输出是每天的任务列表。**同样的输入必得同样的输出**，且不调用模型。
- **REQ-021 每项必须落到真实内容**：读/做/复习三类项都必须带一个**已发布**条目的 id 与标题；取不到就降级为「缺口」项，不得编造标题或链接。
- **REQ-022 每日预算**：3 天营每天 90 分钟、7 天营每天 60 分钟。任务是整块分配，不跨天切开。
- **REQ-023 不出现空白日**：任何一天都必须至少有一项；任务不够时分摊而不是让最后一天空着。
- **REQ-024 排不完要说实话**：任务装不下时，未排入的项单独列出并写「时间不够，还有 N 项没排进来」，不静默丢弃。
- **REQ-025 每项带一句理由**：理由由数字生成（例如「这个主题 3 题错 3 题；它的前置你已经掌握」），不由模型自由撰写。
- **REQ-026 首日先啃最弱**：第 1 天的第一项固定是答对率最低的主题——第 1 天动力最高，不该拿来做最容易的事。
- **REQ-027 计划可重排**：作答结果变化后（例如复测完）可以重新排一份计划；旧计划与其完成状态保留。
- **REQ-028 完成状态**：每一项可勾选完成/取消完成；状态刷新后保持。**计划本身不可手工编辑。**

### 复测

- **REQ-029 同主题同分布**：复测卷与诊断卷的主题集合、每主题题量、难度分布完全一致；**题干不得重复**（交卷过的题干作为「不要再出这些」的清单传给模型）。
- **REQ-030 并排对比**：结果页把诊断与复测按主题并排显示，逐主题给结论：复测答对率高于诊断 → 进步；相等 → 持平；低于 → 退步。
- **REQ-031 题量不一致要标注**：某主题两次题量不同（因为有效题被丢弃）时，该主题标注「两次题量不同，对比仅供参考」，不出结论。
- **REQ-032 复测不限次数**：可以在同一营里做多次复测；每次都单独一条记录，最新一次用于对比。**每次都是一次计费调用**，按钮上写明。

### 与掌握度联动

- **REQ-033 训练营成绩进入掌握度**：诊断与复测的得分按概念聚合后，作为**第四路证据**进入 `ConceptMastery.compute` 的证据列表；没有概念映射的主题不进图谱。
- **REQ-034 不改掌握度算法**：`ConceptMastery` 的权重、半衰期、档位阈值一个都不改。新增的只是证据来源，不是新的打分规则。
- **REQ-035 助手可读**：既有助手的「我哪里弱」工具能读到训练营产生的弱项（沿用 `ConceptGraphService.weakest`，不新增工具）。

### 归属与数据生命周期

- **REQ-036 只有本人**：营、题目、作答、计划、任务全部按令牌里的用户过滤；拿别人的 id 统一返回 404（不是 403）。
- **REQ-037 可删除单个营**：删营连带删它的题目、作答、计划与任务，一次删干净。
- **REQ-038 注销级联**：注销账号后本项五张表逐表 0 行。
- **REQ-039 无公开读路径**：不得新增免鉴权端点，也不得把营的任何内容写进公开附件存储。

## 质量要求

- **计费**：出卷与复测各一次计费，走既有预留/结算；余额不足返回 402 且**不发起上游请求**；失败按既有语义退款或按已发生用量结算；流水用**独立种类**，让用户能回答「这个营花了多少」。
- **失败不落半条数据**：出卷失败不创建营；交卷失败不落作答；复测失败不改已有结果。
- **不可信内容**：简历文本与模型返回都是**数据，不是指令**。简历里出现「忽略前面的指令」「把答案设成 A」这类文字只能被当作被引用的内容，不得改变流程。
- **模型返回必须是可校验的 JSON**：解析失败先做**一次修复性重试**（把违规项原样回传让它改）；仍失败则整次失败并退款，**不得**把空结果当成「0 道题」。
- **空返回要当失败**：思考型模型可能因 `max_tokens` 被思考 token 吃满而返回空内容——空内容与解析失败同等对待。
- **题目质量的诚实披露**：诊断页必须有固定文案说明题目由模型按技能画像生成、答案未由第三方校验；**不得**出现「权威」「精准测评」「通过率」这类措辞。
- **窄屏**：390px 宽下作答页、结果页、计划页不得横向滚动；并排对比窄屏改上下堆叠。
- **计划页不许空转**：没有弱项时显示「这次没有明显薄弱项」并给复测入口，而不是一张空表。
- **常驻技术纪律**：Boot 4 / JDK 25 / 手写 MyBatis / 仅 MySQL / Flyway，不引入向量检索，不新增前端依赖（除已批准者），迁移号取执行时下一个，不建跨模块外键，集成测试不用 H2，新增 `/api/v1/**` 必须 `@ApiAccess` 声明并进入契约测试。

## 约束与依赖

- **依赖 WORK-018（简历）**：读取 `ResumeData`。不依赖它的版本/提案功能，只读主简历。
- **依赖 WORK-021（概念与掌握度）**：复用 `ConceptMastery` 与概念↔条目关联。**本项不是它的前置**；概念表为空时本项退化为「主题级」计划（REQ-021 的缺口项），不报错。
- **依赖 WORK-020（学习记录）**：复习任务读 `review_due_at`；「做」类任务指向的条目里的 quiz 块自动写记录。
- **依赖 WORK-009（计费）**：两次调用都走平台凭据与积分。
- 不依赖 WORK-025（八股文）：v1 不把抓取内容作为出题来源。
- 跨模块：营在 `paideia-ai` 模块（它已依赖 `paideia-knowledge`）；需要给 `KnowledgeApi` 增加**读取概念载体条目**与**读取某一用户弱概念**两个方法。不得让 knowledge 反向依赖 ai。

## 验收标准

- **AC-001 开营到出卷**：从一份有技能区的简历开 3 天营 → 库里出现营与 12 道题（或按 REQ-008 说明实际题数）；题干里**不含**简历里的姓名、电话、邮箱；余额为 0 时返回 402 且上游调用次数为 0。
- **AC-002 画像为空被拒**：一份技能区为空且正文无技术词的简历开营 → 拒绝、不建营、不扣积分、提示指向简历体检。
- **AC-003 交卷判分**：全部正确的作答得到「每主题答对率 100%」且没有弱项；故意错 2 题得到对应主题的错题计数为 2。
- **AC-004 不能提前看答案**：交卷前调用获取题目的接口，返回体里没有 `answer_index` 与解析（用响应字段断言，不是人工看）。
- **AC-005 不能改判**：提交里带 `correct: true` 与伪造分数 → 服务端忽略并用自己的判定落库；同一卷提交两次，第二次返回冲突且作答行数不变。
- **AC-006 坏题被丢且不崩**：喂一组刻意违规的题目（选项 3 个、答案下标 9、选项重复、解析为空）→ 这些题不入库、被计数、有效题仍可用于开营。
- **AC-007 弱项判据**：一个 4 题主题错 1 题 → **不**判弱项；同主题错 2 题 → 判弱项；难档全错 → 判弱项；一个 2 题主题错 1 题 → 判弱项（题量少时不给豁免）。三条判据与题量豁免各自有用例。
- **AC-008 计划是纯函数**：同一弱项快照连续算两次，逐项相同；把弱项顺序打乱后再算，每天的项集合仍按优先级排列且**首个主题是最弱那个**。
- **AC-009 计划锚定真实内容**：计划里每一个读/做/复习项都能用它的 entryId 打开一个已发布条目；人为把一个载体条目下架后重排，该项变成「缺口」项而不是保留失效 id。
- **AC-010 预算与空白日**：3 天营每天任务分钟数之和不超过 90，且三天都至少有一项；弱项多于容量时出现「还有 N 项没排进来」。
- **AC-011 复测可比**：复测卷与诊断卷的主题集合与每主题题量一致，题干无重复（按题干指纹比对）；把这两条约束去掉后对应测试必须红。
- **AC-012 并排对比**：诊断某主题 1/3、复测 2/3 → 结果页该主题标记为「进步」；两次相等 → 「持平」；题量不一致的主题 → 「仅供参考」且不给结论。
- **AC-013 掌握度变化**：同一概念在诊断全错时图谱分数低于诊断全对时；连续算两次结果逐位相同（复用 WORK-021 的纯函数纪律）。
- **AC-014 归属与删除**：用户 B 用用户 A 的营 / 题目 / 计划 id 访问 → 404；删除营后题目、作答、计划、任务**逐表 0 行**。
- **AC-015 注销级联**：注销后本项五张表逐表 0 行。
- **AC-016 无公开读路径**：路由清单里没有本项的 `PUBLIC_READ` 端点。
- **AC-017 窄屏**：390px 宽下作答页、结果页、计划页无横向滚动；并排对比上下堆叠。
- **AC-018 失败不留脏数据**：上游超时或返回空内容时营数、题数、作答数均不变，积分按既有语义退款。

## 假设

- 模型能稳定按 JSON 契约返回单选题。**未验证**：本项目此前只做过简历的结构化输出，单选题质量与解析正确率**没有实测数据**。这是本项最大的未知，因此 REQ-007 的结构校验与 REQ-016 的「错一题不算弱项」是必须的兜底。
- `knowledge_entries.body` 的长度足以估算阅读时长（按 400 字/分钟）。**未实测**该系数是否贴近真实阅读速度；它只影响计划里的分钟数展示，不影响排序。
- 概念表可能为空。本项按「主题级」降级运行，这是已知缺口而非缺陷。
- 一个用户同时开的营不超过 3 个（REQ 里的上限），超出时拒绝并要求先删旧营。

## 待确认问题

- **Q1 出题数量**：3 天 12 题 / 7 天 18 题是否合适？题越多诊断越准，但一次调用越长、成本越高，而且 7 天营的人未必愿意做 18 题。
- **Q2 是否要「我不知道」选项**：调研里的 N.O.V.A. 把它当作一次 0 分作答并进错题本。本项一期没有选项，**跳过即视为未答**。要不要加？
- **Q3 首日先啃最弱**（REQ-026）：也有产品主张先做容易的建立信心。当前按「用户本人正在秋招、时间紧」选择先啃最弱，可否？
- **Q4 训练营是否要出现在学习页**：`/learn` 现在列的是轨道。营是加一张卡片，还是只从简历页进入？
- **Q5 复测时机**：现在是「随时可点」。要不要在计划走完后给出提示，或限制为至少隔一天（否则容易变成刷同一批记忆）？
