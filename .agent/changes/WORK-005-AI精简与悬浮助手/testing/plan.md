# AI 精简与悬浮助手测试计划

## 三层怎么分

| 环 | 覆盖什么 | 手段 | 为什么这样分 |
| --- | --- | --- | --- |
| 内环（秒级） | 地址校验、加解密、卡片字段校验、指纹 | 纯函数单测（`paideia-ai` 的 26 条） | 这些是**安全与正确性的判断点**，逻辑分支多、跑得快，失败时定位最准 |
| 中环 | 凭据落库与不泄密、缓存与可见性、无凭据可读不可生成、正文改动失效、SSRF 拒绝、失败不落缓存 | 集成测试（真实 MySQL + MockMvc，**端口换桩**） | 这些行为跨 HTTP + 数据库 + 编排，只有真链路能证明；桩同时用来数"有没有调用模型" |
| 外环 | 壳常驻、取当前内容、无凭据给配置入口且不触发调用、桌面产物 | 学习者端 e2e + 既有边界检查 + 桌面打包 | 界面语义（"未产生调用"这类表述）只有真浏览器才算数 |

## 明确不做的检查

- **任何测试都不真连上游模型**：没有网络可达的上游，也不该花谁的 Key。生成路径用桩替身覆盖；
  安装包里的桌面端也一样——它跑起来时用的是**用户自己配的凭据**，测试阶段不碰。
- **不在 e2e 里覆盖"生成成功"**：那需要一个可用的 Key 与真实上游。它的证明在集成测试里
  （桩返回卡片 → 断言落库、用量、缓存命中不再调用），e2e 只证明"用户看得见、点得动、
  打开页面不会偷偷花钱"。
- 不做性能与并发压测：本项的产品量级是"用户读内容时点一下"，限流本身就按单实例内存态设计。

## 回归范围

`mvn -B verify`（全部后端模块）、`pnpm -r typecheck`、`pnpm -r test`、学习者端与管理端与展览页三端 e2e、
桌面打包并核对产物内容（管理端仍不在包里、助手壳在包里）。

## 反向验证（本项至少要咬住这两条）

1. **去掉 SSRF 校验**：`UpstreamGuard.assertAllowed` 改为直接放行 → `UpstreamGuardTest` 里
   回环／私网／元数据那批用例必须失败；如果照样通过，说明校验没被真正执行。
2. **命中缓存改成照样调模型**：把 `SummaryService.generate` 的缓存命中分支改成"继续调用" →
   集成测试的 `verify(summarizer, times(1))` 必须失败（那正是"不重复花钱"的唯一证据）。
