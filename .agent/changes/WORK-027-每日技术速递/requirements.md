### 数据源实测（详细数字见 [research.md](research.md) 第二节）

- **可用**：HN Algolia（字段最全）、arXiv 官方 API、量子位 / IT 之家 / InfoQ 的 RSS（量子位**无正文**，只有标题）、掘金、开源中国、OpenRouter 模型库（470 个含 `pricing`）。
- **可用但不稳**：`github.com/trending` 本机三次连接被拒、生产 200 且 12 行可解析 ⇒ **必须有第二条路**。

- **GitHub 限额实测**：匿名 search 10/分、core 60/时；本机 `gh` token 为 **core 5000/时、search 30/分**。

## 实现选择

以下是 Agent 的技术判断，D-01..D-03 之后基本确定。

| 编号 | 选择 | 理由 |
| --- | --- | --- |
| I-01 | **不新建 Maven 模块**，放进 `paideia-ai/internal/digest` | WORK-025 的面经抓取已经在 `paideia-ai` 里，同一个模块内已有「外部抓取 + 定时 + AI + 写库」的完整先例。新开模块要多一个 pom、多一次模块边界装配，换不来任何隔离收益——本项不对外提供模块间 API |
| I-02 | **新建一张 `digest_items` 表，不塞 `knowledge_entries`** | 新闻是「会过期的流」，知识条目是「策展内容」。塞进去会让全文检索被每日新闻淹没，也让「已发布/草稿」这套语义对新闻无意义 |
| I-03 | **不建 edition（日报）表**：日报 = `digest_items` 里 `edition_date` 等于某天的那批行 | 一期的「日报」只是按日期分组展示。单独一张表只为了存「今天成刊了」这个状态，而这个状态可以从「当天有没有行」推出来。**若 Q-03 要「今日综述」，则给它一列 `daily_brief` 放在当天的第一行**（而不是新表） |
| I-04 | 抓取收在 `DigestSource` 端口后面，每个源一个实现，**单源失败不影响其它源** | 与 WORK-025 同一纪律。七个源里坏三个，剩下四个照常出内容 |
| I-05 | **GitHub 热榜走两条路**：主用 `github.com/trending` 页面解析，失败退回 Search API（`created:>=<7天前> stars:>100 sort=stars`） | 实测页面抓取时通时断，而 Search API 稳定；但 Search API 量的是「新建且涨得快」，不是官方热榜，只能当兜底，不能当主源 |
| I-06 | **AI 每天只调一次**：收集完成后对候选池做一次调用，产出「今日要闻」的挑选与每条一句中文摘要 | 面经是「每篇一次调用」，新闻如果照抄那个形态，一天几十条就是几十次调用。一次调用把「选」和「写」一起做掉，成本从几十次降到一次 |
| I-07 | **不把 AIHOT 的接口当数据源** | 那等于给别人的服务套壳，用户要的是「自己做一个类似的东西」。AIHOT 只作为**产品形态参考**（六步流水线、聚簇算热度、日报成刊） |
| I-08 | 调度沿用 `@Scheduled(fixedDelay=24h, initialDelay=5min)`，**默认关闭**，与面经任务同一形态 | 既有三处都是这个形态，不引新依赖 |
| I-09 | 指纹去重按**规范化 URL**（去掉 `utm_*`/`ref`/`spm` 等追踪参数）+ SHA-256 | 同一条新闻会被多个 RSS 转，URL 只差追踪参数。与 WORK-025 的题目指纹同形态，但**各写一份**：一个是规范化题目文本，一个是规范化 URL，共用反而不清楚（规则三：出现第三处再抽） |
| I-10 | 只存**标题 + 我们自己写的一句话摘要 + 原文链接**，不镜像正文 | 与 WORK-025 I-02 同一纪律。版权面最小，也让「摘要」必须是我们写的 |
| I-11 | 前端一个页面 `/digest`，按日分组；首页加一张入口卡 | 与知识库两级结构同形态，不新建前端包 |
| I-12 | **管理端加「当日条目删除」**：一个列表 + 删除，不是完整内容管理页 | D-07 直出之后，一条脏数据原本只能进数据库删。这个页面是直出的配套，不是额外功能 |
| I-13 | GitHub token 放 `paideia.ai.digest.github-token`，**环境变量占位 + 值只进被忽略的 `application-local.yml`** | 与 AI 凭据同一位置同一纪律。**未配置时自动退回匿名**（限额 60/时仍够一天一次），所以这个配置是可选增强而不是硬依赖 |
| I-14 | **有 token 时不再走页面解析，直接走 Search API** | 页面解析是「不稳定但语义准」的通路，Search API 是「稳定但语义偏」（量的是新建且涨得快）。有 token 后限额 5000/时，没必要再依赖一个会随改版坏掉的解析器；**保留页面解析作为 token 未配置时的兜底** |

## 背景

平台现在的内容全部是**人工策展或半自动采集的长内容**：知识库靠管理端录入，课程靠 markdown 导入，八股文靠牛客面经抓取后 AI 解析。**没有任何「今天技术圈发生了什么」的位置。**

而这条需求对 Paideia 不是锦上添花：定位是「千人千面的 AI 个性化学习平台」，一个学习者如果不知道本周出了什么模型、哪个框架在涨、哪篇论文在改变做法，学的内容会很快过期。**「前沿」本身就是学习材料的一种**，只是它的形态是流而不是课。

## 目标

- 学习者每天打开平台能看到一屏「今天值得知道的事」，不需要去刷 Hacker News、GitHub、arXiv。
- 无人介入即可产出；某个源挂了也能出内容，并明确记录挂了哪个。
- 每条都能点回原文，不制造「平台说这是真的」这种无出处的断言。
- 成本可控：**每天一次 AI 调用**量级，而不是每条一次。

## 非目标

- 不做实时流（D-02）。不做推送、不做邮件订阅。
- 不做社区投稿、评论、点赞。
- 不镜像第三方正文。
- 不做「事件聚簇 + 热度算法」（AIHOT 的核心竞争力）。一期的排序用**源自身的信号**（HN 点数、GitHub 当日新增 star、arXiv 提交时间）+ 一次 AI 挑选，不做跨源合并同一件事。
- 不做个性化推荐排序（一期所有身份看到同一份日报）。
- 不做向量检索（项目级约束仍生效）。

## 用户与工作流程

**学习者**：从导航栏进「每日速递」→ 默认看今天 → 卡片分三组（前沿新闻 / GitHub 热榜 / 社区热帖）→ 每条有中文标题、一句话摘要、来源与热度数字、原文链接 → 可往回翻历史日期。

**运维**：定时任务每天跑一次，把各源结果写库并标记当天「已生成」。某个源失败时，该组为空并在任务日志里点名；页面不因此报错。**内容直出（D-07）**，发现不合适的条目在管理端「当日条目」页删掉。

## 功能需求

- **REQ-001**：每天定时从多个外部源采集条目，一次运行覆盖「昨天至今」。
- **REQ-002**：包含三类源（D-05）：AI/技术新闻（量子位、IT 之家、InfoQ 的 RSS）、GitHub 每日热榜、Hacker News 前 10。
- **REQ-003**：GitHub 热榜**配置了 token 时走 Search API**；未配置 token 时走页面解析，解析失败再退回 Search API（匿名限额 60/时仍够用）。**任何一条通路都不能让整组为空而不留记录**。
- **REQ-004**：按规范化 URL 去重；同一条内容跨源、跨天重复出现时只入库一条。
- **REQ-005**：每天对候选池做**一次** AI 调用，产出每条的中文标题与一句话摘要；调用失败时该日降级为「只有原标题 + 链接」，页面仍可用。
- **REQ-006**：学习者端**导航栏**有可发现的「每日速递」入口（D-06），默认展示当天，可查看历史日期。
- **REQ-007**：每条都标注来源与原文链接；正文不出现第三方原文的整段镜像。
- **REQ-008**：采集、AI 摘要两个环节的失败都可观察（日志 + 当日条目的降级状态），不允许静默失败。
- **REQ-009**：单个源失败不影响其它源；单次运行的总条目数有上限（成本闸）。
- **REQ-010**：AI 调用计入 `ai_runs`（新增一个 `RunKind`），成本可从既有遥测看到。
- **REQ-011**：管理端能按日期查看当日条目并删除单条（I-12）。**这是直出的配套**：没有它，一条脏数据只能进数据库删。

## 质量要求

- 抓取失败不得影响站点其它功能，定时任务异常不得拖垮进程。
- 每日 AI 消耗有硬上限：一次调用、候选池条数上限可配置。
- 抓取频率克制：**每源每天一次**，不做轮询。
- 尊重来源的访问规则：优先用官方 API（GitHub Search / Algolia），只在没有 API 时才解析页面；带可识别的 User-Agent。
- 存储在 UTC；SQL 只写 mapper；时间由应用写入，不调数据库 `NOW()`。
- 公开仓库纪律：抓取地址、User-Agent、限额走配置；**GitHub token 只进被忽略的本地文件，仓库里只留环境变量占位**（D-09）。

## 约束与依赖

- **硬依赖 WORK-025**（D-08）：八股文的**前端入口**完成后本项才开工。理由是两个列表页形态几乎一样（按时间倒序 + 来源链接），一起做省一次设计；而且 WORK-025 现在后端跑着、前端点不进去，本身就是个待补的缺口。
- 依赖 WORK-009 的平台凭据（AI 摘要走平台出钱，不扣用户积分——与面经同一取舍）。
- 依赖 WORK-022 的遥测（新增 `RunKind.DIGEST`）。
- 与 WORK-025 **共用纪律但各自独立**：两个定时任务、两张不同的存储路径、两套源实现，不互相依赖。
- 外部源是**长期风险**：RSS 会改版、GitHub 页面结构会变、限额会收紧。端口化 + 兜底通路是为此准备的。
- **GitHub token 是可选增强不是硬依赖**（I-13）：未配置时退回匿名，功能不降级，只是限额从 5000/时降到 60/时。

## 关联工作项

- **WORK-025 八股文专区**：形态最近的先例（定时抓取 + AI 解析 + 指纹去重 + 端口化）。本项刻意复用它的**纪律**而不是代码。
- **WORK-004 知识库**：本项**不进**知识库，理由见 I-02；但未来「把某条速递沉淀成条目」是自然的桥。

- **WORK-019 MCP 网关**：将来可把「今天的速递」做成一个只读工具给外部 agent 查（与 AIHOT 的 `/agent` 接口同构），一期不做。

## 验收标准

- **AC-001**：定时任务按日运行，连续两个自然日都能在 `digest_items` 里看到对应 `edition_date` 的批次；不需要人工触发。
- **AC-002**：把同一个 URL（含不同 `utm_*` 参数）在两个源里各喂一次，库中只有一条。
- **AC-003**：把 GitHub 主通路改成不可达，任务仍产出热榜条目（来自兜底通路），并在日志里点名失败的那条通路；**配置 token 时主通路是 Search API，未配置时主通路是页面解析**。
- **AC-004**：把某一个 RSS 源改成不可达，其余源照常入库，当日页面正常显示，缺的那组为空而不是整页报错。
- **AC-005**：把平台 AI 凭据清空后跑一次，当日条目仍然入库（标题 + 链接），状态标记为未摘要，页面不崩。
- **AC-006**：学习者端**从导航栏**可达「每日速递」，默认当天，能翻到前一天；每条点得开原文。
- **AC-007**：抽查当日全部条目，正文只有我们自己写的摘要，没有第三方原文整段镜像；每条都有来源与链接。
- **AC-008**：一天内 `ai_runs` 里 `kind=digest` 的记录为 **1 条**（不是每源一条、更不是每条一条）。
- **AC-009**：`max-items-per-run` 调小后，入库条目数随之下降（成本闸生效）。
- **AC-010**：管理端按日期能看到当日条目清单；删除单条后学习者端不再出现该条，刷新页面仍然不在。
- **AC-011**：**去掉 `github-token` 配置后跑一次，任务仍然成功**（退回匿名 + 页面解析），证明 token 是可选增强而非硬依赖。

## 假设

- **假设**：RSS 源的标题足以让 AI 写出一句话摘要。量子位实测**没有正文**（只有标题/链接/时间），InfoQ 有 HTML 正文——所以摘要质量会因源而异，这是已知的降级。
- **假设**：`github.com/trending` 的页面结构短期内不变。已实测 12 行可解析（repo 路径、描述、当日新增 star、语言），但**解析器一定会随 GitHub 改版而坏**，这是兜底通路存在的理由。
