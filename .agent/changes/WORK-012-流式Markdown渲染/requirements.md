**调研结论（外部，2026-10-16）**

| 来源 | 关键事实 |
| --- | --- |
| opencode（`anomalyco/opencode` issue #49360） | **"在最后一个完整 token 处切开，把尾巴愈合为纯文本"**——这就是它的降级策略。另有 issue #11765 说明它也在重做流式渲染组件（174 行的 `markdown.ts`） |
| opencode 官方论坛 | 用户报"时不时渲染不对，控制台与桌面版都有，换模型改配置都压不住" → **连它也没做到"百分百"** |
| `vercel/streamdown` + `remend` | 6 阶段管线。**remend** 是独立的"补全"包，按**优先级 handler** 补：未闭合的强调/行内 code/代码围栏/链接(占位 URL)/`$$`，并把单个 `~` 转义。块级切分用 `htmlStack` **栈**跟踪未闭合 HTML；`$$` 奇数则合并下一块；脚注出现则整篇一块 |
| streamdown 的流式三招 | **块级 memo**（只有内容变了的块重渲）+ **处理器 LRU 缓存**（首次 ~10ms、命中 ~0.01ms）+ **`useTransition`** 非阻塞更新；动画只动画"上次渲染之后的字符"以防闪 |
| 性能实测文章（dev.to，300x） | 真凶是"**每个 token 对整串完全重解析**：标题重新识别、代码块重新高亮、表格重新测量" |

## 目标

- 助手回答**按 markdown 渲染**，且**流式过程中不出现结构性跳动**。
- 已渲染好的内容**不因为后续 token 到达而重排或闪成别的形态**。
- 渲染开销**不随回答长度线性增长**（已完成块不重解析）。
- 有一个**可扩展且可回归**的结构：新增一种"渲染不对"的真实样本，能固化成一条用例；新增一种语法，能加一个 handler。

## 非目标

- 不做代码语法高亮（那是**新增依赖**级别的决定，另议）。
- 不做 LaTeX / 公式、mermaid 图、脚注。
- 不做富文本所见即所得编辑器（WORK-004 已定）。
- 不做"消息内搜索"。
- 不改助手面板形态（WORK-011 已定）。
- **不改后端**：这是纯前端呈现层的工作（语料是**离线抓取**后固化的，不在运行时依赖上游）。

## 用户与工作流程

**读者**：提问 → 回答边生成边格式化 → **滚动位置和已读内容不动** → 代码块/表格/列表从第一个字符起就长成最终的样子（未完成的一小段至多是"还没上格式"，不会先错后改）。

## 功能需求

- **REQ-001 接上渲染**：助手回答走 markdown 渲染（复用既有渲染器的能力与安全立场）。
- **REQ-002 块级切分**：把累积文本切成块；**未闭合的结构必须与其后续块合并**——未闭合的代码围栏、未闭合的 HTML 标签（用栈跟踪）、奇数个 `$$`、以及需要整篇一起解析的情形（如脚注）。
- **REQ-003 块级增量与记忆化**：已完成且内容未变的块**不得重新解析**（用稳定的 key + memo）；流式时只重算最后一个（未完成）块。
- **REQ-004 终止补全（termination）**：对**最后一个块**补全未闭合语法，覆盖：代码围栏、行内 code、粗体/斜体/删除线、链接与图片、`$$`；并处理"单个 `~` 不得被当成删除线"这类误判。**handler 顺序固定且有据可依**（照 remend 的优先级，不是自创）。
- **REQ-005 降级（healing）**：补全**失败**或**不确定**时，**切在最后一个安全边界、把尾巴当纯文本渲染**（opencode 的做法）——**绝不允许**把未完成的内容渲染成一个会随后续 token 改形的结构。
- **REQ-006 不跳动**：对同一段输出，**任意前缀渲染出的"已完成块"内容必须与最终渲染的对应块一致**（这是本项的核心可测性质，见 REQ-011）。
- **REQ-007 流式友好**：块数组更新走非阻塞更新；动画（若有）只作用于新增字符。
- **REQ-008 安全**：沿用"不生成 HTML 字符串"的立场；补全注入的占位（如未完成链接的 URL）不得成为可点开的真实外链。
- **REQ-009 与既有面一致**：条目页与管理端预览继续用同一套渲染能力，**不出现两套 markdown 行为**。
- **REQ-010 语料**：用**真实上游输出**产出语料（用户提供 key 与 baseUrl），覆盖代码块/表格/嵌套列表/引用/混合排版等；语料**离线固化进仓库的测试夹具**，运行时不依赖上游。
- **REQ-011 可测的等价性质**：把每条语料**逐字符（或逐 token）前缀**喂进去，**在每个前缀上渲染一次**，断言"已完成块与最终一致"。这是把"百分百"变成可验收的核心手段。
- **REQ-012 可扩展**：新增 handler 与新增语料都只改各自一处（注册表 / 语料目录），不需要动渲染主流程。

## 质量要求

- **三条可验收口径**（替代"百分百"）：
  1. **逐前缀等价**：任一前缀的"已完成块"与最终渲染一致（REQ-006/011）；
  2. **解析次数不随长度增长**：流式渲染 N 个增量时，**已完成块的解析调用次数为 0**（用计数器断言）；
  3. **无结构性跳动**：e2e 里对"代码块/表格/列表"三类，断言其在流式过程中不出现形态反复。
- **安全**：不得因补全而引入可执行/可外链的注入点。
- **可维护**：补全 handler 每个都有独立单测；块切分有独立单测；**主流程代码量要小**（复杂度放在被单测覆盖的纯函数里，而不是组件里）。

## 验收标准

- **AC-001 渲染生效**：回答里的粗体/列表/代码块/表格按 markdown 呈现（不是原样字符）。
- **AC-002 未闭合不破形**：`（```java\nclass A {` 这种未闭合围栏的前缀，渲染结果是**一个代码块**，而不是"后面整段正文都变成代码"。
- **AC-003 逐前缀等价**：对全部语料逐前缀渲染，**"已完成块"与最终一致**（0 例不一致）。
- **AC-004 增量真的省**：流式 N 个增量时，**已完成块的解析次数 = 0**；总解析次数不随 N 线性增长。
- **AC-005 降级可见且不跳**：构造一个"补全不了"的输入（如极端嵌套），断言走的是**纯文本降级**路径，且该片段**不会随后续 token 改形**。
- **AC-006 表格与代码块不闪**（e2e）：这两类在流式过程中不出现形态反复。
- **AC-007 安全回归**：语料里含 `<script>`、`![](javascript:...)`、`[x](javascript:...)` 等，断言**不被执行、不成为可点外链**。
- **AC-008 单一实现**：条目页与管理端预览的行为与助手一致（同一套渲染，有断言或明确的复用证据）。

## 假设

- "逐字符前缀"在语料上跑等价断言的开销可接受（语料条数 × 平均长度）。若过大，退化为"逐 token 前缀"并记录口径。
- 真实上游的输出分布会随模型变化，所以语料既要**固化**（可回归），也要能**重新采集**（提供脚本）。

## 待确认问题

**无阻断批准的问题**。两条属实现选择：

1. **渲染器放哪个包**：现在在 `@paideia/knowledge`。建议**挪到 `@paideia/ui`**（通用 markdown 渲染不属于"知识库"这个业务概念），`knowledge` 侧改成 re-export；这样 `@paideia/assistant` 不必依赖业务包。
2. 语料的**规模与采集方式**：建议先 8–12 条（覆盖各语法 + 若干"故意恶劣"的混合排版），采集脚本与语料一起提交。

## 什么情况下该重审

- 若"逐前缀等价"在真实语料上**无法达到 0 例不一致**（说明某类语法本质不可稳定渲染）→ 那一类必须**明确降级为纯文本**并登记，而不是放宽断言。
- 若要引入代码高亮 / 公式 → 那是"新增依赖"的决定，回到本项"非目标"重开。
- 若真实上游的输出形态出现大变化（如大量 HTML 表格）→ 语料与 handler 需要重采、重定。
