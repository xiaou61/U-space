# AI 调用追踪与运营统计提案

## 摘要

给每一轮 AI 调用留下一条落库记录，给轮次内部的每次上游调用与每次工具调用留下步骤记录，再在管理端提供两个只读页面做统计与下钻。

采集端做成**一个端口 + 多个落地实现**的形状：业务代码只调 `RunRecorder`，`RunRecorder` 只往一个有界队列里塞不可变快照，单写线程再交给若干 `RunSink`。本期只实现 `MysqlRunSink`；将来接 OTel、Langfuse 或 Micrometer 是加一个类，不改任何埋点。

## 推荐方案

### 为什么是"端口 + sink"而不是"直接写表"

这是本项唯一真正重要的设计决定，其余都是它的推论。

如果业务代码里直接 `jdbcTemplate.update("INSERT INTO ai_runs ...")`，那"可扩展"就不成立：每接一个新的观测后端，要在七个调用点各改一次；想临时关掉统计，要改代码；想同时写 MySQL 和 Langfuse，要在每个调用点上写两遍。

把落地拆出来之后，扩展点收敛成一个方法：

```java
interface RunSink {
    void accept(RunRecord run);   // 一个不可变的轮次快照，含它的全部步骤
}
```

- 接 Langfuse：加一个 `LangfuseRunSink`，把 `RunRecord` 映射成 OTel span。字段名在设计里已经照 OTel 的 `gen_ai.*` 对齐，映射是翻译不是重设计。
- 接 Prometheus：加一个 `MicrometerRunSink`，把计数与直方图报出去。
- 想两边都写：两个 sink 都注册，`RunRecorder` 挨个调用。
- 想关掉：`paideia.ai.telemetry.enabled=false`，装配一个 `NoopRunRecorder`。

代价是多一层间接，以及一个"快照必须自包含"的约束——`RunRecord` 里不能放懒加载的东西。这个代价换来的是**以后加观测后端零埋点改动**，值。

### 为什么一行一轮 + 一行一步，而不是一张宽表

工具调用当前是黑盒：`AgentToolBridge.run` 把异常吞成一段文本（`AgentToolBridge.java:166-169`），连失败计数都没有。要回答"哪个工具最常失败""一轮调了几次工具""是上游慢还是工具慢"，必须有步级行。

把步骤塞进 JSON 列的好处是表少，代价是**再也聚合不了**——"按工具名统计失败率"这种查询在 JSON 里只能全表扫或者用 MySQL 的 JSON 函数硬算，且加索引极不灵活。两张表在这个量级上不增加任何运维负担。

### 为什么 span 用 trace_id 关联而不是自增 run_id

异步写入下有个具体的麻烦：轮次行是"开始时插入"的，但步骤行是"结束时批量插入"的。如果用自增 `run_id` 关联，写步骤时要记得住那个 id（多一份内存状态，且插入失败时要重试拿 id）。

改用一个全局唯一的 `trace_id`（服务端生成的 32 位十六进制串，与 `TraceIdFilter` 的生成写法一致；**不复用客户端传来的 `X-Trace-Id`**，那个值可以被伪造）做关联：开始时 `INSERT ... (trace_id, status=running)`，结束时 `UPDATE ... WHERE trace_id=?` 再批量 `INSERT` 步骤。两次写互相独立，任何一次失败都不影响另一次，也不需要往返取 id。

代价是 join 的是字符串而不是整数。在一轮几十条步骤、总量百万级的规模上，这个代价量不出来。

### 为什么先插 running、再更新终态

如果只在结束时写一行，那么"进程崩溃""线程卡死""上游永远不返回"这三类最需要排查的情形**一行记录都不会留下**——而它们恰好是用户投诉最多的。先插 running 之后，一个长时间停在 running 的行本身就是信号：统计里"进行中"计数异常升高、或者有一批行的 `started_at` 很早却从未结束，直接指向卡死。

### 为什么采样按轮不按步

按步采样会得到半截的 trace：一次对话留下了第 1 轮上游、丢了工具、丢了第 2 轮。这种记录比"完全没记"更有害，因为它会让排查的人得出错误结论。

按轮采样之后，一条记录要么完整要么不存在。并且失败/超时**永远保留**——采样是为了省存量，不是为了把问题藏起来。

### 为什么不碰计费流水

`ai_credit_ledger` 现在只有一条净额 `SETTLE` 行，且 `reserve` / `refund` 不写流水。要让它变成完整的逐笔账，得改三条结算路径的语义、补两种流水、再处理"预留了但进程死了"的悬挂。

本项的目标是运营统计，不是审计。`ai_runs.credits` 记下"这一轮实扣多少"，足以按天对账：同一时间窗内 `SUM(ai_runs.credits)` 与 `SUM(-ai_credit_ledger.delta WHERE kind='SETTLE')` 应当相等。逐笔对账是另一件事，触发条件写在设计里。

## 范围

**做**：
- 两张表与一个迁移（`ai_runs`、`ai_run_spans`）；
- 采集端口 `RunRecorder` / `RunScope` / `StepScope`、快照类型、有界队列、`RunSink` 与本期唯一的 `MysqlRunSink`；
- 七条 AI 路径的接入（对话链路最细，含每轮上游与每次工具）；
- `MdcTaskDecorator` 让 HTTP traceId 活到异步线程，且轮次标识单独一个 MDC key；
- 管理端两个只读端点（概览、明细 + 详情）；
- 管理端两个页面；
- 注销级联加两张表；
- 保留期清理任务、采样与开关三项配置；
- 把 `CreditService` 三个结算方法改成返回实扣金额（向后兼容）。

**不做**（与需求非目标一致，此处只点名最容易"顺手做掉"的三项）：
- 不接 OTel SDK 或 Langfuse——本期不需要跨服务链路，且自托管四个存储的成本远超收益；
- 不采正文与提示词——隐私面直接扩大，而排查能力增益有限（正文已在消息表）；
- 不做 trace 树 UI——列表 + 步骤表已经能回答本期所有问题。

## 备选方案

### 备选一：接 OpenTelemetry SDK + 自托管 Langfuse

**它最强的理由**：社区标准、生态成熟，Langfuse 现成有会话视图、trace 瀑布、成本面板、prompt 管理与评分，几乎不用自己写 UI。将来要接商业观测平台时零成本。规范里 `gen_ai.*` 的字段命名已经是事实标准。

**为什么没选**：自托管 Langfuse 需要 Postgres + ClickHouse + Redis/Valkey + S3 四个存储加 web 与 worker 两个容器，而生产机是 4 核 16G 且已跑 MySQL、RustFS、Firecrawl——这台机器上再加四个有状态服务是实打实的风险。OTel SDK 的核心价值是**跨进程上下文传播**，本项是单进程应用，用不上。

**它给出的代价，本方案接受了什么**：没有现成的 trace 瀑布图与评分体系，将来要自己补；字段名照 OTel 对齐后，接时要写一遍映射。这是真实短板，见风险一节。

### 备选二：只加 Micrometer 指标，不落明细

**它最强的理由**：代码量最小（十几个 `Timer` / `Counter` 注册），可与 Actuator 现有的 `metrics` 端点一起暴露，零新表。

**为什么没选**：指标是聚合值，回答不了"某个用户的某一轮发生了什么"。而本项的核心诉求之一正是"用户反馈某次很慢，怎么定位"。指标也抓不住上下文规模这类高基数下钻字段。

**代价**：本方案写入量更大、需要保留期管理。这是明确的取舍。

### 备选三：一张宽表，步骤存 JSON

**它最强的理由**：表少、迁移简单、读取一次扫描就能出完整一轮，很适合"详情页"这种场景。

**为什么没选**：聚合能力基本丧失。而且 JSON 列里的字段无法建普通索引，将来想"按工具名筛选失败"只能退化成全表扫。

### 备选四：先插 running 改成只在结束时写一行

**它最强的理由**：写库次数减半，不需要"结束更新"那条路径，也不会有永远停在 running 的僵尸行要清理。

**为什么没选**：崩溃与卡死的那一轮会彻底消失。而"永远没结束"恰恰是最需要留证据的一类故障。僵尸行的处理放在保留期清理里（超过 N 小时仍 running 的标为 interrupted），成本很小。

## 交付拆分

1. **数据与采集骨架**（迁移、端口、快照、队列、一个 sink）——可独立验证：用一个测试触发一轮，断言两表各有行。
2. **对话链路埋点**（控制器、上游每轮、工具、上下文规模）——最细的一条路径，也是验收主场景。
3. **其余六条路径接入**——每条只需 begin/finish。
4. **MDC 传播与日志对齐**——让记录能被日志找到。
5. **计费返回实扣金额**——让 `credits` 列有值且能对账。
6. **管理端端点**——概览与明细。
7. **管理端页面**——用户可见的最终切片。
8. **注销级联 + 保留期清理 + 采样开关**——收尾，可独立验证。

第 1–5 步交付后即使没有页面，也能用 SQL 回答"昨天花了多少"；第 6–7 步是把它变成可用的运营面。

## 风险与缓解措施

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| **埋点拖慢回答** | 用户感知变慢 | 调用方线程零 IO（只进队列）；有界队列满了直接丢；单测断言"调用线程内没有写库" |
| **写库失败影响业务** | 回答失败或计费异常 | sink 的全部异常在队列线程内吞掉并打日志；业务路径只做内存操作 |
| **没有 trace 树 UI，排查体验弱** | 定位复杂问题时要看多张表 | 详情页把该轮全部步骤平铺成表并用序号表达先后；字段名照 OTel 对齐，将来接外部平台可直接映射 |
| **僵尸行（running 永不结束）堆积** | 统计里"进行中"数字失真 | 保留期清理顺手把超过阈值（默认 6 小时）仍 running 的行标为 `interrupted` |
| **`settle` 返回值改动波及既有调用方** | 编译或语义漂移 | 只改返回值不改参数与语义；既有调用方忽略返回值即可编译通过；集成测试核对 `credits` 与流水一致 |
| **上下文规模字段选错，将来要加列** | 一次 DDL | 冷字段一律进 `attrs` JSON，等真的需要按它筛选再提成列 |
| **采样开启后单次排查查不到** | 用户投诉时无记录 | 失败/超时永远保留；默认采样率 1.0；采样是显式配置，默认不开 |
| 管理端统计在数据量大时变慢 | 页面卡 | 时间窗上限 90 天；分位数在 SQL 内算；百万行以后再加日汇总表（有触发条件） |
