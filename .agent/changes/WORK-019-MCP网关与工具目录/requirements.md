# MCP 网关与工具目录需求

## 本项状态与本轮变化

- **2026-10-18 建项起草（draft）**。用户原话：「现在我们的 api 其实也很多了 我感觉 是不是可以做一个统一的 mcp 网关 就是把 api 转换成 MCP 这个你联网搜索调研一下实现思路 方便我们后续的调用 就是直接链接上我们的超级 ai 那个」；随后补充：「只保留这么点吗 其实我看到一个技术 就是按需保留 … 所以设计的时候考虑长远一点可以 我们可以分内部外部」。
- 调研证据见 [`research.md`](research.md)。**签字之前不动代码**。

## 已确认事实

| 项 | 事实 |
| --- | --- |
| 端点规模 | 生产端点 83 个 / 26 个 controller（ai 40、knowledge 19、note 12、account 9、sandbox 2、security 1） |
| 没有 OpenAPI | 仓库无 springdoc/swagger，也没有规格文件——任何配置驱动的自动转换都得先补规格生成 |
| 助手工具 | 4 个进程内工具，直接调 `KnowledgeApi`，不经 HTTP；schema 在工具循环外算一次 |
| 模块边界 | Spring Modulith 构建期校验；跨模块只能依赖包根 API |
| 认证 | 自签 JWT，15 分钟 access + 单次轮换 refresh；配置在 MCP 客户端里放不下 |
| 协议现状 | MCP 最新规范 2026-07-28 无状态；标准传输只剩 stdio 与 Streamable HTTP；`tools/list` 允许按请求授权变化；**协议层没有工具搜索** |
| Java SDK | 稳定版 2.1.0 支持到 2025-11-25；2026-07-28 只在 2.2.0-M1；核心件不依赖 Spring AI |
| 成熟参考 | GitHub 官方 server 用一份 Inventory + 多层过滤 + 多视图 URL（`/mcp/x/{toolset}/readonly`）暴露约 90 个工具 |

## 用户决定

| # | 问题 | 裁决 |
| --- | --- | --- |
| 1 | 要不要做统一 MCP 网关 | 要做，把平台能力暴露成 MCP，方便后续调用 |
| 2 | 是否只做少量工具 | 不只做少量：要「按需保留」（延迟加载 / 渐进式披露），工具数量不应成为上限 |
| 3 | 架构取向 | **分内部与外部两层**：内部是自家超级 AI 直接用；外部是别的助手接入我们的 MCP |
| 4 | 迭代预期 | 「这个功能会很快的迭代，架构一定要设计好」——优先可扩展的骨架，而不是一次性把 83 个端点转完 |
| 5 | 参考对象 | 参考 GitHub 等成熟项目的设计架构，不自己发明 |
| 6 | 写工具一期范围 | 除推荐的 `note.create`/`note.append`/`assessment.mark_entry` 外，其余写操作（知识库管理、账号删除、积分管理）不暴露 |
| 7 | 是否暴露 `assistant.ask` | **放到第一期**：外部助手可调用平台 AI 问答（复用现有积分与平台凭据） |
| 8 | PAT 默认过期 | 默认 90 天，可选永不过期 |

## 实现选择

> 根据已批准边界与仓库既有模式做的技术决定，不替代用户对产品范围的决定。

1. **一份工具目录，两个适配器**：工具的定义（名称、分组、schema、注解、权限、只读标记）是唯一真源；内部 harness 与外部 MCP server 都从它生成各自的清单。禁止两边各维护一份工具表。
2. **契约放 `paideia-platform`**（共享内核，所有模块已依赖）：`ToolDescriptor`、`PaideiaTool`、`ToolContext`、`ToolResult`、`ToolCatalog`。业务模块实现工具，不依赖 MCP SDK。
3. **外部新增 `paideia-mcp` Maven 模块**：只依赖 `paideia-platform` 与 MCP SDK；工具实例通过 Spring 收集，模块之间不新增编译依赖。放不进 `paideia-ai`——那会让 ai 反向依赖 note/account，且 MCP 是传输适配层而非 AI 领域。
4. **复用 AgentScope 已传递引入的 MCP SDK 0.17.0**（`io.modelcontextprotocol.sdk:mcp:0.17.0`，含 `HttpServletStreamableServerTransportProvider`，协议到 2025-06-18），**不新增 MCP 依赖**。2026-10-18 实测 `mvn dependency:tree` 确认它已在 `paideia-ai` 的 classpath 上（由 `agentscope-core:2.0.0` 带入），直接升到 2.x 会与 AgentScope 自带版本冲突。目录与传输无关，将来 SDK 统一升级时只换适配器，不改工具代码。
5. **外部视图按 URL 静态切分**（照 GitHub）：`/mcp`（默认组，只读）、`/mcp/write`（含写，需 write scope）、`/mcp/x/{toolset}`、`/mcp/x/{toolset}/write`。视图片段在启动时构建，`tools/list` 与 `tools/call` 永远一致；不依赖 2026-07-28 才允许的「每请求返回不同列表」。
6. **外部凭据用长效 PAT**，不用 OAuth 2.1 完整流程（RFC 9728/8707 + 客户端注册成本高，而我们的客户端都支持自定义 Bearer 头）。PAT 哈希入库、可吊销、带 scope 与可选过期；access token 仍然只有 15 分钟，不作为 MCP 凭据。
7. **内部按需加载用客户端本地机制**：常驻核心包 + 一个 `find_tools` 元工具；命中后把 schema 并进下一轮。不依赖 provider 端 tool search（DeepSeek 没有）。
8. **工具命名 `toolset.verb_object`**（如 `knowledge.search`），点号是规范允许字符，同时把聚合撞名问题提前解决。
9. **一期只做策展工具，不做 83 个端点全量转换**：全量转换会让每轮上下文与积分成本失控，且流式对话、附件上传这类端点转成「一个操作一个工具」本来就是坏工具。

## 背景

平台已经有 83 个端点，但它们只服务自家前端。用户想要的是两种「接线」：

- **内部**：自家超级 AI 助手能调用更多平台能力，而不是每次加一个能力就改一处 `AssistantTools` 的 switch；工具多了也不能把每轮 context 撑爆。
- **外部**：ZCode、Claude Code、Cursor 这类外部助手能接上 Paideia，读知识库、管笔记、查自己的学习数据，将来还能调用平台 AI。

两者要的东西在结构上是同一件：**一份描述「平台能做什么」的目录**，以及**按调用者身份裁剪它**的能力。区别只在传输与工具选择机制。先把这个共同骨架立起来，后面加工具就是注册一条描述符，不需要动适配器。

## 目标

- 平台能力有**一份**机器可读的工具目录；新增一个能力 = 注册一条描述符 + 一个处理函数，内外两侧自动可见。
- 内部助手支持**按需加载**：工具总数增长到几十个时，首轮只发核心工具；模型能通过 `find_tools` 发现其余工具并在同一请求内使用。
- 外部助手能通过 **Streamable HTTP + Bearer PAT** 接入，按视图（默认组 / 单个工具组 / 只读 / 可写）拿到工具清单，且清单与可调用范围一致。
- 外部访问**按用户隔离**：归属只来自凭据，工具参数里没有「读谁的数据」这种字段。
- 写操作有明确标记，默认不暴露；只读视图里不可能出现写工具。
- 全链路可观察：每次工具调用一行结构化日志（谁、哪个工具、多久、成功与否），不含正文。
- 架构允许后续增加工具组、增加传输（2026-07-28）、增加资源与提示词，而不改已有工具的代码。

## 非目标

- **不做「83 个端点全量自动转 MCP」**，也不为了转换先补 OpenAPI。
- **不做 OAuth 2.1 授权服务器**、不做动态客户端注册；一期只支持 PAT。
- **不把平台变成 MCP 客户端**（不反向接入别人的 MCP server）。目录预留位置，但本项不实现。
- **不做 MCP resources / prompts**，只做 tools；也不做 sampling、elicitation、MCP Apps。
- **不暴露流式 AI 对话为工具**：工具调用是一问一答；需要长任务时后续用 MCP Tasks 扩展单独设计。
- **不做工具级计费表**：AI 类工具沿用现有积分预留-结算，非 AI 工具不计费。
- **不做多租户、不做向量检索**（项目常驻约束），工具搜索用词面打分。
- **不在本项做桌面端/移动端的 MCP 客户端**，只做服务端。

## 角色与场景

**内部（自家助手）**：学习者在助手面板提问 → 助手判断需要平台数据 → 调用已加载的工具或先 `find_tools` → 拿到结果继续回答。归属由当前登录会话决定。

**外部（第三方助手）**：用户在设置页创建一个 PAT（选 scope：只读 / 读写，可选过期）→ 把 URL 与 token 填进 ZCode 或 Claude Desktop → 外部助手列出该视图的工具 → 调用。读工具返回本人数据；写工具在写视图且 token 有 write scope 时才出现。

**管理员**：不需要新角色；PAT 是用户自己的凭据。管理端不新增工具开关（一期）。

## 功能需求

### 工具目录

- **REQ-001 唯一真源**：平台所有可被 AI 调用的能力由一份目录描述；内部清单与外部 `tools/list` 必须由同一份描述生成，不得出现「内部有、外部另写一份」。
- **REQ-002 描述符字段**：每条工具至少包含：稳定名称、所属工具组、标题、给模型看的描述、输入 JSON Schema、输出 JSON Schema（可空）、只读标记、破坏性标记、幂等标记、所需 scope、是否属于默认组。
- **REQ-003 启动期校验**：工具名重复、名称为空、名称不符合字符规则、输入 schema 不是 object、默认组引用了不存在的工具组——都必须在**启动时**失败并指出具体名称，不得静默覆盖。
- **REQ-004 视图过滤**：给定（工具组集合、显式工具集合、只读开关、调用者角色、调用者 scope）得到一个确定的有序工具子集；过滤顺序固定并写进文档。同一输入必须得到同一顺序（便于提示词缓存）。
- **REQ-005 目录即文档**：能从目录导出「当前注册了哪些工具、属于哪组、是否只读」的清单，供文档与测试对照。

### 内部按需加载

- **REQ-006 核心包**：内部助手每轮至少携带默认组工具（数量不超过配置阈值）。tool harness 与工具组的关系由配置决定，不再用硬编码 switch 决定「哪个 harness 有哪些工具」。
- **REQ-007 发现元工具**：当目录工具数超过阈值时，额外提供一个 `find_tools` 元工具；它按自然语言/关键词检索目录（词面打分，最多返回 N 条），返回匹配工具的名称、描述与完整 schema。
- **REQ-008 同请求内生效**：`find_tools` 命中的工具必须能在**同一轮请求的后续工具循环**里被调用，不需要用户再发一条消息。
- **REQ-009 会话内缓存**：已发现的工具在同一请求内不重复付费检索；未命中时明确返回「没有匹配」，不得崩溃或编造工具名。
- **REQ-010 工具不足阈值时行为不变**：工具总数不超过阈值时不出现 `find_tools`，行为与现在一致（现有 4 个工具的场景零变化）。

### 外部 MCP 服务

- **REQ-011 传输**：通过 MCP **Streamable HTTP** 暴露；支持 `POST`（JSON-RPC）与 `DELETE`（结束会话）；`tools/list` 支持分页游标。
- **REQ-012 视图**：至少提供这些端点，且每个端点的清单与该端点可调用的工具一致：`/mcp`（默认组，只读）、`/mcp/write`（默认组，含写）、`/mcp/x/{toolset}`（单组只读）、`/mcp/x/{toolset}/write`（单组含写）、`/mcp/x/all`（全部只读）。
- **REQ-013 鉴权**：所有 `/mcp/**` 请求必须带 `Authorization: Bearer <PAT>`；缺失、格式错误、已吊销、已过期、未知 token 一律 401，且响应不泄露 token 是否存在。
- **REQ-014 授权**：token 的 scope 决定能否访问写视图（无 `write` scope 访问写视图 → 403）；角色为 `ADMIN` 的用户额外看到管理类工具组（若该组存在）。越权工具不得出现在清单里，也不得被调用。
- **REQ-015 PAT 管理**：登录用户可创建、列出、吊销自己的 token。创建时明文只显示一次；列表只显示名称、前缀、scope、创建时间、最后使用时间、过期时间、状态；吊销立即生效。
- **REQ-016 PAT 存储**：只存哈希与展示用前缀，不存明文；校验使用恒定时间比较；token 长度足够（≥ 32 字节随机）。
- **REQ-017 归属绑定**：工具处理函数拿到的用户 id 只能来自凭据解析结果；工具参数里不得存在 userId/ownerId 之类字段；拿不到归属或不属于调用者时统一 404。
- **REQ-018 写操作确认标记**：写工具必须标 `readOnlyHint=false`、破坏性工具标 `destructiveHint=true`，描述里写明影响；只读视图不得包含任何写工具。
- **REQ-019 协议错误与工具错误分离**：未知工具、参数不符合 schema → JSON-RPC 协议错误；业务失败、上游失败 → `isError: true` 的工具结果，文本可读、不含堆栈与内部地址。

### 可观察与运维

- **REQ-020 审计日志**：每次 `tools/call` 一行结构化日志：tokenId（不含 token 值）、userId、工具名、视图、耗时、是否失败、结果字节数。不记录工具正文与用户数据。
- **REQ-021 限流**：按 token 限制调用频率（默认每分钟 N 次，可配置）；超限返回可读错误，不落库、不调用上游。
- **REQ-022 注销级联**：账号注销时该用户全部 PAT 立即删除（硬删），且不残留可用凭据。

### 计费与依赖

- **REQ-023 AI 类工具计费**：调用会触发模型请求的工具必须走现有积分预留-结算；余额为 0 时返回 402 且**一次上游请求都不发**。
- **REQ-024 复用现有能力**：知识检索、笔记、自评标记等一律复用模块包根 API 或现有用例，不在 MCP 层重写查询。

### 前端

- **REQ-025 PAT 管理页**：学习者端「设置」内提供 token 列表、创建（选 scope、可选过期、填名称）、吊销（二次确认）；创建成功后一次性展示完整 token 与复制按钮，并提供「改主意立即吊销」。

### 兼容与演进

- **REQ-026 工具名稳定**：工具名一旦公开不得随意改名；如需改名必须保留别名映射一个版本，并在描述里标注弃用。
- **REQ-027 协议演进**：传输层与目录解耦；将来增加 2026-07-28 无状态传输或 resources/prompts 时，不改动已有工具的实现。
- **REQ-028 平台 AI 问答工具**：暴露 `assistant.ask(question, entryId?)`，外部助手可让平台代为回答一次学习问题。它复用现有对话能力与平台凭据、按轮计积分；**不写会话历史**（外部调用不是用户的一段会话），返回纯文本结果。

## 质量要求

- **安全**：PAT 视同口令；日志、异常、文档、测试夹具里不得出现完整 token。所有 `/mcp/**` 端点默认拒绝，不加入任何免鉴权前缀。
- **隔离**：每个工具处理函数自己不做「归属判断」以外的越权想象；归属判断必须出现在 SQL 的 `WHERE user_id = ?` 上，拿不到 404。
- **失败不产生半条数据**：写工具失败不得留下部分写入；涉及多表时要在一个事务里。
- **不可信输入**：工具参数是不可信输入，按每个工具的 schema 校验后再用；模型给的数字要夹范围。
- **性能**：`tools/list` 单次 P99 目标 < 100 ms（视图在启动时预构建，不在请求里扫全部目录）；`find_tools` 检索不调模型。
- **可测**：过滤链、PAT 校验、视图清单、归属绑定都要有直接的单元/集成测试；不靠端到端猜。
- **常驻纪律**：Boot 4 / JDK 25 / 手写 MyBatis / 仅 MySQL / Flyway；迁移号取当时实际最大号 +1；集成测试不用 H2；无数据库口令时「跳过而非失败」且必须核对 Skipped 列；新增 `/api/v1/**` 端点必须 `@ApiAccess`。

## 约束与依赖

- 新增依赖只有一个：`io.modelcontextprotocol.sdk:mcp:2.1.0`（含 core + Jackson 3 绑定）。不引入 Spring AI。
- `paideia-mcp` 只能依赖 `paideia-platform`；不得依赖任何业务模块的 `internal` 包。
- 工具实现分散在业务模块，通过 `PaideiaTool` Bean 被收集；Modulith 边界不变。
- `/mcp/**` 不适用 `@ApiAccess`（那是 `/api/v1/**` 的契约工具）；但必须在 `SecurityConfiguration` 之外用独立的安全链显式声明，不允许落入默认放行。

## 验收标准

- **AC-001 目录一致性**：同一工具在内部清单与外部 `tools/list` 里的名称、描述、输入 schema、只读标记逐字一致（用同一份目录导出对照，不靠肉眼）。
- **AC-002 视图正确**：`/mcp` 只含默认组的只读工具；`/mcp/x/knowledge` 只含知识组；`/mcp/write` 含写工具；任一 `/mcp/**/readonly` 等价视图不含写工具。四个断言各自可独立失败。
- **AC-003 鉴权矩阵**：无 token、错 token、过期 token、已吊销 token → 401；只读 token 访问写视图 → 403；有效 token → 200。响应体不含 token 存在性提示。
- **AC-004 清单与调用一致**：清单里没有的工具一律无法调用（协议错误）；清单里有的工具在读 token 下调用成功。
- **AC-005 归属隔离**：用户 B 的 token 用用户 A 的资源 id 调用 → 404；工具参数里传入 `userId` 字段不改变实际归属（被忽略或校验失败，且不越权）。
- **AC-006 内部按需加载**：用 20 条合成工具构造目录 → 首轮只发核心包 + `find_tools`；`find_tools("知识 检索")` 命中后同一请求的下一轮出现该工具 schema；无关查询返回「没有匹配」且不抛异常。
- **AC-007 零积分**：余额为 0 调用 AI 类工具 → 402，上游调用次数为 0（用桩计数）。
- **AC-008 协议一致性**：官方 conformance 套件对目标协议版本跑一次，结果如实写入报告（通过数/失败项）；`tools/list` 顺序在同一目录下多次调用一致。
- **AC-009 错误语义**：未知工具 → JSON-RPC 错误；工具内部抛出 SQL 异常 → `isError: true` 且文本不含堆栈、连接串、表名；取消请求不产生第二次执行。
- **AC-010 审计日志**：每次调用产生一行日志，含 tokenId/userId/tool/view/durationMs/isError/bytes，不含正文；测试用日志捕获断言字段齐全。
- **AC-011 注销级联**：删除账号后 `mcp_access_tokens` 中该用户 0 行，旧 token 立即 401。
- **AC-012 迁移与守卫**：新迁移在生产库执行成功，重复启动校验和不报错；新表登记进注销清单；迁移号不写死。
- **AC-013 PAT 管理页**：创建后完整 token 只出现一次；刷新后列表只见前缀；吊销后旧 token 立即 401；页面在 390px 宽下无横向滚动。
- **AC-014 接入文档**：给出 ZCode 与 Claude Desktop 的配置片段（URL + Authorization 头）、三种视图的用途、只读建议；文档里不出现任何真实 token。
- **AC-015 `assistant.ask` 计费**：余额充足时返回文本并产生一条积分流水；余额为 0 时 402 且上游调用 0 次；调用不新增任何 `ai_conversations` / `ai_messages` 行。

## 假设

- 外部客户端至少支持 Streamable HTTP 与自定义 Authorization 头（ZCode、Claude Desktop/Code、Cursor 均支持）。
- 一期只有「学习者」与「管理员」两种角色，PAT 不细分更细的权限位；`read`/`write` 两个 scope 够用。
- 工具数量在可预见的一期不超过 30 个；超过时按需加载仍然有效，但检索质量需要重新评估。
- 外部客户端会自己处理写工具的确认提示；我们仍以视图与 scope 做第二道闸。
