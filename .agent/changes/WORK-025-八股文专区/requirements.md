## 两个分类的划分

用户说的「分成两个类」按**内容从哪来**切，而不是按难度或知识点切——因为读者对这两类的信任预期完全不同：一类是"这道题真被问过"，另一类是"这套讲法我们整理过"。

| 分类 | 内容来源 | 对标题目 | 是否标来源链接 | 更新节奏 |
| --- | --- | --- | --- | --- |
| **面经真题** | 牛客 Java 面经合集的帖子正文（A，走 `jobId=639` 列表 API）+ 平台按标题在合集里的二次筛选（C） | A + C | 是，每条带原站链接 | 每日定时 |
| **平台精讲** | 平台按 Java 知识大纲自行生成（B） | B | 否 | 按缺口补，不按日 |

两类共用同一套存储、渲染、检索与自评，只是 `category_id` 不同。**对用户来说它们是专区里的两个页签，不是两套系统。**

A 与 C 归在同一个分类，是因为它们最终呈现给用户的都是同一件事：**一道被真实问过的题 + 我们自己的解析**。C 只是"AI 解析失败或内容不合格时退回人工触发"的降级形态，不是独立的内容类型——所以不单开第三个分类。

**分类到此为止，不再往下细分**（D-07）：Java 基础、JVM、Spring、Redis、MySQL、并发这些主题全都留在「面经真题」这一个分类里。理由是这个专区的用法是"刷题"，靠全文检索和题目标题找，不靠浏览分类树；一上来就按技术栈铺开十来个分类，只会让入口变复杂。将来真题量足够大、确实需要按主题浏览时再拆，那时是移动 `category_id`，成本很低。

## 实现选择

以下是 Agent 的技术判断，给定 D-01..D-05 后基本确定。**其中 I-02 与 I-05 是实测后改写的**（原先以为只能拿到标题）。

| 编号 | 选择 | 理由 |
| --- | --- | --- |
| I-01 | 内容存在 `knowledge_entries`，不新建内容表 | 渲染器、quiz 块、全文检索、自评与复习排期全部现成；自建一套等于把四件事各写一遍。专区靠两个分类 + 一个入口页实现，"专区"是导航概念不是新存储 |
| I-02 | **入库存的是"从面经里提炼出的一道题 + 我们自己的解析"，不是帖子原文** | 面经正文是用户 UGC，逐字入库等于转载（且帖子含大量个人叙事、公司名、薪资，不适合做学习内容）。做法：AI 从帖子里抽出**题目清单**（往往是编号 1..N 的面试题列表），再对每题写解析。来源链接指向原帖 |
| I-03 | 抓取收在一个可替换的端口后面，牛客只作为其中一个实现 | 抓取源是最不稳定的一环，写死在业务代码里将来换源要动服务层 |
| I-04 | 调度沿用 `@Scheduled` + `fixedDelay`，每天一次 | 与既有两个定时任务同形态，不引新依赖 |
| I-05 | 去重按**题目指纹**（规范化后的题目文本，如去掉序号、标点、大小写） | 同一道题会在不同面经里反复出现（"HashMap 为什么线程不安全"每天都有）。按帖子去重会漏，按题目去重才不重复 |
| I-06 | 直接吃列表 API 的 `momentData.content`，**不再逐条抓详情页** | 实测列表接口已带完整正文，一次请求 20 条。详情页只在需要补历史时用 `/feed/main/detail/<uuid>` |
| I-07 | 「平台精讲」不走定时任务，按「面经真题」的缺口补 | B 是兜底与补全，每天自动生成本质是在造重复内容 |
| I-08 | 只取 `contentType=74`（面经帖），跳过 `contentType=250` | 实测 250 那批没有标题、没有时间戳、没有正文，是另一种内容形态 |
| I-09 | 抓取时固定翻前几页直到越过"上一天"边界，不做全量 100 页 | 日增量 3-7 条，翻 2 页足够覆盖一天；全量翻页既慢又没必要 |
| I-10 | **技术词密度按下式判定，阈值可配置**：帖子里命中**不同** Java 技术词的个数 ≥ 阈值（默认 3）才进入抽取与解析 | 实测同日 14 条里技术词命中 ≥8 的有 5 条、命中 1 的也有 5 条（「如何提高工程能力」「优博讯软件开发面经」）。按**去重后的技术词种类数**判，比按出现次数判更抗"某条帖子反复提 Java 十几次但其实没讲题"。阈值放配置里，因为真实准确率没跑过，默认 3 是个待调的起点 |

## 背景

「八股文」指国内技术面试的高频固定题目。用户本人正在秋招，是这条需求的第一用户。牛客是国内 Java 八股文的主要集散地。

现状是纯人工录入：知识库靠管理端手抄，课程靠 `content/courses/` 的 markdown 加 `scripts/import-course.mjs` 导入，**没有任何自动采集**。所以这条需求不是在已有能力上开个口子，而是从零加一条"外部内容进站"的通路。

## 目标

- 学习者在平台上有一个固定入口，能持续看到 Java 八股文，不需要去牛客。
- 无人介入即可产出新增内容，或明确记录"今天没有新增"。
- 每条内容带一段能看懂、讲透的 AI 解析，而不只是题干搬运。
- 抓不到的地方由平台自己的精讲补上，不让专区出现大片空白。

## 非目标

- 不做 Java 之外的分类（D-04）。
- 不复制、不镜像牛客上的任何回答正文。
- 不做社区投稿、评论、点赞。
- 不抓取需要登录或付费才能看的内容。
- 不做向量检索（项目级约束本期仍生效）。
- 不改牛客的分类体系。

## 用户与工作流程

**学习者**：从专区入口进入 → 看到两个页签「面经真题 / 平台精讲」→ 面经真题按抓取时间倒序，平台精讲按知识点分组 → 点开条目看题目与 AI 解析，真题类还能点来源链接回原站 → 可标记已掌握（复用现有自评）。

**运维**：定时任务每天跑一次，入库为 `draft` 或 `published`（待定，见 Q4）；抓取失败时能在某处看到失败原因与影响范围，而不是静默无声。

## 功能需求

- **REQ-001**：每天定时调用牛客 Java 面经合集列表接口（`jobId=639`）抓取新帖，直到越过"上一天"边界为止。
- **REQ-002**：从抓到的帖子正文里**抽取题目**，并按题目指纹去重——同一道题跨帖、跨天重复出现时只入库一条。
- **REQ-003**：每个入库的题目都有一段 AI 生成的详细解析；解析失败时该条不对外展示，或明确标记为待解析。
- **REQ-004**：学习者端有一个可发现的「八股文专区」入口，内含「面经真题」与「平台精讲」两个分类。
- **REQ-005**：「面经真题」的每条内容标注原始来源（牛客 + 原帖链接），用户能回原处；「平台精讲」不标来源。
- **REQ-006**：抓取、抽取、解析三个环节的失败都可被观察到（日志、管理端或统计），不允许静默失败。
- **REQ-007**：「平台精讲」按 Java 知识大纲补齐真题覆盖不到的高频点，且不与已有真题重复。
- **REQ-008**：入库内容里**不出现帖子原文的个人叙述**（公司名、薪资、个人经历、作者昵称），只保留技术题目与我们的解析。
- **REQ-009**：技术词密度低于阈值的帖子**跳过抽取与解析**，不消耗 AI 调用；跳过要计数并可观测，不能静默丢。
- **REQ-010**：专区只有一个内容分类「Java 八股」，不按 JVM / Spring / Redis 等技术栈再细分。

## 质量要求

- 抓取失败不得影响站点其他功能，定时任务异常不得拖垮进程。
- 每日 AI 消耗有上限，超限时停止解析而不是无限消耗额度。
- **每条帖子的解析成本只在通过密度阈值后才产生**（D-06 / REQ-009），阈值可配置。按实测日增量 3-7 帖、约一半含技术内容估算，一天落在 10-40 道题量级。
- 抓取频率克制：每天一次、每次最多翻 2–3 页（20 条/页），不做全量 100 页扫描。
- 遇到接口返回 `success:false`（如 `pageSize>20` 会报"系统未知错误"）时按失败处理并记录，不静默吞掉。
- 存储在 UTC；SQL 只写 mapper；不新增跨模块内部依赖。
- 公开仓库纪律：抓取相关的 Cookie/凭据/User-Agent 细节不进仓库，抓取地址走配置。

## 约束与依赖

- 依赖 WORK-009 的平台凭据与积分机制（解析走平台出钱）。
- 依赖 WORK-004 的知识库承载与 WORK-012 的渲染器。
- 若接掌握度则依赖 WORK-021 / `learning_progress`。
- 牛客站点与接口是**外部依赖，随时可能变更、加风控或关闭**。这是本项最大的长期风险，端口化设计就是为了吸收它。

## 关联工作项

- **WORK-004 知识库**：内容承载、分类、全文检索、学习者只读接口都来自这里。本项不新建内容表。
- **WORK-009 AI 网关与积分配额**：AI 解析走平台凭据，是持续的平台支出，需要额度闸。
- **WORK-020 从零开始学编程**：相邻但不同——那是"课程"（有顺序、有关卡），本项是"选题池"（无序、按时间）。两者都落到知识库条目上，但导航层不该混。
- **WORK-021 个人知识图谱与掌握度**：若专区只做列表页就是纯搬运；接上掌握度才有平台自己的价值。
- **WORK-022 AI 调用追踪**：解析调用应被计入既有遥测，否则这部分成本不可观测。

## 验收标准

- **AC-001**：定时任务按日运行，连续两个自然日都能在库里看到对应批次（或明确记录无新增），不需要人工触发。
- **AC-002**：同一道题跨天、跨帖重复出现后，库中条目数不增长。
- **AC-003**：随机抽查 5 条新入库内容，每条都有非空的 AI 解析正文，且解析是我们自己写的、不是帖子原文。
- **AC-004**：学习者端从首页可达专区，能看到「面经真题」与「平台精讲」两个分类；真题类按时间倒序、点开有来源链接，精讲类无来源链接。
- **AC-005**：人为断网或把抓取源改成不可达地址，任务失败并留下可读的失败原因，站点其他页面不受影响。
- **AC-006**：「平台精讲」的条目与「面经真题」无重复题目，且覆盖到 Java 大纲里真题未涉及的知识点。
- **AC-007**：抽查入库内容，正文里不含作者昵称、公司名、薪资数字等个人信息。
- **AC-008**：喂一条明确无技术内容的面经帖（如「终于找到实习了！」），任务跳过它、不产生 AI 调用，且跳过被计数；喂一条技术密集的帖子，正常产生条目。阈值改配置后该判定随之改变。
- **AC-009**：「面经真题」分类下只有一个分类节点，JVM、Spring、Redis 等主题的题目都落在同一个分类里。

- **Q5 专区形态**：独立顶级入口（`/essays`），还是知识库下挂两个分类？前者是导航层改动，后者几乎零成本；但两个分类要并列展示，独立入口更贴合"专区"的感觉。
