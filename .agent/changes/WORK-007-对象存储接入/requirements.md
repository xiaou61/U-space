## 已确认事实（代码，2026-10-15 逐条复核）

| 项 | 事实 |
| --- | --- |
| 端口 | `FileStorage`（`paideia-knowledge/.../internal/file/`）：`put(byte[] content, String contentType) → id`、`read(id) → Optional<byte[]>`、`delete(id) → boolean`。id 是**不透明标识**，调用方不得解析；实现必须保证不可枚举（因为读端点免鉴权） |
| 端口的 S3 准备度 | 接口注释里明写：`contentType` 是嗅探所得、**「实现可以拿它去做对象元数据（S3 就需要）」**——当初就是照 S3 留的接缝 |
| 唯一实现 | `LocalFileStorage`：文件名 = UUID，先写 `.part` 再 `ATOMIC_MOVE`（"存在"即"完整"），启动时校验目录可写 |
| 元数据位置 | **在 MySQL、不随本项搬**：`knowledge_files(id CHAR(36) PK, original_name, content_type[嗅探], size_bytes, uploader_id, created_at)`。本项只挪**字节** |
| 读端点 | `GET /api/v1/knowledge/files/{id}` **免鉴权**（全项目唯一），安全配置里**只放行 GET**；写入在 `/api/v1/knowledge/admin/files`（需管理员） |
| 配置 | `paideia.knowledge.upload-dir`，有默认值但默认落系统临时目录并**启动告警** |
| 部署现状 | 服务器**没有 Docker**、**只有 8081 从公网可达**（80/443/8080 被云安全组封）、4 核 / 16GB / 79GB 盘；附件目录是 `/opt/paideia-app/uploads` |

**天花板（D-15）**：现在是**单实例本地盘**。多实例部署（或需要多副本）时必须换共享存储——`FileStorage` 端口就是为此留的。

## 目标（草案）

- 附件存储可换成 S3 兼容对象存储，**接在既有端口之后**；业务代码与 `knowledge_files` 表都不动。
- 对外契约不变：前端仍用 `/api/v1/knowledge/files/{id}`；`id` 仍不可枚举、读端点仍只放行 GET。
- 让"换实现"这件事**可验收**（有同一批用例能在两种实现上跑过的证明）。

## 非目标（草案）

- 不做通用插件运行时 / SPI 热加载 / 插件注册表（与 D-02 Spring Modulith 的构建期边界冲突，你 2026-10-10 已定性否决）。
- 不在本项做多实例部署本身（本项只解决它的前置件：共享存储）。
- 不做 CDN、不做对象直接对外暴露（除非裁决 ③ 选预签名 URL 那条）。
- 不做附件去重 / 压缩 / 转码 / 生命周期归档。

## 待你裁决（每项都列了备选与优缺点，不给结论）

**① 本轮范围**

- **A. 真接一个对象存储服务**：一步到位；代价是服务器上新增一个常驻进程（无 Docker，只能手工或 systemd 跑二进制），4 核 16GB 要再分一份内存给它。
- **B. 只做"第二个实现 + 可跑的集成测试"**：不引入常驻服务（测试里跑一个 S3 兼容实现或 mock），花小代价把"将来真换得动"证明到可验收；代价是**没解决真实部署的多实例问题**，接缝只是被验证、没有被使用。
- **C. 暂缓（维持现状）**：零成本；代价是接缝一直没被第二实现验证过——现在只有 `LocalFileStorage` 一个实现，"端口可换"目前是**声明**而不是**事实**。

**② 选型**：RustFS（新，GA 仅约 1 个月，我未能核实）／SeaweedFS（成熟、单二进制）／其它。若要选 RustFS，我建议先做一个**隔离尖刺**（本机起一个、只验"上传/读/删 + 我们的端口能不能接上"），而不是直接写进部署。

**③ 读路径**

- **A. 后端继续代理读**（`/files/{id}` 不变）：改动最小、契约不变、免鉴权论证照旧；代价是字节仍过一次后端。
- **B. 改成预签名 URL / 直读对象存储**：省后端带宽；代价是"UUID 即凭据"的免鉴权论证要重写（预签名有有效期、URL 会泄漏对象存储地址），前端 `resolveMediaUrl` 也要改。

**④ 既有附件**：只对新上传生效（最省）／把既有文件迁过去（线上目前有多少附件我还没统计，要的话我查库）。

**⑤ 部署形态**：与后端同机 systemd 常驻（服务器无 Docker，基本只能这样）／其它。**端口只能绑回环**——8081 是唯一公网口，对象存储端口不外露。

## 验收要点（草案，批准后细化到可执行）

- 换实现后**既有附件用例不改仍全过**（`KnowledgeFileIntegrationTest` 等）——这是端口契约的证明。
- 上传 / 读 / 删三条路径在 S3 实现下各有集成测试。
- 免鉴权读端点仍只放行 GET、`id` 仍不可枚举（有回归断言）。
- 若选迁移：迁移后既有附件可读，且迁移可重入。

## 风险与代价

- 新增常驻服务的内存与运维开销（4 核 / 16GB 的机器上，对象存储进程不是零成本）。
- 若选 RustFS：**极新**（GA 约 1 个月）且我没能独立核实其生产案例——数据放进去再换出来是有成本的。
- 若选 ③B：免鉴权契约与安全论证要重写，属于"改契约"而不是"换实现"。
