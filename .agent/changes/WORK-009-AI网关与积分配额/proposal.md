# 提案 · AI 网关与积分配额

## 一句话

把 AI 调用的**凭据来源**从"每人自带 Key"换成"平台统一配置"，并在调用路径上接一层**积分计量与扣减**；顺手修掉工具循环只上报最后一轮用量这个既有的钱路缺陷。

## 已确认事实

见 `requirements.md` 的「已确认事实」表。最要紧的两条：

1. **换凭据来源只需要动 2 个调用点**（`ConversationService.java:116`、`SummaryService.java:96`，都是 `credentials.access(userId)`）——接缝极小。
2. **用量数据已经在库里**（`ai_messages.token_usage`），缺的不是采集，是"在正确的位置聚合 + 额度 + 视图"。

## 备选方案

### A. 在既有接缝上自建（建议）

**做法**：改 `CredentialService` 的来源为平台凭据；在 2 个调用点前后加"预留 → 结算"；新增积分账户与流水两张表；管理端加"积分调整"与"用量审计"两页。

**优点**：
- 复用已有的用量落库与管理端骨架（`apps/admin` + 路径级 `hasRole('ADMIN')` + `@paideia/ui` 的表格组件），新增依赖为零。
- 不引入新的常驻服务，不增加网络跳数——**我们是流式 SSE，中间插一层网关会多一个要单独验证的转发路径**。
- 计量口径只有一处（我们自己的库），不存在"两本账要对齐"。

**缺点/代价**：
- 计费、额度、审计这三件事要自己写，包括并发不超扣与失败退款这两处容易出错的逻辑。
- 价目表要自己维护（但可以做成配置）。

### B. 引入 sub2api（或同类网关）

**做法**：部署 sub2api（`Wei-Shaw/sub2api`，37k+ star），由它持有上游凭据、发放 key、做计量与配额；Paideia 把上游指向它。

**优点**：网关、计费、审计、账号池调度、并发与速率控制都是现成的。

**缺点/代价**（这是我不建议它的理由）：
- **它的核心价值是"把订阅/账号池变成可分发的 API Key"**——而**我们的用户不拿 Key**，他们用的是我们的界面，调用发生在我们自己的后端。它最值钱的那一半我们用不上。
- 多一个要运维的常驻服务。生产机（codenest-online）是 4 核 16G 且同时跑着 Paideia 与自托管 Firecrawl（api 需 ≥6G），内存与 CPU 都是真的。
- 多一跳网络，且**我们要单独验证它的流式转发**（自托管 Firecrawl 就踩过 nginx 反代只在启动时解析上游 IP、容器一重建整段 502 的坑）。
- **两本账**：我们的 `ai_messages.token_usage` 与它的账要能对上，对不上时以谁为准是一个新的维护面。

### C. 只做用量审计，不做额度与扣减

**优点**：最省，几乎白捡（数据已在库）。
**缺点**：**没有限制消耗的能力**——与"平台出钱"直接冲突。用户端无法感知成本，平台端的成本不可控。**不满足 REQ-003/004/006。**

## 决策

**选 A。** 理由：

1. **接缝已经存在且极小**（2 个调用点），"换凭据来源"本身几乎不花成本。
2. **用量数据已在库**，审计这一半是白捡的；真正要新写的只有"额度 + 扣减 + 管理端两页"。
3. **B 的成本花在我们不需要的那一半上**，而且要多养一个服务与一条转发路径。
4. **不引入新依赖**——符合项目一贯的克制（`always.md` 的 D-15 与"能不加依赖就不加"）。

## 代价（已告知并接受）

- 平台承担全部 token 成本。**本期因为不放免费额度、也不做充值，普通用户积分为 0、AI 实际不可用**——这是刻意的封闭状态，唯一入口是管理员手动发放。
- 一旦将来做充值 + 开放注册，滥用成本直接落到平台账单，届时必须重新评估防刷与注册政策。
- 幂等性只做在"预留-结算"这一对操作上，不追求跨请求的全局一致性；极端情况下（进程在预留后、结算前被杀）会留下一个待对账的预留记录，**本项只保证"不会超扣"，不保证"不会多扣"**——多扣的那笔需要人工按流水核对。这是本项刻意的简化，见 `design.md` 的「已知缺口」。
