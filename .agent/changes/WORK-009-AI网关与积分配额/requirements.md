## 背景

WORK-005/006 让 AI 能力上了线，但走的是纯 BYOK——用户自己配 Key，平台一分钱不出，用量只是"返还给用户看"。这条路线上试过一句实话："做了没用过"（线上两张 AI 表 0 行，真人从未配过 Key）。

现在要做的 `WORK-010`（身份化千人千面 + 求职者面）是一个**AI 重度**的功能：模拟面试、点评打分都是多轮带工具的调用，单次会话的 token 消耗会成倍上升。若继续 BYOK，"没配 Key 就用不了 AI"会让身份面直接空转。因此先把费用与计量这一层落到平台上。

## 目标

- AI 调用的**凭据来源**从"每用户自己的 Key"换成"平台统一配置的上游凭据"，业务代码不接触明文。
- 每次真实的上游调用都**被计量、被扣减、可审计**——包括工具循环里的每一轮。
- 用户能看到自己的余额与消耗；管理员能发放/调整积分并看到谁用了多少。
- 余额不足时**不发上游请求**，并给出前端可区分的错误。

## 非目标

- **不做支付/充值**（本期明确不做；积分只能由管理员手动调整）。
- 不做多供应商路由、账号池调度、负载均衡、粘性会话——那是 sub2api 那一类网关的职责，本项不要（见 `proposal.md`）。
- 不做套餐/订阅/优惠券/退款。
- 不做按模型的差异化定价**策略**（价目表可配，但本期只有一个上游）。
- 不做用户之间的积分转让。
- 不改业务模块：`paideia-knowledge`、`paideia-note` 等不感知积分的存在。

## 用户与工作流程

**学习者**：打开 AI 功能 → 若余额为 0，界面明确告知"积分不足"，并说明当前无自动充值（可联系管理员）→ 有余额时正常使用 → 界面上能看到这次消耗了多少、还剩多少。

**管理员**：在管理端配置上游凭据（baseUrl / model / apiKey）→ 给某个用户增减积分（填数量与原因）→ 在审计页看到"谁、何时、哪个模型、多少 token、扣了多少积分"。

## 功能需求

- **REQ-001 平台凭据**：管理端可配置上游凭据（`baseUrl` / `model` / `apiKey`）；`apiKey` **加密落库**，任何读接口只返回末四位；业务代码只通过既有端口拿到明文，纪律不变（不进日志、不进响应、不被长期持有）。
- **REQ-002 凭据来源切换**：AI 调用不再读用户私有的 `ai_model_credentials`，改读平台凭据。用户侧"配置 Key"的界面与写接口**下线**（保留只读说明，避免用户以为还要自己配）。
- **REQ-003 积分账户**：每个用户一个积分余额；新用户初始为 0。
- **REQ-004 管理员调整**：管理端可按用户**增加或减少**积分，必须记录"操作人 / 时间 / 数量 / 原因"，并作为一条流水留痕。
- **REQ-005 全量计量与扣减**：**每一次真实的上游调用**都按上游返回的用量计量并扣减，**包含工具循环中的每一轮**（这是 REQ 与既有缺陷的交点，见 REQ-012）。
- **REQ-006 额度校验**：余额不足或预留失败时**不发起上游请求**，返回前端可区分的业务错误（不是 500、不是上游错误）。
- **REQ-007 用量审计（管理端）**：一页可查"谁 / 何时 / 哪个模型 / input / output / 扣减积分 / 操作人"，可按用户与时间过滤。
- **REQ-008 用户可见**：用户能看到自己的余额与自身消耗明细（沿用既有的"用量返还给用户看"方向）。
- **REQ-009 请求频次限制**：额度之外仍保留请求频次限制（沿用既有 `UserRateLimiter`），防"余额充足时的突发刷量"。
- **REQ-010 单次调用上限**：可配置单次调用的积分上限，防御"一条消息吃掉全部余额"。
- **REQ-011 价目表可配**：模型单价与"积分 : token"换算率走配置（环境变量/配置文件），**不写死在代码里**——上游调价时不需要重新构建。
- **REQ-012 修既有计量缺陷**：工具循环里每一轮的用量都要累计并上报（当前只上报最后一轮）。**这一条同时修掉一个既有的钱路缺陷**：今天（BYOK 下）用户看到的用量是少报的，切到积分制后会变成平台漏扣。
- **REQ-013 注销**：用户注销时，积分账户、积分流水、审计记录一并删除（见「待确认问题」，全套并入既有注销级联清单）。

## 质量要求

- **扣减按实际用量结算**：先预留、流式结束后按上游返回的实际用量结算并归还差额；上游失败或中断时归还未发生的部分。
- **并发不超扣**：同一用户并发调用时，最终余额**不得为负**。实现上以数据库原子扣减（带余额条件）为准，不用读-改-写。
- **失败语义清晰**：上游不可用、凭据被拒、余额不足，三者在接口层可区分，且都不回显上游原始报文（沿用既有纪律）。
- **平台凭据不泄漏**：任何响应、日志、错误信息里不得出现 `apiKey` 明文或其可逆形式。
- **可追溯**：任一历史助手消息都能对上一条扣减流水。

## 约束与依赖

- 沿用 `ModelAccess` 的明文纪律（D-09 相关：业务代码不接触框架类型）。
- 新迁移接着仓库当前最大号（起草时为 V10）。
- 管理端写接口必须挂在已被 `hasRole('ADMIN')` 保护的路径前缀下（路径规则必须排在更宽规则之前）。
- 平台配置的 `baseUrl` 也走 `UpstreamGuard`（SSRF 防护）。
- 依赖 `WORK-006` 已有的会话/用量落库；不依赖 `WORK-010`。

## 关联工作项

- `related_to: WORK-006`——本项推翻其"纯 BYOK / 不做成本记账"两条裁决，并修复其留下的工具循环计量缺陷；会话、消息、`token_usage` 落库均为其成果，本项复用。

## 验收标准

- **AC-001 平台凭据生效**：清空/删除所有用户私有凭据后，AI 调用仍成功（走平台凭据）。
- **AC-002 工具循环全量计量**：构造一次触发 N 轮工具往返的对话，落库用量与扣减积分 = **N 次调用之和**（含失败路径下绕满轮次的场景）。
- **AC-003 余额不足拦截**：0 积分用户发起 AI 调用时，**上游没有收到任何请求**（以桩或计数证明），且返回可区分的业务错误。
- **AC-004 并发不超扣**：同一用户并发发起超过余额所支撑的调用数，最终余额 ≥ 0。
- **AC-005 管理员调整可审计**：调整积分后，审计页能看到"操作人 / 时间 / 对象 / 数量 / 原因"。
- **AC-006 逐条可对账**：任一助手消息都能对上一条扣减流水（用量与扣减一致）。
- **AC-007 注销清零**：注销后积分账户表与流水表断言行数为 0（并入既有那份逐表清单用例）。
- **AC-008 价目表改配置即生效**：修改换算率配置后，不重新构建即改变同一用量的扣减数。
- **AC-009 凭据不泄漏**：管理端读凭据的响应只含末四位；应用日志中不出现任何明文 Key（含启动日志）。
- **AC-010 用户可见**：学习者端能看到余额与自己的消耗明细。

## 假设

- **本期是一个封闭状态**：不做充值 + 不放免费额度 → **普通用户积分为 0、AI 不可用**；唯一可用路径是管理员手动发放。这是刻意的（与"公开钱包"风险相权衡的结果），但必须写进验收时的说明，否则会被误判为缺陷。
- 上游用量字段（`input` / `output`）足够支撑计价；**若 `ChatUsage` 不暴露缓存命中维度，则拿不到缓存折扣，计费会偏高**——这是已知偏差，需在设计阶段核实并记录。
- 本期只有一个上游模型，不做按模型的多路配置。

## 待确认问题

1. **注销时审计记录删不删？**（**唯一阻断批准的问题**）

## 什么情况下该重审

- 决定要做**充值/支付**：会引入支付集成、对账、退款与更严的防刷，本项的非目标与方法都要重审。
- 引入**第二个上游或按模型差异化策略**：价目表与预留策略需要重审。
- `WORK-010` 出现"零积分导致验收无法进行"的实际阻塞：需要重新讨论是否给新用户一笔极小体验额度（**注意：那会让"公开钱包"风险重新成立**）。
